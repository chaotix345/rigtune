### rules-accuracy-1 (confirmed, high): ram-low's new "6 GB with Distant Horizons" wording contradicts ram-distant-horizons-low-system's "4 GB at most" for any DH user with 6-12 GB of system RAM
- Location: rules/rules-v2.json:1677-1686 (advice[ram-low]) vs rules/rules-v2.json:1790-1802 (advice[ram-distant-horizons-low-system]); identically present in rules/rules-v1.json:1358-1367 and 1446-1457 (0.1.x clients get the same two rules with no cross-exclusion)
- Problem: Commit 4e07893 changed ram-low's text from "Set it to 4 GB" to "Set it to at least 4 GB (6 GB with Distant Horizons or shaders)" specifically to stop it contradicting the DH/shaders-specific advice, but only checked the >=12000MB-RAM DH/shaders rules (ram-distant-horizons, ram-shaders). It did not add any exclusion for advice[ram-distant-horizons-low-system] (modPresent distanthorizons + ramMbAtMost 11999, no heap condition), which recommends capping Minecraft's memory at about 4 GB specifically because the system has under 12 GB. ram-low's `when` (heapMbAtMost 2560, ramMbAtLeast 6144) overlaps that rule's range for any system with 6144-11999 MB of total RAM, so both fire together with directly opposing numbers: "at least ... 6 GB with Distant Horizons" vs "about 4 GB at most".
- Scenario: A user with an 8 GB RAM laptop, Distant Horizons installed, and Minecraft currently allocated 2 GB of heap (a very ordinary starting state before they've touched their launcher's memory setting) opens RigTune. Recommender.advice() (src/main/java/io/github/chaotix345/rigtune/core/recommend/Recommender.java:382-397) has no dedup/priority logic between advice rules, so both fire and are shown together: "Give Minecraft more memory" — "Set it to at least 4 GB (6 GB with Distant Horizons or shaders) in your launcher's Java or memory settings," and "Distant Horizons on a PC with little RAM" — "...so give Minecraft about 4 GB at most. Keep Distant Horizons' render distance short instead..." This exact scenario is not hypothetical: the repo's own `Fixtures.lowEndLaptop()` (ramMb=8192, heapMb=2048) plus `distanthorizons`, used by KnowledgeV2ScenarioTest.ramAdviceWithDhAndShaders:313, reproduces it — the test only asserts ram-distant-horizons-low-system is present and never checks whether ram-low also fired, so the contradiction passes CI unnoticed. Because rules-v1.json carries the identical text and identical `when` clauses for both rules, 0.1.x users hit the exact same contradiction.
- Suggested fix: Give ram-low a `not` guard for the range ram-distant-horizons-low-system already owns, e.g. add `"not": {"modPresent": ["distanthorizons"], "ramMbAtMost": 11999}` to ram-low's `when` (in rules/source/knowledge.json, then regenerate both rules-v1.json and rules-v2.json), or fold the DH-with-little-RAM case into ram-low's own text instead of leaving ram-distant-horizons-low-system's unconditional "4 GB at most" to fire independently. Either way, add a KnowledgeV2ScenarioTest case that asserts the exact set of ram-* ids for {ram=8192, heap=2048, distanthorizons} so this can't regress silently again.
- Verifier: rules/rules-v2.json (e16e146): ram-low's when={heapMbAtMost:2560, ramMbAtLeast:6144} has no `not`/exclusion for the distanthorizons-low-system case; ram-distant-horizons-low-system's when={modPresent:[distanthorizons], ramMbAtMost:11999} has no floor, so both match for any RAM in [6144,11999] with heap<=2560 and DH installed. Text: ram-low says 'Set it to at least 4 GB (6 GB with Distant Horizons or shaders)'; ram-distant-horizons-low-system says '...give Minecraft about 4 GB at most.' Same overlap exists verbatim in rules/rules-v1.json (ram-low at line 1358, ram-distant-horizons-low-system at line 1446), so 0.1.x clients hit it too. Recommender.java advice() (core/recommend/Recommender.java) iterates all AdviceRule entries and calls matches(rule.when) independently per rule with no cross-rule priority/exclusion logic, then put()s each as a distinct id (advice:ram-low, advice:ram-distant-horizons-low-system), so both surface simultaneously when both match. Commit 4e07893 ('fix(rules): ram-low says at least 4 GB (6 GB with Distant Horizons or shaders)') confirms it was a text-only change addressing the ram-distant-horizons/ram-shaders (>=12000MB RAM) contradiction but did not touch the low-system (<=11999MB) rule or add any guard. Fixtures.lowEndLaptop() (src/test/java/.../Fixtures.java) sets ramMb=8192, heapMb=2048 — squarely inside the overlap. KnowledgeV2ScenarioTest.ramAdviceWithDhAndShaders line 313 runs exactly this fixture with distanthorizons and only asserts `.contains("ram-distant-horizons-low-system")`, never checking whether ram-low is also present/absent, so the contradiction passes CI silently. Scenario reproduces: 8GB RAM laptop, DH installed, heap=2048MB (an ordinary default) triggers both contradictory advice strings together.

### apply-safety-1 (refuted, low): dropQueuedUpdates only matches ops that already carry a stored modId, so SPEC 3a's own-updater race guard is blind to exactly the legacy/undo-produced ops it must cover
- Location: src/client/java/io/github/chaotix345/rigtune/client/undo/Staging.java:198-215 (filter at :210-211); corroborated by src/main/java/io/github/chaotix345/rigtune/core/apply/ApplyExecutor.java:311-312
- Problem: dropQueuedUpdates() filters pending.json's ops with `op.id() != null && op.modId() != null && queuedModIds.contains(op.modId()) && loadedModIds.contains(op.modId())`. It never falls back to reading the jar's own fabric.mod.json (the way ApplyExecutor.jarModId/ModJars.readModId already do at apply time, ApplyExecutor.java:342-349) when the stored modId field is absent. ApplyExecutor's own comment at :311-312 documents that an ENABLE_FILE op with no modId is a real, expected shape - 'staged without a mod id (by 0.1.0, or an Undo of a jar it couldn't read)' - not a hypothetical. Grepping every production call site of Op.withModId (DownloadPlanner.java:182,215 and UndoPlanner.java:782) confirms there is no code path that backfills a missing modId onto an already-staged op before dropQueuedUpdates runs, and StagingTest.java's dropQueuedUpdates tests all construct ops with .withModId(...) set, so this exact gap is untested.
- Scenario: A 0.1.0 user upgrades straight to 0.3.0 with a leftover staged mod-update group in pending.json whose ENABLE_FILE op has no modId (the 'real 0.1.0 DH failure' scenario docs/v0.3/plan-review.md's A-H1/H-M2 sections describe as the motivating real-world case), and that mod's own external updater has since queued a newer build in mods/update/ while the mod is still loaded. RealController.rebuild() and unstageQueuedUpdates() call Staging.dropQueuedUpdates(queued, loaded) on every rebuild and at exit (RealController.java:288,313,318-330), but because the op's modId is null the filter at Staging.java:210 never matches it, so the group is never unstaged despite 3a existing specifically to prevent this. At the next exit, RigTune's helper renames/enables jars in mods/ for that mod while the mod's own updater independently installs its own queued build from mods/update/ around the same time, which can leave two jars satisfying the same mod id in mods/ - Fabric then refuses to start until the user manually removes one, or at best the rename loses a race and is retried.
- Suggested fix: In dropQueuedUpdates's filter, don't require the persisted modId field; when it's null, resolve the op's mod id the same defensive way ApplyExecutor already does at apply time (read fabric.mod.json off op.to()/op.from() via ModJars.readModId, treating an unreadable jar as 'no match' as today), and use that resolved id for the queued/loaded comparison instead of relying solely on the stored field. Add a StagingTest case with a null-modId ENABLE_FILE op (as a 0.1.0 legacy import would produce) whose jar's mod id is in both queuedModIds and loadedModIds, asserting it is still dropped.
- Verifier: The filter itself is accurately described: Staging.dropQueuedUpdates (src/client/java/io/github/chaotix345/rigtune/client/undo/Staging.java:210-212) requires `op.modId() != null` and never falls back to reading the jar's own fabric.mod.json, unlike ApplyExecutor.runGroup which always re-derives the id from the actual file (ApplyExecutor.java: `modIds[i] = jarModId(Path.of(op.from()))`, unconditional, then compares to op.modId() only if present). So the code-reading premise is correct in isolation.

However, the finding's concrete motivating scenario and its practical reachability are both wrong:

1. The cited 'real 0.1.0 DH failure' is NOT a null-modId case. The actual captured real-instance fixture (src/test/resources/v010/real-instance/last-apply.json:106-118, and confirmed again in the analogous rigtune-0.1.0-shaped fixture used by AC4.1/H-M2) shows the failed/carried-over ENABLE_FILE op for the Distant Horizons update explicitly has `"modId": "distanthorizons"` set. Every op the real, released 0.1.0 client wrote (all 16 ops in that file) carries a populated modId. This directly contradicts the finding's claim that this is 'the exact real-world case docs/v0.3/plan-review.md's A-H1/H-M2 sections describe.'

2. Traced all three live call sites of `Op.enableFile(...).withModId(...)` in the current e16e146 tree: DownloadPlanner.addMod (DownloadPlanner.java:159-163, throws `notAMod` before calling withModId if the freshly-downloaded jar's id is unreadable — jarModId passed is always non-null), DownloadPlanner.updateMod (DownloadPlanner.java:204-207, same guard, fixed in review-4/commit 1a13e4b per docs/reviews/review-4.md), and UndoPlanner.netOps (UndoPlanner.java:782, `withModId(content.info() == null ? null : ...)`). For the third site, UndoPlanner.move() (UndoPlanner.java:636-639) rejects any re-enable candidate whose content has `info() == null` with a NOT_A_MOD failure *before* that group's moves are ever committed to `sim`/`accepted`, so a null-info content can never end up 'isActive' by the time netOps() runs — this matches this project's own prior verification (docs/reviews/review-4.md: 'netOps()'s own content.info()==null ? null : ... null-coalescing ... is dead code in practice, not a live bypass'), which I independently re-confirmed by reading move()/netOps() at e16e146.

3. The only fixture that produces a genuinely null-modId ENABLE_FILE op is `pending-pre-groups.json`, a hand-written test fixture representing a hypothetical pre-id/pre-group era of the format (MigrationV010Test.java:112-120) — not a shape any actually-released client (confirmed via the real captured/real-instance data) ever wrote, so it is not a reachable real-world upgrade scenario today.

4. Even granting a hypothetical null-modId op reached pending.json, ApplyExecutor.duplicateProblem() (ApplyExecutor.java:289-308) runs at actual apply time using an id re-derived straight from the jar file being enabled (not the stored field), and would abandon the whole group (Status.ABANDONED, nothing renamed — see runGroup's `if (duplicate != null) { ...ABANDONED...; return; }` before any file op executes) if the external updater's own jar was already installed under that mod id, so the claimed 'two jars with the same mod id / Fabric refuses to start' outcome is independently guarded against in the case that matters most (external update lands before RigTune's helper runs).

Given the scenario cannot be reproduced with any currently-reachable pending.json shape, and the cited real-world incident actually had modId populated, this finding is refuted as a practical, high-severity defect; the underlying code asymmetry (dropQueuedUpdates not re-deriving from the jar like ApplyExecutor does) is real but currently dead code, worth a defensive follow-up at most low severity, not the claimed high.
- Decision: Refuted as high (every op a released client wrote carries a mod id; ApplyExecutor re-reads the jar's id at apply time). Defensive FIX anyway: dropQueuedUpdates reads the jar's own id for an enable staged without one (test anEnableStagedWithoutAModIdIsMatchedByItsJar).

### security-1 (confirmed, medium): gametest matrix's mc-id validation isn't fully anchored, so a malformed versions/<mc> directory name can inject a literal newline into an unquoted CI run: step
- Location: tools/gametest_matrix.py:17,21-25,45-51 and .github/workflows/build.yml:125
- Problem: _VERSION = re.compile(r"^(\d+)\.(\d+)(?:\.(\d+))?(-[0-9A-Za-z.-]+)?$") is checked with `_VERSION.match(mc)` (tools/gametest_matrix.py:21-25), not `fullmatch`/`\A...\Z`. Python's `$` matches either at the absolute end of the string or immediately before a single trailing newline, so `_VERSION.match("26.2\n")` succeeds (verified empirically: `_VERSION.match('26.2\n').group(0) == '26.2'`, while any additional trailing content, e.g. `'26.2\ninjected'` or `'26.2\n\n'`, correctly fails). `legs()` (lines 45-51) then puts the *raw, unvalidated* directory name (not the matched substring) into the JSON matrix as `mc`. build.yml's client-gametest job consumes that value unquoted in a `run:` step: `run: ./gradlew :${{ matrix.mc }}:runProductionClientGameTest --stacktrace` (build.yml:125). GitHub Actions performs this `${{ }}` substitution as raw text before the shell parses the script, so a value ending in a real newline splits that one line into two physical shell lines. This directly contradicts the code comment at gametest_matrix.py:16 ('the id goes into the workflow's shell steps, so the suffix is limited to letters, digits, dots and dashes') — that guarantee doesn't actually hold for a trailing-newline suffix.
- Scenario: A contributor (including via a fork PR, since `pull_request` checks out the PR's proposed tree before any maintainer review) adds a new directory literally named `versions/26.4<LF>` (a bare trailing line-feed byte, which both POSIX filesystems and git permit in a filename) containing a minimal gradle.properties. `python3 tools/gametest_matrix.py` accepts it as a valid node and emits `{"mc": "26.4\n", "backend": "OpenGL"}` instead of refusing it. In the generated client-gametest job, build.yml:125 expands to two lines — `./gradlew :26.4` and `:runProductionClientGameTest --stacktrace` — breaking that leg's build step. Because the `$` quirk only ever allows a single, content-free trailing newline (anything after it fails the regex, as shown above), the attacker cannot inject arbitrary shell commands or exfiltrate anything through this path — client-gametest carries no secrets and build.yml's permissions are contents:read only — so the concrete, demonstrated impact is a broken/misleading CI job rather than code execution or secret exposure. It is nonetheless a real gap in the stated character-allowlist safety check for a value that flows unquoted into a shell run: step, and it's the exact class of hazard ('matrix feeding run: steps') this review was asked to check.
- Suggested fix: In tools/gametest_matrix.py, validate with `_VERSION.fullmatch(mc)` (or anchor the pattern with `\A` and `\Z` instead of `^`/`$`) so any trailing byte, including a lone newline, is rejected the same way `'26.2\ninjected'` already is. As defense in depth, also quote the interpolations that reach unquoted shell contexts, e.g. `run: ./gradlew ":${{ matrix.mc }}:runProductionClientGameTest" --stacktrace`, so a future validation gap in this or another producer of matrix values can't split or otherwise alter the command line.
- Verifier: tools/gametest_matrix.py:17,21-25,45-51 (git show e16e146) exactly matches the citation: _VERSION = re.compile(r"^(\d+)\.(\d+)(?:\.(\d+))?(-[0-9A-Za-z.-]+)?$") at line 17, checked via `_VERSION.match(mc)` at line 22 (not fullmatch/\A..\Z), and `legs()` (lines 45-51) appends the raw `mc` string (from `nodes()`, which is `p.name`, the literal directory name) into the matrix dict, not the regex-matched substring. Empirically verified in this session: `_VERSION.match('26.4\n').group(0) == '26.4'` succeeds, while `_VERSION.match('26.4\ninjected')` and `_VERSION.match('26.4\n\n')` both correctly fail — confirming Python's `$` matches immediately before one single trailing newline at end-of-string, exactly as claimed, and that only a bare trailing LF (no further content) can sneak through. build.yml:125 (git show e16e146) is verbatim `run: ./gradlew :${{ matrix.mc }}:runProductionClientGameTest --stacktrace` — an unquoted interpolation in a shell run: step, and the workflow's triggers include plain `pull_request` (build.yml top, permissions: contents: read) so a fork PR's tree is checked out and its `versions/<name>` directory names flow through this path unreviewed. GitHub Actions' `${{ }}` substitution is textual and happens before the shell parses the script, so a value ending in a real newline byte would split this run: line into two physical lines, contradicting the safety comment at line 16. The finding's own scenario correctly notes the impact is limited to a broken/misleading CI leg (only a lone trailing newline can pass, not arbitrary injection; no secrets are in scope under contents:read), which matches what the code shows — a real, demonstrated gap in the stated character-allowlist guarantee, not a hypothetical or already-mitigated one.
- Decision: FIX: gametest_matrix.py uses fullmatch; build.yml quotes the Gradle task path. Test test_a_trailing_newline_is_refused.
