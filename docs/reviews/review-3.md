### apply-safety-1 (confirmed, medium): A null mod id on an ENABLE_FILE op completely bypasses the duplicate-mod-id safety check
- Location: src/main/java/io/github/chaotix345/rigtune/core/apply/ApplyExecutor.java:293 (duplicateProblem), src/main/java/io/github/chaotix345/rigtune/core/modrinth/DownloadPlanner.java:94-115 (addMod), src/main/java/io/github/chaotix345/rigtune/core/history/UndoPlanner.java:620 (netOps) and :561 (violations)
- Problem: ApplyExecutor.duplicateProblem() (the check that stops a mod from being installed twice under different jar names, which would crash Fabric at startup) only runs for an ENABLE_FILE op when op.modId() != null: `if (op.type() != ENABLE_FILE || op.modId() == null || !Files.exists(...)) continue;` (ApplyExecutor.java:293). Any ENABLE_FILE op whose modId is null is therefore enabled completely unconditionally, with zero duplicate/collision protection. Two producers can legitimately create such an op: (1) DownloadPlanner.addMod (DownloadPlanner.java:100-115) sets `withModId(jarModId)` where `jarModId = modIdOf.apply(pending)` — this is null whenever the just-downloaded, hash-verified jar's fabric.mod.json can't be parsed (wrong/corrupted file, non-Fabric loader variant, resource pack mislabeled as a mod, etc. — hash verification only proves the bytes match what Modrinth served, not that the content is a valid Fabric mod). Unlike updateMod (line 133), which falls back to `update.modId()` from the existing installation, addMod has no such fallback. (2) UndoPlanner.netOps (UndoPlanner.java:620) does the same for a re-enable during Undo: `withModId(content.info() == null ? null : content.info().id())` — null whenever the disabled jar being restored can't be parsed. The same 'unreadable jar' blind spot also silently skips UndoPlanner's own duplicate/dependency simulation (`violations()`, UndoPlanner.java:561: `if (info == null) continue;`), so neither the planning-time check nor the execution-time check catches it.
- Scenario: A rules-v2 entry (or the Modrinth dependency resolver) ends up pointing an Add-mod recommendation at a Modrinth version whose primary file is not actually a valid Fabric mod jar (e.g. a wrong-loader build, a corrupted upload that Modrinth's own hash still matches, or a resolver/rules bug picking the wrong file id — ModrinthVersion.primaryFile() in ModrinthVersion.java:44-49 does no content validation, it just takes the file Modrinth flags primary). RigTune downloads it, the hash check passes, ModJars.readModId() can't find/parse fabric.mod.json so returns null, and DownloadPlanner still stages `Op.enableFile(pending, target).withModId(null)`. At apply time this op sails through duplicateProblem() untouched (no other mod on disk can 'match' a null id) and gets moved into mods/ as an active .jar. If that mod id happens to collide with an already-installed mod under a different filename, or if the file itself is malformed enough that Fabric's mod-discovery step errors out on it, the result is exactly the 'unstartable game' outcome this dimension is about to catch — and because modId is null, the journal change also has no mod id recorded, so Undo/UndoPlanner can't identify or safely reason about it either.
- Suggested fix: Treat an ENABLE_FILE op with modId == null as unsafe by default instead of exempt: either refuse to stage it in DownloadPlanner.addMod when modIdOf(pending) returns null (mirroring updateMod's requirement that a mod id be known before proceeding, deleting the pending download the way dropDuplicate() already does), or have ApplyExecutor.duplicateProblem() require a readable fabric.mod.json (reject/hold the op when the new jar's own id can't be read) rather than skipping the check outright when modId is null. Apply the same fix to UndoPlanner.netOps for the re-enable case, or at least surface a clear 'this file's mod id can't be confirmed' skip reason instead of silently applying it.
- Verifier: Verified against 5f57eee. ApplyExecutor.duplicateProblem (ApplyExecutor.java:290-300) skips any ENABLE_FILE op with op.modId()==null: `if (op.type() != ENABLE_FILE || op.modId() == null || !Files.exists(...)) continue;` — no other check in ApplyExecutor validates jar content; containmentProblem/problem() (ApplyExecutor.java:407-439) only checks path containment and safe filename, never mod-id readability. DownloadPlanner.addMod (DownloadPlanner.java:99-115) computes `jarModId = modIdOf.apply(pending)` and only guards against duplicates `if (jarModId != null && !attempt.modIds.add(jarModId))` (line 108) — when jarModId is null this condition short-circuits false, so the op is staged unconditionally via `Op.enableFile(pending, target).withModId(jarModId)` (line 115) with no null fallback (unlike updateMod at line 133, which does `Objects.requireNonNullElse(modIdOf.apply(pending), update.modId())`). ModJars.readModId (ModJars.java:29-45) returns null whenever fabric.mod.json is absent, has no 'id' key, or the id isn't a JSON primitive, and ModJars.modIdOf (ModJars.java:19-26) also swallows IOException (corrupt zip / unparseable JSON) into null — confirming hash verification (which only checks byte-for-byte match against Modrinth's declared hash) says nothing about content validity, and ModrinthVersion.primaryFile() (ModrinthVersion.java:42-46) does no content validation, just takes whichever file Modrinth's metadata flags primary. UndoPlanner.netOps (UndoPlanner.java:618-620) has the identical null-propagation: `Op.enableFile(...).withModId(content.info() == null ? null : content.info().id())`, and UndoPlanner.violations() (UndoPlanner.java:550-561) independently skips any jar whose info is null (`if (info == null) continue;`) in its own duplicate/dependency simulation, so neither the undo-planning-time nor apply-time check catches it either. No test in DownloadPlannerTest.java or ApplyExecutorTest.java exercises a null-modId ENABLE_FILE op, and no design doc (docs/v0.2/design/*.md, docs/v0.2/plan-review.md, docs/DESIGN.md) documents this as a known/accepted gap — grepping for 'duplicat', 'modId null', 'unreadable', 'unparseable' in those docs turns up nothing addressing this specific bypass. The finding's mechanism is accurate in every particular I could check. The one place I'd soften it: the 'mod id collision' framing is a bit loose, since with modId==null there is by construction nothing to compare against InstalledJars.withModId, so the concrete harm isn't really 'duplicate load' but rather 'an unvalidated, unidentifiable jar file gets moved into mods/ with zero safety check' — which can still plausibly break Fabric's mod-discovery/startup if the file is a corrupted or non-Fabric jar that Modrinth genuinely served (or a stale/mismatched disabled jar restored via Undo), but that consequence depends on Fabric Loader's own tolerance for a bad jar in mods/, which is external behavior not verifiable from this repo. Given the real precondition is an atypical external state (a mod author's bad Modrinth upload, or version metadata error) rather than an internal RigTune bug, and the resulting crash is plausible but not certain, medium (missing safety check on a genuine edge case) is the right rating — same as the reported severity.
- Decision: FIX: never enable a jar whose fabric.mod.json id cannot be read (DownloadPlanner.addMod drops it with an error; ApplyExecutor reads the id from the jar when the op has none and fails the op if unreadable; UndoPlanner skips such re-enables with a reason).

### security-1 (refuted, low): Unbounded recursion on Condition.not/anyOf lets a malicious rules document stack-overflow the client, uncaught
- Location: src/main/java/io/github/chaotix345/rigtune/core/rules/Condition.java:36-37; ConditionEvaluator.java:60-68,100-101,108-117; ConditionAdapterFactory.java:55-79; RulesLoader.java:44-52,82-97; RemoteRulesFetcher.java:40-70
- Problem: Condition.not (a self-referential Condition) and Condition.anyOf (a List<Condition>) can nest arbitrarily deep; nothing in the schema, the Gson parsing path (ConditionAdapterFactory.read(), which recurses into every nested Condition via delegate.fromJsonTree) or the evaluator (ConditionEvaluator.poisoned() and node()/anyOf(), which recurse once per not/anyOf level with no depth counter) bounds that nesting. Every other 'huge/malicious remote input' vector in this same file has an explicit guard — gpuTiers/cpuTiers/gpuModelMatches patterns are length-capped at 200 chars (RulesDocument.PatternRule.MAX_PATTERN_LENGTH) and matched under BudgetedChars' 1,000,000-char ReDoS budget, and RulesLoader.parse() explicitly catches OutOfMemoryError for an oversized document — but nesting depth has no equivalent limit, and the resulting failure mode (StackOverflowError) is a java.lang.Error, not an Exception, so it is NOT caught by RulesLoader.parse()'s `catch (JsonParseException | IllegalStateException e)` / `catch (OutOfMemoryError e)`, by RulesLoader.loadCache()'s `catch (IOException | IllegalArgumentException e)`, or by RemoteRulesFetcher.fetch()'s `catch (Exception e)`.
- Scenario: A compromised/MITM'd rules-v2.json (or rules-v1.json, fetched from https://raw.githubusercontent.com/chaotix345/rigtune/main/rules/ by default, or from any http(s) host via -Drigtune.rules.baseUrl) contains one rule whose `when`/`recommendWhen` is `{"not":{"not":{"not": ... {"always":true} ...}}}` nested tens of thousands of levels deep — about 8 bytes of JSON per level, so >100,000 levels fit comfortably inside the 2 MB MAX_RULES_BYTES cap. Parsing (Condition.java's fields are consumed recursively by Gson/ConditionAdapterFactory) and/or evaluating that condition (ConditionEvaluator.node()/poisoned() recurse the same depth) exhausts the JVM call stack. In RealController.loadRules() (RULES_EXECUTOR, via CompletableFuture.runAsync with no exceptionally()/whenComplete() attached) the resulting StackOverflowError is swallowed silently by CompletableFuture's internal Throwable handling with no log line and no status update, so the client's rules refresh for that launch simply stops working with zero visible symptom. Worse, a payload deep enough to survive the parse in RemoteRulesFetcher.fetch() (so RulesLoader.saveCache() writes it to config/rigtune/rules-v2-cache.json) but too deep for RulesLoader.loadCache()'s own re-parse or for ConditionEvaluator's evaluation pass leaves that cache file permanently poisoned: RulesSources.local() is read first on every future launch (even fully offline / with remote rules turned off), so every future launch repeats the same uncaught crash and the whole recommendation engine stays silently broken until a user who has no error message to go on manually finds and deletes rules-v2-cache.json. The identical unbounded-recursion pattern (Condition.not/anyOf, matches()'s recursive evaluation) also exists in the pinned v0.1.0 core under src/test/java/.../v010/core/rules/, and rules-v1.json (served to already-shipped 0.1.x clients, which can receive no further code fix) carries the same `not`/`anyOf` keys, so the same payload threatens 0.1.x installs too.
- Suggested fix: Track recursion depth (or pre-scan/limit total node count) while parsing and evaluating a Condition tree — e.g. reject/treat-as-poisoned any Condition whose not/anyOf chain exceeds a small bound (a few dozen is plenty for any real rule) in ConditionAdapterFactory.read() and again as a cheap sanity check in ConditionEvaluator.node()/poisoned(). Independently, catch StackOverflowError (or widen to `catch (Throwable e)`) alongside OutOfMemoryError in RulesLoader.parse()/loadCache() and RemoteRulesFetcher.fetch() so a still-pathological document degrades to 'skip this candidate' with a logged warning instead of an unhandled Error; also attach an exceptionally()/whenComplete() to the CompletableFuture in RealController.reloadRules() so a swallowed failure is at least logged. Since 0.1.x can't be patched, also add the same depth check to tools/update_rules.py's rules-v1/v2 validation (and rules/REVIEW.md's generated diff) so a deeply-nested condition can never be merged into the rules feed in the first place.
- Verifier: Gson's JsonReader (both 2.10.1 and 2.14.0, the versions actually present in this project's Gradle cache for MC 26.2/26.3) hard-codes a default nestingLimit of 255 in its constructor (confirmed by disassembling the class: `sipush 255; putfield nestingLimit`), and JsonReader.push() throws MalformedJsonException once that is exceeded. RulesLoader.java:47 calls the unmodified `GSON.fromJson(json, RulesDocument.class)`, so any Condition tree nested past 255 levels fails to parse. MalformedJsonException extends IOException; Gson wraps that as JsonIOException, and JsonIOException extends JsonParseException (confirmed via javap on Gson.class and the exception classes) — so this failure IS caught by RulesLoader.parse()'s existing `catch (JsonParseException | IllegalStateException e)` (RulesLoader.java:48), turned into a clean IllegalArgumentException, and handled normally by loadCache/fetch's existing catches. 255 levels of recursion in ConditionEvaluator's simple node()/poisoned() methods is also nowhere near enough to cause a real StackOverflowError. The finding's premise that 'nothing bounds nesting depth' and that a payload needs '>100,000 levels' to exploit this is factually incorrect for the actual Gson version in use.
- Decision: No action (refuted: parsing depth is bounded in practice and failures fall back; see the verifier).

### security-2 (confirmed, low): SettingKeys.changeable() doesn't validate the sodium.* key suffix the way it validates dh./iris.*
- Location: src/main/java/io/github/chaotix345/rigtune/core/model/SettingKeys.java:38-48
- Problem: For the DH and Iris namespaces, changeable() requires the suffix after the prefix to match SAFE_DOTTED_KEY (letters/digits/underscore segments only) precisely so that — per the class's own comment — remote-rules-supplied keys can't contain 'characters that could break the TOML or properties syntax' or path-traversal segments. The sodium.* branch has no equivalent check: `key.startsWith(SODIUM_PREFIX) && key.length() > SODIUM_PREFIX.length()` accepts any non-empty suffix, including dots, quotes, control characters or thousands of consecutive dots. That string is later split on '.' and used to walk/create nested JsonObjects in SodiumConfigPatcher.set() (RealController.java:301, `set.key().substring(target.prefix().length())`), with no independent validation at that point either.
- Scenario: Today this isn't reachable through the shipped recommendation flow: Recommender.settings() (Recommender.java:304) only turns a rule's SettingRule into a SetSetting action when `snapshot.has(key)` is true, i.e. the key must already exist in the user's real sodium-options.json, which rules out an attacker inventing a new, pathologically deep or malformed sodium key. But that pre-existence check is the *only* thing standing between an untrusted rules key and SodiumConfigPatcher, is specific to one call site, and isn't part of the allowlist itself — unlike DH/Iris, where the allowlist enforces the safety property directly. Any future code path that constructs a SetSetting for a sodium.* key without first checking it against the live file (e.g. a new UI affordance, or a change to the Undo/rebuild path) would inherit no protection from SettingKeys at all.
- Suggested fix: Give sodium.* the same treatment as dh./iris.: `key.startsWith(SODIUM_PREFIX) && safeNamespaced(key, SODIUM_PREFIX)`, so the allowlist itself — not an incidental call-site check — is what keeps a settings key safe to hand to SodiumConfigPatcher.
- Verifier: SettingKeys.java:38-48: the sodium.* branch of changeable() is `key.startsWith(SODIUM_PREFIX) && key.length() > SODIUM_PREFIX.length()`, with no SAFE_DOTTED_KEY check, unlike dh./iris. which use safeNamespaced(). SodiumConfigPatcher.set() (SodiumConfigPatcher.java:35-52) splits the raw suffix on '.' with no validation of its own, walking/creating nested JsonObjects. Confirmed the only current protection is Recommender.settings()'s `!snapshot.has(key)` gate (Recommender.java:300-301) at the sole call site, exactly as the finding describes — a real defense-in-depth gap in the allowlist itself, not currently reachable through the shipped flow.
- Decision: FIX: validate the sodium.* key suffix with the same safe charset as dh./iris.

### security-3 (confirmed, low): -Drigtune.rules.baseUrl accepts plain http:// for any host, unlike the equivalent Modrinth property
- Location: src/main/java/io/github/chaotix345/rigtune/core/rules/RulesSources.java:38-55
- Problem: RulesSources.baseUrl() accepts any URI whose scheme is 'https' or 'http' as long as it has a host — plain HTTP is allowed for an arbitrary remote host, not just localhost. HttpModrinthClient's equivalent test-only override (extraDownloadOrigin(), HttpModrinthClient.java:230-244) deliberately restricts a plain-http base URL to loopback addresses (localhost/127.0.0.1/::1) precisely so the same kind of JVM property can't be used to downgrade a real download to cleartext.
- Scenario: Both properties are documented as test-only (docs/RULES_SCHEMA.md: '-Drigtune.rules.baseUrl=<folder URL> ... (for tests)'), so this requires whoever launches the JVM to already be setting a system property — not a remote network attacker. But if a launcher profile, modpack JVM-args field, or misconfigured environment ever sets this property to a non-loopback http:// URL, RigTune would fetch its entire rules feed (the primary untrusted-input surface reviewed here) over plaintext HTTP with no TLS, making it trivially tamperable by anyone on the network path, whereas the Modrinth client's identical mechanism was explicitly hardened against exactly this.
- Suggested fix: Apply the same loopback restriction RulesSources uses for HttpModrinthClient's base URL property: allow plain http only when the host is localhost/127.0.0.1/::1, require https otherwise.
- Verifier: RulesSources.baseUrl() (RulesSources.java:39-55) accepts `http` for any host with a hostname, no loopback restriction. HttpModrinthClient.extraDownloadOrigin() (HttpModrinthClient.java:228-239) explicitly restricts its equivalent http override to localhost/127.x.x.x/::1 via a `loopback` check. docs/RULES_SCHEMA.md:29 confirms -Drigtune.rules.baseUrl is documented as test-only, matching the finding's own caveat about exploitability requiring a JVM-property-setting actor.
- Decision: FIX: -Drigtune.rules.baseUrl requires https, except localhost (as the Modrinth property does).

### compat-1 (confirmed, medium): rules-v1.json's Nvidium avoidWhen was silently weakened for 0.1.x, and the differential safety test can't detect this class of regression
- Location: rules/source/knowledge.json:334-337 (the manual "v1" override); rules/rules-v1.json:741 (current projected output); src/test/java/io/github/chaotix345/rigtune/core/rules/RulesV1DifferentialTest.java:211-230 and :200-204 (the safety-net gap)
- Problem: Comparing `git show v0.1.0:rules/rules-v1.json` with the current `rules/rules-v1.json` at 5f57eee, Nvidium's `avoidWhen` lost its `{"gpuTierAtMost": 2}` branch: v0.1.0 shipped `anyOf[not gpuVendor:nvidia, gpuTierAtMost:2, flags:shaders-enabled]`; the current file has `anyOf[not gpuVendor:nvidia, flags:shaders-enabled]`. This comes from a hand-authored `"v1"` override in knowledge.json (since v2's avoidWhen uses a v2-only `gpuModelMatches` regex that 0.1.x can't evaluate, the maintainer wrote a v1-specific avoidWhen instead of using the updater's automatic per-field safeguard) that simply drops the tier check rather than reproducing it. The `avoided()` recommendation (in the pinned v0.1.0 Recommender, `avoided()` at RulesV1DifferentialTest's copy, mirrors src/main/java's own Session.avoided()) fires independently of `recommendWhen` whenever the mod is already installed and avoidWhen is TRUE, so this is not compensated by the unrelated, still-conservative recommendWhen (tier>=4) gating additions. `RulesV1DifferentialTest` is supposed to prevent exactly this kind of regression (docs/RULES_SCHEMA.md and the class's own javadoc: "rules-v1.json may only take actions away from a 0.1.x user ... no lost warning"), but its `Outcome` record only classifies ids starting with `conflict:` or `advice:` as protected "warnings"; a `disable:<modId>` recommendation produced by an avoidWhen match lands in `actions()` instead, and `actions()` is only checked one-directionally for *additions* (`after.actions() minus before.actions()`), never for losses. So a lost avoid/disable suggestion is invisible to the test regardless of which hardware profiles are in its matrix, and CI stayed green through this change (rules revision 4 -> 7).
- Scenario: A 0.1.x user (has not upgraded to 0.2.0) owns an older/weak NVIDIA GPU that RigTune classifies as effective tier <=2 (e.g. an entry-level dedicated NVIDIA card), has manually installed the beta mod Nvidium, and is not running a shader pack. Under the rules-v1.json shipped with v0.1.0 (revision 4), RigTune shows a ticked 'Disable Nvidium — Nvidium needs an NVIDIA GTX 16-series or RTX graphics card ... it can't help on this setup' recommendation (impact medium) every time rules are (re-)evaluated. After 0.2.0 ships and the updater's regenerated rules-v1.json goes live on raw.githubusercontent.com (revision 7, current HEAD), that same 0.1.x client's next remote rules fetch replaces its cache and this recommendation silently stops appearing, with no test or REVIEW.md flag catching the behavior change as unsafe (REVIEW.md (d) lists 'mods[nvidium] | v1 override: avoidWhen, recommendWhen' but only as a note to manually eyeball, not something the automated checks verify for conservativeness).
- Suggested fix: Restore the tier check in the v1 override's avoidWhen (e.g. `{"gpuTierAtMost": 2}` alongside the existing branches, mirroring v0.1.0's condition) so 0.1.x keeps getting the same disable suggestion it always had. Separately, close the safety-net gap: extend RulesV1DifferentialTest's Outcome/differences() to also flag any `disable:` (or more generally, any action id) that is present in `before` but absent from `after` as a 'lost' change requiring review, not just entries prefixed `conflict:`/`advice:` — this is what would have caught the regression automatically instead of relying on manual REVIEW.md eyeballing of every v1 override.
- Verifier: Diff verified directly. rules/source/knowledge.json's manual "v1" override for nvidium (lines ~334-337) reads avoidWhen: anyOf[not gpuVendor:nvidia, flags:shaders-enabled] — no gpuTierAtMost branch. The current generated rules/rules-v1.json:760-773 (5f57eee) matches that override exactly. `git show v0.1.0:rules/rules-v1.json` (lines 761-779) had a third anyOf branch `{"gpuTierAtMost": 2}` that is absent from HEAD; `git diff v0.1.0..5f57eee -- rules/rules-v1.json` shows it being deleted. src/test/resources/v010/rules-v1-baseline.json is byte-identical to the v0.1.0 file (confirmed via diff), so it is the differential test's 'before'. In the pinned v0.1.0 Recommender (src/test/java/.../v010/core/recommend/Recommender.java:150-159), Session.avoided() fires disable(mod,...) whenever avoidWhen matches an installed mod, independent of recommendWhen; disable() (line 315-327) builds id "disable:"+modId with a real Action.DisableMod and selectedByDefault=true — i.e. an 'action', not a 'warning'. In RulesV1DifferentialTest.java, Outcome.warnings() only collects ids prefixed conflict:/advice: (line 218); disable: ids land in actions()/ticked() instead. differences() (lines 199-204) only ever computes after.actions() minus before.actions() (additions) and ticked-but-not-before, then separately before.warnings() minus after.warnings() (lost warnings) — it never computes before.actions() minus after.actions(), so a lost disable/avoid action is structurally invisible to the test. The test's own hardware matrix contains a concrete trigger: 'gtx-1660-laptop' (NVIDIA GeForce GTX 1660 Ti with Max-Q Design, no shader flag) which resolves to gpuTier 2 via the generic laptop tier rule in rules-v1.json's gpuTiers (falls through the more-specific RTX-laptop patterns to the `(?:RTX|GTX)\s*\d{3,4}\b.*Laptop` tier-2 rule), combined with modSets 'sodium+nvidium' (line 282) — under the v0.1.0 baseline this profile makes avoidWhen true (gpuTierAtMost:2) and fires disable:nvidium; under the current rules-v1.json avoidWhen evaluates false (not nvidia=false, shaders=false) so no disable fires, and nothing else produces disable:nvidium for that profile, making it a genuine silent loss the test cannot see. rules/REVIEW.md's section (d) does list 'mods[nvidium] | v1 override: avoidWhen, recommendWhen' but only as a bare table row for manual eyeballing, with no automated conservativeness check — corroborating that this is a real, currently-unflagged regression rather than a documented/known-accepted deviation. docs/v0.2/plans/ws-h.md:63 confirms the v2 rules intentionally still disable nvidium for a Pascal-era GTX 1080 via gpuModelMatches, underscoring that the equivalent v1 protection for tier<=2 NVIDIA cards was dropped only in the v1 projection, not intentionally deprecated behavior.
- Decision: FIX: restore the v0.1.0 Nvidium v1 avoidWhen exactly (including gpuTierAtMost 2), and make the differential test flag lost disable: actions. (This reverses the coordinator decision #3 given to WS-H.)

### rules-accuracy-1 (confirmed, medium): Nvidium's gpuTierAtLeast:3 floor reintroduces the exact laptop-GPU gap the model regex was added to fix
- Location: rules/source/knowledge.json:330 (mods[nvidium].recommendWhen); identical in rules/rules-v2.json (generated); interacts with gpuTiers pattern at rules/source/knowledge.json:7
- Problem: recommendWhen requires BOTH gpuTierAtLeast:3 AND gpuModelMatches (the Turing+/mesh-shader whitelist regex from triage.md §5). But gpuTiers buckets any *laptop* NVIDIA card not explicitly listed in the higher-tier laptop patterns (lines 5-6, which only cover RTX 30/40/50-series-Laptop) into the generic `"(?i)(?:RTX|GTX)\s*\d{3,4}\b.*Laptop"` rule at tier 2 (knowledge.json:7). That generic bucket catches RTX 2060/2070/2080 Laptop, RTX 3050/3050 Ti Laptop, and GTX 1650/1650 Ti/1660 Ti Laptop — all genuinely Turing-or-newer, mesh-shader-capable per Nvidium's own README (quoted in triage.md §5: "nvidia gtx 1600 series or newer... turing+"), and all matched by gpuModelMatches. Because their raw tier is 2, the AND with gpuTierAtLeast:3 blocks them anyway. This is precisely the gap triage.md §5 identified and proposed fixing by *dropping* the tier check entirely ("gpuModelMatches lets the rule check the real thing directly...
