## STUTTER-3's refusal rate, estimated from the rules (the lead's question)
CHANGED needs, between the capture's start (StutterService.java:225, the first tick with a level) and the analysis, one of:
RW-11's four values (RD, SD, shaders on/off, DH rendering) differing with both ends known; a DISPLAY difference (framebuffer
width/height or `options.fullscreen`; minimising doesn't count, since vanilla ignores a 0x0 framebuffer); a SETTING difference
with both values present (the 30 ShareKeys.V1 performance keys + `iris.shaderPack`); or VERSION, MODS, MEMORY, GRAPHICS,
WORLD or MEASUREMENT, none of which can move within one run (the mod-set hash is cached, the collector is set when the rings
are made, before fixAtStart; GRAPHICS null -> known is ignored; world kind and the measurement flags come from the same
source on both sides). A resource reload (a server resource pack at every join) isn't a change. So it refuses only sessions
with a real mid-session change: the player lowering render distance because of the stutter (common, and rightly refused),
F11 or maximising after joining in windowed mode (vanilla doesn't remember the window size, so at most once per launch, and
only if done after joining), a C16 F8 profile switch after joining, or a RigTune Apply or Try It during play. The next
session without a change qualifies. Not "nearly every session"; C20 isn't made useless.
