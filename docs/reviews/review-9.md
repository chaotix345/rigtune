### X3-1 — FrameRing phase-word regression breaks the hard-fail footprint budget

**Scenario.** A player turns on the Stutter Doctor session monitor (continuous, opt-in), then opens Tools → Benchmark and runs a benchmark while still in a loaded world. `StutterService.benchmarkSweep()` (`src/client/java/.../client/stutter/StutterService.java:224-233`) starts a second `FrameRing` capture for the benchmark and only **pauses** the running session capture (`pause(true)` at :233) — it never stops/frees it. For the run's duration a `SESSION_FRAMES`-sized ring (1<<17 frames) and a `BENCHMARK_FRAMES`-sized ring (1<<15 frames) are alive simultaneously alongside the shared `StutterRings`, and `StutterMonitor.retainedBytes()` (`StutterMonitor.java:238-242`) sums all three. This dual-capture design pre-dates this diff and was within budget before it (~2,326,816 bytes, comfortably under the 2,621,440-byte hard-fail ceiling). This diff's ST-2 fix adds a `phases` `int[]` sized to each ring's frame capacity (`FrameRing.java:76`, `retainedBytes()` at `:212-213` now adds `phases.length * 4L`), adding 524,288 bytes to the session ring and 131,072 bytes to the benchmark ring.

**Evidence.** `FrameRing.java:76` `this.phases = new int[frameCapacity];`; `:212-213` `... * 8L + phases.length * 4L`. `SESSION_FRAMES=1<<17=131072`, `BENCHMARK_FRAMES=1<<15=32768` (`FrameRing.java:17,19`). `StutterMonitor.java:238-242` sums session+benchmark+shared whenever both captures are non-null. `StutterService.java:224-233` (`benchmarkSweep`) starts a benchmark capture and only pauses (never stops) an active session capture — confirmed intentional by the method's own comment. `tools/footprint-budgets.json:25` `"monitorOnRetainedBytes": {"limit":2621440,"ceiling":2621440}`, top-level `"mode":"fail"` (`:3`), unchanged by `9cf84f66..b27f33fa`. Recomputed independently from source constants (`SESSION_FRAMES=131072`, `BENCHMARK_FRAMES=32768`, `STRIDE=10`, `BUCKETS=9`, shared=606,208): session=1,900,688 + benchmark=475,280 + shared=606,208 = **2,982,176 bytes**, i.e. 360,736 bytes (13.8%) over the 2,621,440-byte ceiling. `FrameRingAllocationTest.java:128-133` (`retainedBytesCountTheRings`) was updated in this same range to add the `phases` term for the session ring and raise the threshold to `2_621_440L`, but never adds a benchmark-ring term — the concurrent-capture path is untested. `FootprintGameTest.java`'s real `monitorOnRetainedBytes` measurement (~line 429-454) likewise only exercises a lone session capture, never a concurrent benchmark.

**Verifier reason (CONFIRMED, medium).** Independently re-derived the same byte totals from source constants and confirmed `phases[]`/the updated `retainedBytes()` formula are new in this diff (pre-diff total was 2,326,816, under budget — a genuine new regression from the ST-2 fix, not a pre-existing issue). Confirmed session+benchmark concurrency is a real, designed, reachable usage path (not a corner case), via `benchmarkSweep()`'s own pause-not-stop comment. No runtime `FootprintGuard`/enforcement exists in `src/main`/`src/client` — `FootprintBudgets` is wired only into `FootprintGameTest` (CI game-test) and `FrameHookBudgetTest` (JUnit) — so nothing crashes or corrupts data for a player at runtime; this is a silent breach of RigTune's own tested/documented ~2.5 MB ceiling (SPEC §10, `en_us.json` tooltip text) via an untested code path. Medium, not high: a real compat/spec-conformance defect in an untested production path, but the ~360 KB delta is imperceptible to a player and nothing crashes, corrupts, or leaks data.

**Fix.** Extend the footprint accounting/tests to include a live benchmark ring: add a `BENCHMARK_FRAMES`-sized `FrameRing` to `FrameRingAllocationTest.retainedBytesCountTheRings` (and ideally `FootprintGameTest`'s `monitorOnRetainedBytes` measurement) and assert the session+benchmark+shared total still fits the real budget; or, if ~2.98 MB is acceptable, raise `monitorOnRetainedBytes`'s limit/ceiling in `tools/footprint-budgets.json` to cover the concurrent case and update the "about 2.5 MB" strings in `en_us.json` to match. Alternatively, only track `phases` on the session ring (not the benchmark ring), since ST-2's own motivation — spikes surviving past ring eviction — matters less for the much smaller/shorter-lived benchmark capture.

### SE2-RESIDUAL — pre-existing untrusted-text gap outside SE-2's scope

**Scenario.** `BenchmarkResultScreen.java:389`'s `reason(String notMeasured)` returns `Component.literal(notMeasured.startsWith(failed) ? notMeasured.substring(failed.length()) : notMeasured)` with zero `SafeText`/`SafeLiteral` cleaning. `notMeasured` is built at `BenchmarkRun.java:46` as `SessionResult.NOT_MEASURED_FAILED + (e.getMessage() == null ? e.getClass().getSimpleName() : e.getMessage())` — a live exception message thrown while `guard.set(step.knobs())` tries to apply a Distant Horizons or Shaders (Iris) knob. Because that message originates in a third-party mod's own code (not RigTune's hardcoded strings), a message that happens to contain a section-sign formatting code or a bidi/control character (e.g. echoing back a player-chosen shader-pack folder name or a DH world-folder path) would render un-stripped on the benchmark result screen — the exact class of issue SE-2 was meant to close, just at a call site SE-2 didn't touch.

**Evidence.** `git log -p 9cf84f66..b27f33fa -- BenchmarkResultScreen.java` confirms the affected lines were never touched by this diff — this predates and is outside the scope of SE-2's fix. `BenchmarkResultScreen.java:389` and `BenchmarkRun.java:46` as quoted above.

**Verifier reason (PLAUSIBLE, low).** Confirmed via the diff that this is genuinely pre-existing and out of this round's scope, so it does not count against SE-2's FIXED status, but it does contradict the `ui-stutter-profiles` scope's own "checked" claim that its grep of `src/client/java` found no unsanitized untrusted-text path. Rated low because: (1) it requires a specific third-party mod's exception message to happen to contain such characters, which is uncommon; (2) the text source is a local, player-installed mod, not remote/network-attacker-controlled the way SE-2's rules-feed scenario was; (3) the practical effect is at most a garbled or stray-colored line on a single results screen, not data loss or a crash. Rated PLAUSIBLE rather than CONFIRMED because no actual reproducing DH/Iris exception message containing such characters was found.

**Fix.** Route `reason()`'s `Component.literal(...)` through `SafeLiteral.of(...)` (or `SafeText.clean(...)`) like every other untrusted-text call site SE-2 fixed. Low priority / can be folded into a future pass rather than this release.

## Refuted

| ID | Severity | Title | Why refuted |
|---|---|---|---|
| NEW-1 | Low | Theoretical data loss in `UnfinishedGroups`' dual-location migration | Hunted as a possible regression: `load()`/`recorded()` prefer `config/rigtune/unfinished-groups.json` over the legacy `helper/unfinished-groups.json` entirely (no merge) once the new file exists, and `save()` unconditionally deletes the legacy file once dirty — so if a legacy record from one run and a new-location record from a different run held genuinely different, unmerged content, the legacy content would be silently discarded on the next save without being considered by Undo/Discard/`ApplyExecutor`. Tracing reachability: the legacy path is only ever written by a **pre-review-8 0.4.0 dev build** (never a released version — 0.1.0-0.3.0 never touch this filename at all, confirmed against the pinned v0.3.0 `HelperLauncher`). Producing the divergent-content precondition requires manually installing an unreleased pre-fix dev jar, crashing it mid-rename, then swapping to the post-fix jar and hitting a second, unrelated half-done crash before ever completing a normal apply — a sequence unreachable through the public release channel (Modrinth) that RigTune's compatibility promise covers, and one the code's own comments already scope narrowly ("0.4.0 dev builds kept it there"). Not reachable by a real player using released RigTune versions. |
