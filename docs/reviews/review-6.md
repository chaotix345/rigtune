## Details

### security-1 (confirmed, medium): MODRINTH_TOKEN is job-level env in release.yml, so every step (including the untrusted-dependency-heavy Gradle build) can read it, not just the two steps that need it
- Location: .github/workflows/release.yml:14-17 (job-level `env: MODRINTH_TOKEN: ${{ secrets.MODRINTH_TOKEN }}`), read at 40-41 (`./gradlew build`), used only at 96-117 ("Publish to Modrinth") and 127-176 ("Verify Modrinth files match", the raw value used at line 157)
- Problem: The publish-capable Modrinth PAT is placed in the job's `env:` block (comment says this is done only so later `if:` conditions can test `env.MODRINTH_TOKEN != ''`, since `if:` can't reference `secrets.*` directly), which makes it part of the process environment for every step in the job, not just the two that actually use its value. That includes `gradle/actions/wrapper-validation`, the tag-format check, and critically the `./gradlew build` step, which runs the mod's full Gradle configuration/compile/test graph (Loom, Fabric API, Minotaur, JUnit, and all their transitive dependencies) with that token sitting in `System.getenv()`. build.gradle:175 also reads `System.getenv('MODRINTH_TOKEN')` at Gradle *configuration* time, so it's touched on every `./gradlew` invocation in the job regardless of which task actually runs.
- Scenario: A compromised or malicious transitive Gradle dependency, annotation processor, or JUnit test pulled into `./gradlew build` (release.yml:41) reads `System.getenv("MODRINTH_TOKEN")` and exfiltrates it over the network during the Build step, well before "Publish to Modrinth" (which is the only step that is supposed to need it) ever runs. With that token an attacker can publish arbitrary files as new versions of the already-moderator-approved `rigtune` Modrinth project — no fresh moderation review is required for a version bump — reaching every user whose mod manager auto-updates RigTune.
- Suggested fix: Don't expose the raw secret at job level. Compute a non-secret boolean at job level for the `if:` conditions, e.g. `env: MODRINTH_TOKEN_SET: ${{ secrets.MODRINTH_TOKEN != '' }}`, and switch the three `if:` checks to `env.MODRINTH_TOKEN_SET == 'true'`/`'false'`. Set the real `MODRINTH_TOKEN: ${{ secrets.MODRINTH_TOKEN }}` only as a step-level `env:` on "Publish to Modrinth" and "Verify Modrinth files match the GitHub release" (the two steps that read it), matching how `GITHUB_TOKEN` is already scoped per-step elsewhere in the same file and in build.yml's "Compile the E2E drivers" step.
- Verifier: release.yml:14-17 sets MODRINTH_TOKEN as job-level env (verified via git show f77af1a); this makes it part of the process environment for every step in the job, including 'Build' (./gradlew build) at line 40-41, well before the only two steps that need it: 'Publish to Modrinth' (96-117, gated by env.MODRINTH_TOKEN != '') and 'Verify Modrinth files match' (127-176, raw interpolation at line 157 `-H "Authorization: ${MODRINTH_TOKEN}"`). build.gradle:175 confirms `System.getenv('MODRINTH_TOKEN')` is read at Gradle *configuration* time, so it is touched by every ./gradlew invocation including `./gradlew build`, not just the modrinth publish task. No step-level env scoping, no separate job, and no other isolation mechanism limits the token's exposure during the Build step's full dependency/plugin/test graph. The scenario (a compromised transitive Gradle dependency/annotation-processor/test reading and exfiltrating the env var during `./gradlew build`, then using the stolen token to push a malicious version bump to the already-moderated 'rigtune' Modrinth project) is a real, unmitigated risk given the current workflow structure. Fix suggested (compute a non-secret boolean like MODRINTH_TOKEN_SET at job level for the if: conditions, and set the real secret only as step-level env on the two consuming steps) is valid and matches least-privilege CI secret handling.
- Decision: FIX. Pre-existing since v0.2's release.yml, still worth closing before the next publish: the job env now carries only MODRINTH_TOKEN_SET ('true'/'false') for the if: conditions; the token is set as step env on "Publish to Modrinth" and "Verify Modrinth files match" only, so `./gradlew build` never sees it (build.gradle reads it at configuration time, which now only happens in the publish step's Gradle runs). actionlint clean.
