## Details

### apply-safety-1 (confirmed, medium): DownloadPlanner.updateMod falls back to the OLD mod's id when the downloaded update can't be parsed, silently bypassing the round-1 "not a Fabric mod jar" check for the update path
- Location: src/main/java/io/github/chaotix345/rigtune/core/modrinth/DownloadPlanner.java:138 and :141 (updateMod); src/main/java/io/github/chaotix345/rigtune/core/apply/ApplyExecutor.java:334-339 (the readable-jar check added for review-3 apply-safety-1) and :285-303 (duplicateProblem)
- Problem: Review 3's apply-safety-1 fix made DownloadPlanner.addMod refuse (delete the download, fail the recommendation) whenever a just-downloaded jar's fabric.mod.json id can't be read, and made ApplyExecutor.runGroup independently re-derive and require a readable id for any ENABLE_FILE op staged with modId==null (ApplyExecutor.java:334-339: `modIds[i] = op.modId() != null ? op.modId() : jarModId(...)`, refusing the op/group when the result is null). But DownloadPlanner.updateMod (the sibling code path for 'Update X') was never touched by that fix and still does `String jarModId = Objects.requireNonNullElse(modIdOf.apply(pending), update.modId());` (line 138) - i.e. when the newly downloaded file's own id can't be parsed, it silently substitutes the CURRENTLY INSTALLED mod's id instead of failing. Because that substituted id is non-null, ApplyExecutor's readable-jar check at line 335 never even calls jarModId() to verify the actual downloaded file's content - `op.modId() != null` short-circuits straight past the new safety check. duplicateProblem() then also finds nothing wrong, because the only jar that legitimately has that mod id is the OLD jar being disabled in the very same group (added to the `disabled` exclusion set at ApplyExecutor.java:287-291), so `installed.withModId(modIds[i], disabled)` returns null (no conflict). The result: an update whose downloaded file is not a valid Fabric mod jar at all sails through every check and gets moved into mods/ as the active file, while the previously-installed, working jar is renamed to .disabled. Grepped every call site of `Op.enableFile(...).withModId(...)` in the codebase (3 total): DownloadPlanner.addMod (fixed), UndoPlanner.netOps (safe - its content is only reachable after UndoPlanner.move() already rejected an info()==null re-enable at the trial-map stage, before it can reach `sim`/`accepted`/netOps), and this one, DownloadPlanner.updateMod, which is the only one still open.
- Scenario: A rules-v2 update recommendation (or the Modrinth dependency resolver) points 'Update ModX 1.0 -> 2.0' at a Modrinth version whose primary file (ModrinthVersion.primaryFile() does no content validation, as review-3 already established) is corrupted, mislabeled, or a wrong-loader build that Modrinth's own hash metadata still matches - the same precondition round 1 accepted as realistic for the twin addMod bug. RigTune downloads it (hash verifies fine - hash only proves byte-match, not validity), ModJars.readModId can't parse fabric.mod.json and returns null, so DownloadPlanner.updateMod falls back to `update.modId()` = "modx" (the OLD, still-installed jar's id) instead of refusing. It stages {disable modx-1.0.jar, enable <bad file>.jar withModId("modx")}. At the next game exit, the helper's ApplyExecutor runs this group: the readable-jar check at ApplyExecutor.java:335 is skipped entirely (op.modId() is already non-null), duplicateProblem() sees no conflicting jar (the only prior holder of "modx" is in the group's own `disabled` set), so the group applies with Status.OK: the working modx-1.0.jar is renamed to .disabled and the unvalidated/corrupted file becomes the live modx-2.0.jar with zero content validation. Depending on how badly formed the file is, this either breaks Fabric's mod-discovery step on the next launch (the unstartable-game outcome this dimension exists to catch) or silently drops the mod's functionality - and unlike the addMod case, the user's previously-working mod is now gone, not merely 'never added'.
- Suggested fix: Give updateMod the same treatment addMod now gets: when `modIdOf.apply(pending)` returns null for the freshly downloaded update file, do not fall back to `update.modId()`. Instead delete the pending download (mirroring `attempt.batch.dropDuplicate(pending)`) and throw/record an error so the recommendation fails cleanly, exactly as the addMod path now does at DownloadPlanner.java:102-105 - the previously-installed jar is then left untouched rather than being disabled in favour of an unverified file.
- Verifier: DownloadPlanner.java:138 (f8303ad) still does `String jarModId = Objects.requireNonNullElse(modIdOf.apply(pending), update.modId());` — unlike addMod (same file, ~line 108: `if (jarModId == null) { attempt.batch.dropDuplicate(pending); throw new IOException(...'not a Fabric mod jar'...); }`), updateMod was never touched by review-3's apply-safety-1 fix and keeps the old fallback to the currently-installed mod's id. ApplyExecutor.runGroup (ApplyExecutor.java:334-337) only re-derives/verifies the jar's own id via jarModId(Path.of(op.from())) when `op.modId() == null`: `modIds[i] = op.modId() != null ? op.modId() : jarModId(Path.of(op.from()));`. Because updateMod's op.modId() is already non-null (the substituted old id), this branch never calls jarModId() to read the actual downloaded file, so the review-3 'is not a Fabric mod jar' check is completely bypassed for updates. duplicateProblem() (ApplyExecutor.java:281-300) then also finds no conflict: the group's DISABLE_FILE op for the old jar populates `disabled` (line 284-288) with that jar's filename, and installed.withModId(modIds[i], disabled) (InstalledJars.withModId, ApplyExecutor.java ~240-256) explicitly excludes filenames in `disabled`, so the only jar that legitimately holds that mod id (the one being disabled in the same group) is excluded and no duplicate is reported. containmentProblem/problem() (ApplyExecutor.java:426-458) only checks path containment and safe filename, never mod-id readability, confirming no other check exists. DownloadPlannerTest.java has a test asserting addMod rejects an unreadable jar (line 223: 'is not a Fabric mod jar') but no equivalent test exists for updateMod, confirming this path is untested and unfixed. Net effect verified: an update whose downloaded file's fabric.mod.json can't be parsed (corrupted/mislabeled/wrong-loader file that still hash-verifies against Modrinth's metadata) stages {disable <old, working jar>, enable <new, unvalidated file> withModId(<old mod's id>)}, sails through every ApplyExecutor safety check, and the group applies with Status.OK — the working jar is renamed to .disabled (ApplyExecutor.disable, line 507-516: recoverable via rename, not deleted) and the unvalidated file becomes the live jar. Severity kept at medium to match this project's own calibration of the analogous addMod issue in review-3 (docs/reviews/review-3.md lines 20-26), which rated the identical 'unvalidated jar bypasses safety checks, plausible but unproven Fabric-startup crash, requires an atypical external precondition (a bad Modrinth upload/version-metadata mismatch)' mechanism as medium; this updateMod variant is a strict regression of the same class (with the added, but recoverable-via-.disabled-rename, aggravating factor that a previously-working mod is also taken offline).
- Decision: FIX: updateMod refuses an unreadable downloaded jar like addMod; ApplyExecutor re-reads every ENABLE jar and fails the group if the id is unreadable or differs from the recorded modId.

### security-1 (confirmed, medium): Unbounded fabric.mod.json parse in ModJars.readModId lets one jar already in mods/ crash the apply helper (uncaught Error), permanently blocking Apply/Undo
- Location: src/main/java/io/github/chaotix345/rigtune/core/apply/ModJars.java:29-46 (readModId); ApplyExecutor.java:259-265 (idOf, used by InstalledJars.withModId), :307-313 (jarModId); ApplyHelper.java:106-119 (applyLocked)
- Problem: ModJars.readModId() (new in this round, added by commit 5f48d1e for the review-3 apply-safety-1 fix) opens the `fabric.mod.json` ZipEntry of a mod jar and calls `JsonParser.parseReader(reader)` with no byte cap of any kind — unlike every other untrusted-input parse path in this codebase (RulesLoader.MAX_RULES_BYTES = 2 MB, BoundedHttp's byte caps on every HTTP body). Both call sites that use it — ApplyExecutor.idOf() (ApplyExecutor.java:259-265) and ApplyExecutor.jarModId() (ApplyExecutor.java:307-313) — only `catch (IOException e)`, not `Error`, so a `StackOverflowError`/`OutOfMemoryError` from parsing an oversized or decompression-bomb'd `fabric.mod.json` entry propagates uncaught. ApplyHelper.applyLocked() (ApplyHelper.java:106-119), the only caller of ApplyExecutor.run(), likewise only catches `IOException | RuntimeException`, not `Error`, so the whole post-exit helper JVM crashes uncleanly instead of finishing the batch and treating that one jar the same way an unreadable jar is already treated (id = null → that op is skipped/reported, others proceed). This breaks the codebase's own stated per-op isolation guarantee ("RuntimeException from a single op's step is caught per-op so one bad op fails only its group" — round 1's OK list, which already flags Error as the one gap in that guarantee, but for the recursion path, not this new file-parsing path).
- Scenario: InstalledJars.withModId (ApplyExecutor.java:242-257), called by duplicateProblem() for every ENABLE_FILE op in a group, enumerates every *.jar currently in the user's mods/ folder and calls idOf() on each (via idsByName.computeIfAbsent) until a matching mod id is found or the list is exhausted — i.e. on the common case where no id collision exists, it reads fabric.mod.json from every jar already installed, not just the one RigTune is staging. A user's mods/ folder routinely holds 50+ jars from mixed sources (Modrinth App, CurseForge, modpacks, manual downloads) that RigTune never hash-verified. If any one of those jars' fabric.mod.json entry is a decompression bomb (a few KB of highly compressible JSON text that inflates to hundreds of MB, or is just pathologically large/deeply nested), the very next time the user applies any RigTune recommendation that adds or updates even one different mod — an everyday action — the helper JVM OOMs while scanning that unrelated jar, uncaught, and exits abnormally instead of logging "Apply failed" and returning 1. Because the offending jar is never removed by this failure, every subsequent Apply/Undo/self-update attempt that stages any enable op re-triggers the identical crash, silently and persistently disabling those features for that instance with no diagnostic in helper.log pointing at the real cause.
- Suggested fix: Cap the bytes read from the fabric.mod.json ZipEntry before/while parsing (e.g. check entry.getSize()/read through a bounded stream capped at a few hundred KB, mirroring RulesLoader.MAX_RULES_BYTES or BoundedHttp's caps) and treat an oversized or otherwise unreadable entry as "no id" (return null) the same way a missing entry or IOException already is. As defense in depth, catch Throwable (or at least OutOfMemoryError/StackOverflowError) around the per-jar lookups in idOf()/jarModId() and/or around ApplyExecutor.run() in ApplyHelper.applyLocked(), so one bad jar fails only its own check instead of crashing the whole helper process.
- Verifier: ModJars.readModId (src/main/java/io/github/chaotix345/rigtune/core/apply/ModJars.java:29-46) opens the fabric.mod.json ZipEntry and calls JsonParser.parseReader(reader) with no size cap whatsoever (no check of entry.getSize(), no bounded/limited InputStream) -- confirmed by direct read of the file at f8303ad. Its only catch is `catch (RuntimeException e)` (line 43), which does not catch Error subtypes like OutOfMemoryError or StackOverflowError. Both call sites -- ApplyExecutor.InstalledJars.idOf() (ApplyExecutor.java:259-265) and ApplyExecutor.jarModId() (ApplyExecutor.java:307-313) -- catch only `IOException`, so an Error thrown while parsing propagates through them uncaught. duplicateProblem() (ApplyExecutor.java:285-303) is invoked from runGroup() for every group containing an ENABLE_FILE op (confirmed at ApplyExecutor.java:349, where modIds[i] is populated for every op.type()==ENABLE_FILE, then duplicateProblem is called unconditionally at line 349-353), and it calls installed.withModId() (InstalledJars.withModId, ApplyExecutor.java:242-256) which does `Files.list(modsDir)` and calls idOf() on every *.jar file already in the mods folder -- not just the jar being staged -- confirmed at lines 247-254 (`for (Path jar : jars) ... idsByName.computeIfAbsent(name, n -> idOf(jar))`). This is genuinely the common path: any Apply that installs/enables even one mod scans fabric.mod.json of every other jar already in mods/. Finally, ApplyHelper.applyLocked() (ApplyHelper.java:106-119) wraps ApplyExecutor.run() in `catch (IOException | RuntimeException e)` only (confirmed by direct read) -- no Error catch -- so an uncaught OutOfMemoryError/StackOverflowError from parsing an oversized or decompression-bomb'd fabric.mod.json entry in any pre-existing jar propagates all the way out of applyLocked/run/main, crashing the helper JVM abnormally instead of the intended 'Apply failed' / exit-1 path, and since the offending jar is untouched by the failed run, the same crash recurs on every subsequent Apply/Undo that includes any enable op. All cited file:line locations match the actual f8303ad source exactly. The 'medium' severity is appropriate: it's a local-file-triggered DoS of the helper process (requires a jar with a pathological fabric.mod.json already present in mods/, whether via user error/corruption or an attacker who already has local write access to the mods folder), not remote code execution or data loss, and it only blocks the apply/undo helper rather than the main game process.
- Decision: FIX: cap the fabric.mod.json read (bounded stream); oversized/unparseable = no id; catch Throwable per jar in idOf/jarModId and around the run in ApplyHelper so one bad jar can never crash the helper.

### rules-accuracy-1 (confirmed, medium): DH self-updater mitigation only checks the auto-updater setting, not a build already staged in mods/update/
- Location: rules/source/knowledge.json:436 (distanthorizons ModRule skipUpdateWhen), rules/rules-v2.json (same), src/main/java/io/github/chaotix345/rigtune/core/recommend/Recommender.java:250-256 (updates()); root-cause text in docs/v0.2/verification/README.md finding 1 and its Suggestion line 109
- Problem: The Phase 5 investigation diagnosed the DH self-update collision and explicitly proposed suppressing RigTune's 'Update Distant Horizons' offer 'when dh.client.advanced.autoUpdater.enableAutoUpdater is true (or mods/update/ holds a DH build)' (README.md:109). Only the first half was implemented: skipUpdateWhen is a bare settingIs check on the enableAutoUpdater TOML key. Nothing in the rule, the Recommender, or anywhere else in the codebase (grep for 'mods/update' and 'updateFolder' returns nothing) inspects whether Distant Horizons already has a self-downloaded jar sitting in mods/update/.
- Scenario: A player who had DH's auto-updater on for a session (so DH already downloaded a new build into mods/update/) later turns enableAutoUpdater off - or a DH release whose config predates/omits the key, leaving it UNKNOWN - still gets RigTune's own 'Update Distant Horizons' recommendation, because settingIs now reads false/UNKNOWN and skipUpdateWhen no longer fires. Applying that update re-creates the exact jar-lock race (RigTune's helper vs DH's own DeleteOnUnlock JVM) that caused the original 0.1.0 failure this fix was written to prevent.
- Suggested fix: Either broaden the mitigation to also cover a queued DH self-update (requires a new HardwareProfile-style detection signal for mods/update/ contents, since a pure JSON condition can't inspect the filesystem), or, if that signal doesn't exist yet, note this as an explicit accepted gap in the schema/verification docs rather than presenting the fix as covering the full diagnosed root cause.
- Verifier: rules/source/knowledge.json:436 — distanthorizons ModRule's skipUpdateWhen is only `{"settingIs": {"dh.client.advanced.autoUpdater.enableAutoUpdater": true}}`. Recommender.java:250-256 evaluates skipUpdateWhen purely via ConditionEvaluator (a settingIs check on parsed TOML), with no filesystem input. `grep -rn "mods/update\|updateFolder" src/` across the whole repo (excluding the unrelated e2e string "update" phase name in SelfUpdateDriver.java) returns nothing — no code anywhere inspects mods/update/ for a queued DH self-update. The Phase 5 doc itself (docs/v0.2/verification/README.md:109) proposed the mitigation as 'when enableAutoUpdater is true (or mods/update/ holds a DH build)', and the Fixes table (README.md:127) confirms only the settingIs half was implemented ('An absent key is UNKNOWN, so the update is still offered'), which is exactly the gap the finding describes. Test RecommenderV2Test.skipUpdateWhenFalseOrUnknownOffersTheUpdate (line 254) confirms false/UNKNOWN → update offered, matching the described scenario (auto-updater toggled off after a build was already staged, or a config predating the key). Confirmed as a real, narrower residual gap versus the diagnosed root cause; medium is a fair severity since it requires a specific antecedent state (a DH build already sitting in mods/update/) rather than being the default/common case.
- Decision: FIX: generic: detect a queued self-update in mods/update/ (any jar there, by its fabric.mod.json id) and never offer RigTune's own update for that mod (advice instead), independent of rules.

### rules-accuracy-2 (confirmed, medium): RigTune can recommend installing two Modrinth-declared-incompatible mods in the same report, since conflictsWith is only checked against already-installed mods
- Location: rules/source/knowledge.json:234-245 (krypton.conflictsWith) and :259-283 (zfastnoise/zmaterial-rule-compiler.conflictsWith); src/main/java/io/github/chaotix345/rigtune/core/recommend/Recommender.java:211-219 (additions(), `rule.conflictsWith.stream().anyMatch(this::refInstalled)`); src/main/java/io/github/chaotix345/rigtune/core/modrinth/DependencyResolver.java:60 (only `dep.required()` is ever consulted)
- Problem: Krypton and Fast Noise/Material Rule Compiler declare a genuine, Modrinth-sourced mutual incompatibility (confirmed real by round-1's rules-accuracy-2 verifier, commit f8da620). But `additions()` only excludes a mod from being recommended when a conflicting mod is *installed* (RULES_SCHEMA.md's own documented criterion); it never checks whether another mod that conflictsWith it is *also* being offered/ticked in the same report. Separately, Modrinth's own `dependency_type: incompatible` metadata is parsed into `Dependency.dependencyType` but the only consumer (`DependencyResolver.java:60`) checks `required()` and ignores it entirely, so nothing in the download/apply pipeline blocks it either. The zfastnoise/zmaterial-rule-compiler reason text also only mentions the C2ME crash risk, never Krypton, so the UI gives no hint the two are mutually exclusive.
- Scenario: Fresh 0.2 setup with only Sodium/Lithium installed: the report offers 'Install Krypton' and 'Install Fast Noise' (both unticked by default, both plausible 'turn on all the free FPS mods' picks). The user ticks both and hits Apply - both jars are downloaded and dropped into mods/, a pair Modrinth itself lists as incompatible, with no warning anywhere in RigTune before or during the apply.
- Suggested fix: Either have `additions()` treat two mutually-conflictsWith mods as mutually exclusive within one recommendation set (drop/hide one, or block ticking both, mirroring the existing 'installed conflict' warning), or have the apply/staging step validate the batch of `Action.AddMod`s against `conflictsWith` before executing, refusing (or warning on) a batch that contains both sides of a declared conflict.
- Verifier: rules/source/knowledge.json:243 (krypton.conflictsWith: ["zfastnoise","zmaterial-rule-compiler"], defaultSelected:false) and :268/:281 (zfastnoise/zmaterial-rule-compiler.conflictsWith includes "krypton", also defaultSelected:false) confirm all three are recommendWhen:always with defaultSelected:false, matching the 'both unticked by default' scenario. Recommender.java:211-219 additions(): the only conflict guard is `rule.conflictsWith.stream().anyMatch(this::refInstalled)` — filters solely on mods already installed, never on other rules concurrently being offered/selected in the same report. Recommender.java:189-208 conflicts() only emits a WARNING for two conflicting mods that are both already installed, not for two being newly added together. DownloadPlanner.java (plan/addMod, lines ~56-118) validates duplicate project ids and duplicate/already-loaded mod ids but never consults conflictsWith or Modrinth's incompatible dependency_type before staging both AddMod ops. DependencyResolver.java:60 (`if (dep.required() && ...)`) only ever branches on required(), never reads an incompatible-typed dependency. So a fresh setup can have both 'Install Krypton' and 'Install Fast Noise' offered simultaneously with no warning, and ticking both stages both jars with no batch-level block. Confirmed; medium severity is reasonable (both are opt-in/unticked by default, so it requires an active user choice to trigger, but nothing in the UI signals the exclusivity when the reason text for zfastnoise/zmatcomp only mentions the C2ME crash risk, not Krypton).
- Decision: FIX: additions never offers two mutually conflicting mods together (the later rule is dropped with a note on the kept one); staging refuses a batch containing both sides of a conflictsWith pair; DependencyResolver honours Modrinth "incompatible" dependencies against installed/selected projects.
