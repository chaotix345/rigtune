## Checked, fine

- **X4.1/X4.2 on the render thread in the windows.** `RealController`'s constructor makes no v0.5 service or notice source: the holder is a volatile field, and the 8 new sources sit behind `NoticeCenter`'s lazy supplier. The verifier needs no v0.5 class there either: sources are stored as `NoticeSource` (interface) and passed through a varargs array. `onInitializeClient` adds only `V05Services.registerEvents`: 3 lambdas and one phase ordering. The CLIENT_STARTED handler adds one `Probes.EXECUTOR` submission (`V05Services.afterStart`) and one more future in `LauncherProbe.probeAsync`; the `.index/` listing and `InstanceEvidence` load run on the worker. `HttpModrinthClient`'s constructor does new work only when `-Drigtune.modrinth.baseUrl` is set.
- **FootprintStats' window and flag.** Only the thread that opened the window can set it, and the launch's own preLaunch/init are the only preLaunch/init windows. A game test's second `onPreLaunch()` opens none. `FootprintStatsTest` proves worker resolution leaves the flag unset and render-thread resolution sets it (AC-X.2). FootprintGameTest fails the leg on the flag in any budget mode. The holder is made on the worker (`v05HolderCreatedOn`).
- **preLaunch RW-3 work.** It runs only when pending.json exists and uses `Files.exists` plus FabricLoader origins. It lists the mods folder and reads unfinished-groups.json only when something looks stale. `StaleGroups` loads no Minecraft class in preLaunch.
- **RW-16 timer.** `CrashReportMixin`/`PreloadTimer` make two `nanoTime` reads into static fields during vanilla's `CrashReport.preload`, outside RigTune's windows; nothing is allocated.
- **Timed tick path** (`RigTuneClient.onTick` + `StutterHooks.tick`). `onTick` changes only in its title-screen branch (toast wording, `SettingsSaver` privacy save). `StutterHooks.tick` gains `StutterMonitor.idle()` (a static boolean read) and `DevFixCalibration.tick`. The latter is dev-only behind a `static final boolean`, so it costs about 0 ns after JIT; strictly it is new code on the path X4.4 reserves, and it could move to its own listener registered only under `-Drigtune.dev.stutterScript=fixcalibrate`. `StutterService.tick` calls `startSession` only when a session starts. The `v05()` holder and its synchronized getters are never reached per tick.
- **Frame path.** DebugScreenOverlayMixin, MinecraftFrameMixin, FrameTimes and `StutterMonitor.onFrame` are unchanged. There is no new HUD element and no new frame mixin. FrameHookBudgetTest's ratio gates and self-check are as ws-ci calibrated them.
- **New END_CLIENT_TICK listeners.** None is on the timed path. Each is registered once (guarded) on first need, never at init. Idle costs and measurement:
  - `SettingsWatch` (first session start): with no session, one volatile read and three field writes. With a session, two cached ints, the overlay reference, and the throttle check every 10 ticks, with no allocation (`Throttle`, `OptionInstance.get` unboxing). Measured 0 B in StutterGameTest.
  - `TryItService.tick` (first queued run): one volatile read. Measured 0 B in TryItGameTest.
  - `ServerProfileService.tick` (first offer): one volatile read.
  - Leftover listener (title screen, only with leftover file ops): one volatile read. While PENDING it adds two `LauncherProbe` static-synchronized reads, deliberately bypassing `V05Services`' lock; 0 B in a unit test.
- **Workers.** All v0.5 async work runs on RigTune-named threads (Probes.EXECUTOR, "RigTune preview", ...), so it counts in `workerCpuMs5s`; nothing uses the common pool. The TryIt and StutterService io chains don't accumulate futures.
- **Retention.**
  - `StutterRings`: the new live ring is 256 x 3 longs, added through the non-varargs `add(long,long,long)`. `SAMPLE_STRIDE` 13 to 14 adds 32 KB to the sample ring, inside `monitorOnRetainedBytes`.
  - `Capture`'s new fields are small maps and records.
  - `StutterService.end` copies `fixAtStart` rather than keeping the capture.
  - `StutterFixService.specsFor` holds the rules document weakly.
  - `BenchmarkConditions.modSetHash` is cached.
  - `OutsideChanges.APPLIED`, `LauncherRepairService.State` and `StaleGroups.FOUND` are small; FOUND entries are removed as their status is shown.
- **Screens.** No v0.5 screen reads files or calls the controller in `extractRenderState`.
  - Per-tick work: StutterScreen/TryItScreen call `view()`, TryIt stats history.json at most once a second, and ToolsScreen compares `perfCounters` identity. `StutterScreen.same` compares by value, so there is no rebuild loop.
  - First Apply's history read runs on Probes.EXECUTOR. ServerProfilesScreen reads its own two small files at init, which X8 allows.
- **Notice sources.** FirstRun, ModFilesNews, StartupRegression, OutsideChanges and ServerProfile read memory only while nothing is pending. HeldModChanges and LauncherRepair stat pending.json, the mods folder and history.json under LAUNCHER/PENDING; that is the coordinator's X8 ruling (LauncherRepairService.java:43-48), accepted.
- **Budgets file and 1d.** Only the six per-call ns limits moved (4x, capped at ceilings). `renderThreadInit*`, `clientStartedWallMs`, `workerCpuMs5s`, bytes, leak and retained keys and `rigtuneClassBytesIdle` (109296) are unchanged. `tickHookOnVsReference` is 2.05 with the twin self-check on every run.
