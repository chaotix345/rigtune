## Checked, fine
- Apply guard: `LauncherModAdvice.guard` removes AddMod/UpdateMod/DisableMod, every file-op variant of the sealed `Action`; it runs first in `RealController.apply` (before DisableGuard, staging and downloads) and fails closed to SetSetting only (`V05Hooks.guarded`). Every staging path with a mod-file op goes through it: C09 (`Triable` refuses non-SetSetting), C20 (builds one SetSetting), profiles, OutsideChanges and FirstApply are settings-only; `.stage(` elsewhere is UndoService's config patches only.
- Policy stability: `ModFilesPolicy.of` is RIGTUNE only once detection AND the listing have answered, both futures are session-wide, and `LauncherProbe.record` never lets a stale NOT_YET replace an answer, so the only RIGTUNE -> LAUNCHER change is turning the opt-in off. Downloads started while opted in and staged after it's switched off are held at exit (offered, not applied).
- Exit: the policy is read live at CLIENT_STOPPING (PENDING/unknown -> hold); `HelperLauncher.helperClasspath` always runs a byte-identical copy of the current jar (re-copied on mismatch, fresh name when the old copy is locked), so a 0.5 helper reads the property.
- Hold semantics: whole groups by group key (a patch sharing a group with a file op is held too); held results stay null and out of last-apply.json; attempts untouched (writeRemaining only touches ops in the result); a held-only exit writes nothing; `prune` keeps held groups' records (plan ids include them); the same `heldIndexes` rule feeds the helper, the notice, the toasts and Cancel.
- RW-1: `doneByLastRun` needs the same UUID op id, same type, OK or SKIPPED-with-resultPath and the rename still in effect; a bare SKIPPED or an unreadable last-apply.json proves nothing; `installedElsewhere` runs before any rename and nothing in mods/ is touched on that path (only `.rigtune-pending` downloads retired).
- Undo: the launcher skip applies per group after the RigTune-jar rule and before any move; `UndoService.undo` re-plans under the lock with a fresh GameState, so the live policy decides; STAGED cancels touch only pending.json and `.rigtune-pending` files; RW-14 no longer guesses `<file>.disabled` (0.2.0+ journals record resultFile, checked in v0.2.0's HistoryUpdates).
- LauncherRepair: read-only; a pair needs the same mod id's new jar present, so the "delete the old disabled copy" step never names a mod's only copy; Copy list is names only, escaped.
- RangeReader / preview checks: memory only, origin and Modrinth gate checked before every request, exact Content-Range, caps and budgets; nothing is downloaded before Apply, and under LAUNCHER no download row reaches the preview.
- `UnfinishedGroups.writeDurably`: temp file forced, atomic move with retries, folder forced where possible; a failed write loses the record, not a rename (the documented safe side).
- SkippedClaims write order (journal first, then last-apply.json; an interrupted relabel is completed), under the apply lock only.
- `ApplyLock` is reentrant per thread and serialises Cancel them, dropStale, dropQueuedUpdates and staging within the JVM and against the helper.
- 2V rollback message: the resultPath semantics (only when the file is stuck) are unchanged.
- StaleOps doesn't drop a fresh update or undo right after Apply's rebuild: a jar any staged disable turns off never counts as "installed elsewhere".
