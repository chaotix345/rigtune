# WS-B: Undo RigTune and the 0.1.0 migration (design notes)

SPEC item 3 with the plan-review fixes H4, H5, M4–M9, L2, L3, L8, L9. The coordinator folds this into DESIGN.md.

## Journal (`config/rigtune/history.json`)
- `core/history/Journal`: `{"formatVersion": 1, "entries": [...]}`, the last 50 entries. Every read-modify-write holds the apply lock and replaces the file with `AtomicFiles`; an update that changes nothing doesn't rewrite it. A corrupt file is kept as `history.json.bad` and the journal starts fresh; a newer `formatVersion` is never overwritten (records are dropped with a warning, and undo is unavailable). Null entries or changes are dropped instead of failing the file (L8).
- Pruning past 50 drops the oldest entries with nothing left to update or undo first, then the oldest with nothing staged, then the oldest.
- `Journal` implements `ChangeRecorder` and is installed at client init. `record(entryId, kind, changes)` adds to the entry with that id or creates it, so one Apply is one entry: RealController makes the id in `apply()` and hands it to the downloads (H4).

## Recording
- Vanilla (`client/undo/VanillaChanges`): the whole options snapshot is read right before and after `SettingsBridge.applyVanilla`, and every option that changed is recorded APPLIED (M7: graphicsPreset rewrites a dozen options). A write that failed changed nothing and isn't recorded.
- Staged ops (`client/undo/Staging`, which now owns `stage()`): lock → relocate → merge → save → retire → record. Changes are recorded after the merge with the id and group each op has in pending.json (`PendingActions.Merged.survivingIds`). An op that repeats a staged change keeps the staged id and isn't recorded twice. A config key's `before` is the value after the ops already staged for it, else the file's value through the namespace's `ConfigTargets` reader (every namespace, so WS-D records nothing itself). Ops replaced by a newer enable, or dropped because they belong to another instance's folders, become DISCARDED (H5).
- A disable's `modId` is read from the jar being disabled (DISABLE ops carry none).
- Discard pending marks every dropped op's change DISCARDED (`PendingActions.discard` returns the dropped ops).
- The helper (`ApplyExecutor.run`) updates the journal last, after pending.json and last-apply.json are written, best-effort (`catch Throwable`, logged to helper.log): OK / already done → APPLIED (with the group it ran in, and a disable's actual file name from the new additive `OpResult.resultPath`, M6), ABANDONED → ABANDONED, FAILED unchanged. An undo change that becomes APPLIED marks the change it reverts REVERTED. Only the JDK, Gson and core classes are reachable from there (M5); a child-JVM test runs the helper with just our main-classes jar and Gson over every op type, and a mutation that touches `RigTune.LOGGER` there fails it.
- Startup (`client/undo/HistoryStartup`, from preLaunch while it holds the lock): the last helper result is applied again (in case the helper's update failed), then any STAGED change whose op is no longer in pending.json becomes ABANDONED (H5). A FAILED op that is no longer in pending.json counts as lost too (the SPEC wording keeps it STAGED; it could never run).

## ApplyLock is reentrant (M4)
Per path, a JVM-wide `ReentrantLock` plus one shared `FileLock`: the same thread re-enters at once (Staging → Journal, preLaunch → HistoryStartup, UndoService → Staging/Journal, helper → journal), and the OS lock is released only when the outermost holder closes, so no nested channel is ever opened or closed (the POSIX release-on-close hazard doesn't arise). Other threads and processes wait as before. Tests that fake a busy helper now hold the lock on another thread (`HeldLock`, and `RigTuneClientGameTest.checkNotices`).

## Undo
`core/history/UndoPlanner` is pure; `client/undo/UndoService` carries a plan out; `client/ui/UndoScreen` shows it.
- Candidates: STAGED changes, and APPLIED ones no undo change (STAGED or APPLIED) is reverting yet. Undo entries themselves are never undone (no redo).
- Undo last = the newest non-undo entry, not undone already (an undo entry has `undoOf` = its id, or an `all` undo came after it), whose plan has at least one non-skip item. Entries with nothing left to undo are passed over (M8's "undo attempted" without a new field). Undo everything = every non-undo entry.
- STAGED → the op's whole pending.json group is dropped (other applies' changes in that group are listed and become DISCARDED; ops in it without a journal change are listed too). A group with a RigTune op is never dropped by an undo (L3: "RigTune's own update stays staged; use Discard pending"). A change whose op is gone is skipped.
- Settings: chained newest to oldest while `older.after == newer.before`; skipped when the current value isn't the latest `after` ("you changed it since"), when the chain stops at a user edit, when the earliest `before` is absent (L2: PATCH_JSON can't delete a key), or for a vanilla key outside `SettingKeys` (graphicsPreset side effects such as `ao` or `mipmapLevels`; restoring the preset restores them only if the old preset was a named one). Vanilla values are set at once through `SettingsBridge.applyVanilla` (preset first); config values go through the namespace's stager (validated against the file) as staged ops.
- Mod files: per original group, newest first, all-or-nothing, against a simulated mods folder that names disables like `ApplyExecutor.disabledTarget` and uses each disable's recorded `resultFile` (M6). A reversal disable needs the file; a reversal enable needs the `.disabled` file and a free name. RigTune's jar (by journal mod id or by reading the jar, M9) is never undone. After each group the simulated folder is checked (M9): no mod id on two active jars, and no active jar missing a mod id it `depends` on (minecraft, java, fabricloader, mods from outside the folder, and every active jar's id, `provides` and nested ids count). Only problems the group adds block it; existing ones don't.
- Net ops: after all groups, one op per file whose place changed (disable or enable with the jar's mod id), one new group per connected set of original groups that touched the same files. So an update chain a → b → c undone to a is {disable c, enable a} as one group, and a chain that kept one file name (`mod.jar`, `.disabled`, `.disabled.1`) works too; per-group reversal ops would have been merged into a broken group by `PendingActions.merge`'s dedupe. A change whose file ends where it started (b in the chain) follows its group's first op.
- `undo(plan)` re-plans exactly the changes the screen showed, under the lock (M8): an item whose state changed becomes a skip, a staged group that gained ops is skipped, and nothing that wasn't shown is added. `UndoPlan` gained `undoOf` and each `Item` its `changeIds`/`opIds` (compatible constructors kept).
- The undo is journaled as one `kind: undo` entry (`undoOf` = entry id or `all`), each change with `reverts`: vanilla APPLIED at once (originals REVERTED), staged ones STAGED with the surviving op id until the helper applies them. The entry is written even if everything was skipped, which marks the entry as undone.
- Undo is refused while downloads run (they would add changes to the entry later).
- Dependencies are checked by mod id presence only (the amendment's rule), not version predicates: undoing an update below a version another mod requires isn't caught.

## 0.1.0 migration
- 0.1.0's files are read unchanged: pending.json with and without id/group/modId/attempts, last-apply.json, rigtune.json (goal, lastShownApply), rules-cache.json, and the `helper/` copies (replaced by 0.2's). Fixtures in `src/test/resources/v010/` are hand-written from the v0.1.0 record shapes, with templated paths (`${MODS}/name`, `${CONFIG}/name`); `MigrationV010Test` also reads `v010/captured/` when WS-G adds files there (same templating).
- Legacy import (`core/history/LegacyImport`), on the first 0.2 run with no history.json, only while preLaunch holds the lock (L2: a still-running helper's last-apply.json may be stale): one `legacy-import` entry with 0.1.x's last run's OK / already-done file ops as APPLIED changes (a disable's name from `resultPath`, else 0.1.0's "Disabled x -> y" message, else `x.disabled`), and leftover staged ops with ids as STAGED changes. RigTune's own jars are left out (ENABLE with mod id rigtune, the DISABLE in its group, or a disabled jar that reads as rigtune), and so are config patches that already ran. history.json is created even when there's nothing to import, so the import runs once. It runs before the game's classes load, so it reads sodium-options.json with core classes only (0.1.x patched nothing else).
