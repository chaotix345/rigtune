# WS-B: Undo RigTune and the 0.1.0 migration (design notes)

SPEC item 3 with the plan-review fixes H4, H5, M4–M9, L2, L3, L8, L9, and the fixes from the WS-B code reviews. The coordinator folds this into DESIGN.md.

## Journal (`config/rigtune/history.json`)
- `core/history/Journal`: `{"formatVersion": 1, "entries": [...]}`, the last 50 entries. Every read-modify-write holds the apply lock and replaces the file with `AtomicFiles`; an update that changes nothing doesn't rewrite it.
- A corrupt file (bad JSON, or bytes that aren't UTF-8) is kept as `history.json.bad`, `.bad.1`, … (never overwritten) and the journal starts fresh. A newer `formatVersion` is never overwritten: records are dropped with a warning and undo is unavailable. Null entries or changes, and entries without an id, are dropped instead of failing the file (L8).
- Pruning past 50 drops the oldest entries with nothing left to update or undo first, then the oldest with nothing staged, then the oldest.
- `Journal` implements `ChangeRecorder` and is installed at client init. `record(entryId, kind, changes)` adds to the entry with that id or creates it, so one Apply is one entry: RealController makes the id in `apply()` and hands it to the downloads (H4). WS-C records the benchmark "Keep" through `ChangeRecorder` (kind `benchmark`); WS-E adds the Undo buttons that open `UndoScreen`.
- The game's journal (`ClientJournal`) makes its first entry itself when it creates the file: the 0.1.x legacy import (below), under the lock. So the import can't be lost to whichever record happens to create the file first.

## Recording
- Vanilla (`client/undo/VanillaChanges`): the whole options snapshot is read right before and after `SettingsBridge.applyVanilla`, and every option that changed is recorded APPLIED (M7: graphicsPreset rewrites a dozen options). A write that failed changed nothing and isn't recorded.
- Staged ops (`client/undo/Staging`, which now owns `stage()`): lock → relocate → merge → save → retire → record. Changes are recorded after the merge with the id and group each op has in pending.json (`PendingActions.Merged.survivingIds`). An op that repeats a staged change keeps the staged id and isn't recorded twice. A config key's `before` is the value after the ops already staged for it, else the file's value through the namespace's `ConfigTargets` reader (every namespace, so WS-D records nothing itself). Ops replaced by a newer enable, or dropped because they belong to another instance's folders, become DISCARDED (H5). Only `.rigtune-pending` downloads are ever retired: a replaced enable of a user's `x.jar.disabled` (an undo's re-enable) leaves that jar alone.
- A disable's `modId` is read from the jar being disabled (DISABLE ops carry none).
- Discard pending marks every dropped op's change DISCARDED (`PendingActions.discard` returns the dropped ops).
- The helper (`ApplyExecutor.run`) updates the journal last, after pending.json and last-apply.json are written, best-effort (`catch Throwable`, logged to helper.log): OK / already done → APPLIED (with the group it ran in, and, for a disable of that change's own file, the actual file name from the new additive `OpResult.resultPath`, M6), ABANDONED → ABANDONED, FAILED unchanged. An undo change that becomes APPLIED marks the change it reverts REVERTED. Only the JDK, Gson and core classes are reachable from there (M5); a child-JVM test runs the helper with just our main-classes jar and Gson over every op type, and a mutation that touches `RigTune.LOGGER` there fails it.
- Startup (`client/undo/HistoryStartup`, from preLaunch while it holds the lock): the first run creates history.json (with the legacy import); later runs apply the last helper result again (in case the helper's update failed), then any STAGED change whose op is no longer in pending.json becomes ABANDONED (H5). A FAILED op that is no longer in pending.json counts as lost too (the SPEC wording keeps it STAGED; it could never run). Nothing here can stop the game from starting: every failure is caught and logged, and preLaunch wraps the journal in `catch (Throwable)`.

## ApplyLock is reentrant (M4)
Per folder real path, a JVM-wide `ReentrantLock` plus one shared `FileLock`: the same thread re-enters at once, even when interrupted (Staging → Journal, preLaunch → HistoryStartup, UndoService → Staging/Journal, helper → journal), and the OS lock is released only when the outermost holder closes, so no nested channel is ever opened or closed (the POSIX release-on-close hazard doesn't arise). A symlinked or differently spelled folder is the same lock. A close on the wrong thread throws before it changes anything, so the owner can still release it. Other threads and processes wait as before. Tests that fake a busy helper now hold the lock on another thread (`HeldLock`, and `RigTuneClientGameTest.checkNotices`).

## Undo
`core/history/UndoPlanner` is pure; `client/undo/UndoService` carries a plan out; `client/ui/UndoScreen` shows it.
- Candidates: STAGED changes, and APPLIED ones no undo change (STAGED or APPLIED) is reverting yet. Undo entries themselves are never undone (no redo).
- Undo last = the newest non-undo entry that hasn't been undone and whose plan has at least one non-skip item. An entry counts as undone when an undo entry names it (`undoOf`), or an `all` undo came after it, and that undo has at least one change that isn't DISCARDED or ABANDONED; so an undo cancelled by Discard pending, or abandoned by the helper, doesn't hide its apply. **Deviation:** instead of a persisted "undo attempted" state (M8), entries whose plan would be all skips are passed over, so Undo last never gets stuck on one. Undo everything = every non-undo entry.
- STAGED → the op's whole pending.json group is dropped (other applies' changes in that group are listed and become DISCARDED; ops in it without a journal change are listed too, including ops of an unknown type). A group with a RigTune op is never dropped by an undo (L3: "RigTune's own update stays staged; use Discard pending"). A change whose op is gone is skipped.
- Settings: chained newest to oldest while `older.after == newer.before`, and after the first mismatch (the user changed it between two applies) every older change is skipped. Also skipped: when the current value isn't the latest `after` ("you changed it since"), when the earliest `before` is absent (L2: PATCH_JSON can't delete a key), and a vanilla key outside `SettingKeys`. Vanilla values are set at once through `SettingsBridge.applyVanilla` (preset first); config values go through the namespace's stager (validated against the file) as staged ops.
- graphicsPreset (M7): restoring the preset rewrites its options, so when the undo restores it, every skipped vanilla option RigTune may write is written back with its current value after the preset, keeping the screen's "skipped" true. **Deviation:** preset side-effect options outside the allowlist (`ao`, `mipmapLevels`, `menuBackgroundBlurriness`, `cloudRange`, `maxAnisotropyBit`) are recorded but skipped ("restoring the graphics preset may change it"), and they stay APPLIED, so they show as skips in every later Undo everything.
- Mod files: per original group, newest first, all-or-nothing, against a simulated mods folder that names disables like `ApplyExecutor.disabledTarget` and uses each disable's recorded `resultFile` (M6). A reversal disable needs the file; a reversal enable needs the `.disabled` file and a free name, and is skipped while another change of the same mod is staged and not cancelled by this undo (merging would silently replace it). RigTune's jar (by journal mod id or by reading the jar, M9) is never undone. After each group the simulated folder is checked (M9): no mod id on two active jars, and no active jar missing a mod id it `depends` on (minecraft, java, fabricloader, mods from outside the folder, and every active jar's id, `provides` and nested ids count). Only problems the group adds block it. Dependencies are checked by mod id presence only (the amendment's rule), not version predicates.
- Net ops: after all groups, one op per file whose place changed (disable, or enable with the jar's mod id). **Deviation:** reversal groups are joined by shared content, one new group per connected set of original groups that moved the same file (union-find), rather than one reversal group per original group: staged separately, two reversals of an update chain that kept its file name (disable `mod.jar` twice) would be merged into one broken group by `PendingActions.merge`'s dedupe. So a → b → c undone to a is {disable c, enable a}, and a same-name chain (`mod.jar`, `.disabled`, `.disabled.1`) works. A change whose file ends where it started (b in the chain) follows its group's first op. Groups that don't share a file stay separate, so cross-group dependencies rely on the executor's order (disables first within a group) and the M9 check on the simulated result.
- `undo(plan)` re-plans exactly the changes the screen showed, under the lock (M8): an item whose state changed becomes a skip, a staged group that gained ops is skipped, and nothing that wasn't shown is added. `UndoPlan` gained `undoOf`, `at` (the undone apply's time, shown in the subtitle), `problem` (why there's no plan: downloads running, a newer history.json, a planning error) and each `Item` its `changeIds`/`opIds` (compatible constructors kept).
- Execution order: staged groups are dropped (journaled at once), then config and file reversals are staged; only then are vanilla settings written, so a staging failure changes no setting, and a failing vanilla write or journal update doesn't lose the record of what was staged. The undo is one `kind: undo` entry (`undoOf` = entry id or `all`), each change with `reverts`: vanilla APPLIED at once (originals REVERTED), staged ones STAGED with the surviving op id until the helper applies them.
- Undo is refused while downloads run (they would add changes to the entry later).
- The plan is worked out off the render thread (the probe executor; the options snapshot is still taken on the render thread). Jar metadata is read only for active jars and the ones an undo moves, capped (a nested jar over 32 MiB, or past the 512th, is skipped) and cached by size and modification time, so the re-check on confirm (render thread) doesn't read them again.
- The planner's descriptions and skip reasons are English strings from core (like rule titles); vanilla options use their captions and On/Off.

## 0.1.0 migration
- 0.1.0's files are read unchanged: pending.json with and without id/group/modId/attempts, last-apply.json, rigtune.json (goal, lastShownApply), rules-cache.json, and the `helper/` copies (replaced by 0.2's). Fixtures in `src/test/resources/v010/` are hand-written from the v0.1.0 record shapes (templated `${MODS}/…`, `${CONFIG}/…`); `MigrationV010Test` also reads WS-G's files captured from the released jar in `v010/captured/` (templated `${INSTANCE}/…`): the plan's ops and ids, the results and 0.1.0's disable message, the goal and absent lastShownApply, the rules cache, preLaunch's report, the 0.2 helper running the plan, and the legacy import.
- Legacy import (`core/history/LegacyImport`): one `legacy-import` entry with 0.1.x's last run's OK / already-done file ops as APPLIED changes (a disable's name from `resultPath`, else 0.1.0's "Disabled x -> y" message, else `x.disabled`), and leftover staged ops with ids as STAGED changes. RigTune's own jars are left out (ENABLE with mod id rigtune, the DISABLE in its group, or a disabled jar that reads as rigtune), and so are config patches that already ran. It's made when history.json is first created, under the lock: preLaunch creates it when it has the lock; if it doesn't (L2: a still-running 0.1.x helper's last-apply.json may be stale), the first record later in the session does. It reads sodium-options.json with core classes only (0.1.x patched nothing else; preLaunch runs before the game's classes load).
