# RigTune v0.4.0: specification

Status: DRAFT (Phase 2). Each item has acceptance criteria (AC). An item ships only when every AC is verified, and the evidence is recorded in docs/PROGRESS.md. Priorities: P0 must ship; P1 should ship (defer with a written reason); P2 stretch. **Cut P2 before compromising P0/P1 quality.** The coordinator's decisions (2026-09-26) are folded in; where a research doc differs, this spec wins.

Theme: turn RigTune from a one-shot tuner into an ongoing performance companion (profiles, stutter diagnosis, JVM advice, benchmark history, server-aware advice, change awareness) that stays within its own footprint budget.

Research inputs: docs/research/v0.4/{mc-versions,v03-deferred,profiles,stutter,jvm-gc,bench-history-a11y,server-view-distance,drivers,footprint,external-review}.md. Orientation (2026-09-26): MC 26.3 is the newest release and 26.4 exists only as `26.4-snapshot-1` (no Sodium/Iris/DH build for it); the Modrinth project is still "processing" (not approved); the user's real instance still runs 0.1.0 and hasn't been played since 2026-09-25 09:08; no PR is open (6 total, all merged, none from the rules updater).

Compatibility promise:
- **0.1.x (rules-v1.json):** never an unsafe or less conservative recommendation. RulesV1DifferentialTest (including `tierTablesStayAtV010`) and `tools/check_rules_v1.py` (CI `rules-v1-compat`) stay green. v0.4's only rules-v1 content change is the VSync-off entry becoming unticked (2k, more conservative). Every new rules feature (`profileTemplates`, `stutterAdvice`, the `driverVersion` condition, the `jvm-*` advice and `jvm-` flag facts) is v2-only: the updater strips the sections from v1, gives the new advice `"v1": false` and never adds a key to `V1_CONDITION_KEYS`. No new tier row is planned; any that is added carries `"v1": false`.
- **0.2.0 and 0.3.0 (rules-v2.json):** their `Condition`/`ConditionAdapterFactory`/`ConditionEvaluator`/`Truth` are byte-identical (`git diff v0.2.0 v0.3.0` empty, drivers.md §4.1). (a) The new condition key `driverVersion` poisons any condition to UNKNOWN there: `LegacyConditionFailClosedTest` runs every rule using it through pinned copies (`src/test/java/.../v020/core/rules/`, verbatim from `v0.2.0`). (b) The new top-level sections are ignored by their parsers (verified with the released 0.2.0 jar and 0.3.0: stutter.md §5.2, profiles.md §3): `LegacyRulesParseTest` loads the regenerated bundled rules-v2.json with pinned 0.2.0 and 0.3.0 `RulesDocument`/`RulesLoader` copies and gets the same mod/setting/advice counts as with the sections removed. `stutterAdvice` entries also carry `requires: ["stutter-doctor"]`. (c) The `jvm-*` advice (item 6) carries `requires: ["jvm-flags"]`, which 0.2.0/0.3.0 skip (their `SUPPORTED_FEATURES` is empty), and a `jvm-` flag they don't know fails closed anyway. (d) No `schemaVersion` bump.
- **Files 0.1.0/0.2.0/0.3.0 wrote keep working after the upgrade, and a downgrade to 0.3.0 keeps working.** No `formatVersion`/`schemaVersion` bump anywhere. New data goes in new files; existing files get only optional additive fields (old record constructors kept as overloads, the BenchmarkRecord precedent). What happens when 0.3.0 (or 0.2.0) rewrites a file and drops an unknown field:
  - `pending.json`: + optional `projectId` on ENABLE_FILE ops (2d). The 0.1.0/0.2.0/0.3.0 helpers ignore it (plain Gson records, verified on gson 2.10.1 and 2.14.0). If dropped, the staged-changes view contributes nothing for those ops (v0.3 behaviour). No new op type.
  - `history.json`: + optional `modName` on changes (2c); `formatVersion` stays 1; profile switches are kind `apply` with ordinary `setting` changes (4). If dropped, History shows file names again; profile labels live in profiles.json keyed by entry id, which 0.3.0 rewrites preserve.
  - `benchmarks.json`: + optional `context.modSetHash` and `context.journalCursor` (7); `schemaVersion` stays 1. If dropped, those runs compare only with runs that also lack a hash, and the change window falls back to timestamps.
  - `settings.json`: + optional `stutterMonitor` (default false, 5). If dropped, the monitor is off (the safe default).
  - Unchanged: `last-apply.json` (only the helper's free-text wording changes, 2f), `rigtune.json`, `rules-cache.json` (0.1.0's, read-only), `rules-v2-cache.json` (content only), `benchmark-restore.json`, `helper/`.
  - New files (older versions never read them): `profiles.json` (4), `stutter.json` (5), `server-limits.json` (8), `awareness.json` (9), `startup-times.json` (13). Footprint numbers are a CI artifact only (10). Shapes and common rules: "Shared contracts" C1.
  - Proof: pinned `src/test/java/.../v030/` copies (verbatim `git show v0.3.0:`, package-renamed like v010/v020) read every 0.4-written file in unit tests; a CI harness compiled against the **released** 0.3.0 jar (profiles.md §3 method) does the same; an e2e downgrade run (AC3.2).
- **The ApplyHelper path stays core + Gson only** (HelperLauncherTest). No new pending.json op type (an older helper fails one as "unknown operation"; one reason P2 item 12 is deferred).

Cross-cutting rules (every item):
- X1 Network off: every new feature works fully on-device, and nothing new opens a connection. Each new game-test class runs its main case once with `networkEnabled = false`.
- X2 No hard-coded UI strings: every string comes from en_us.json (LangCheckTest), inserted alphabetically inside the feature's prefix block (C5). Rule-provided text stays English data.
- X3 One hub, one notice slot: RigTuneScreen gets exactly one new footer button ("Tools…") and one header notice line (C3). No feature adds its own button or header line there.
- X4 Honest wording: estimates are called estimates; benchmark and stutter correlations are "may be related" or "likely", never causes. `WordingTest` fails if an en_us.json value or ShareReport output contains "limited by" or "bottleneck", or if a `rigtune.stutter.*`, `rigtune.benchmark.trend.*`, `rigtune.awareness.*` or `rigtune.startup.*` value contains "caused" or "because of".
- X5 Footprint: every new always-on path (frame hook, tick hook, notice evaluation, PowerWatcher, stutter sampler) is inside item 10's budget and measured by it. Notices are evaluated on screen init/rebuild, never per frame.
- X6 Undoable: anything that changes a setting goes through `RealController.apply` → journal → Undo (profile switches included). Advice-only features (stutter, JVM, server, awareness, trend, startup) write nothing outside their own new file.
- X7 Screens fit 640×480 at GUI scale 2. Game-test screenshots at the standard 3 sizes (1280×720@2, 640×480@2, 854×480@2); owners look at them.
- X8 `core/` has no Minecraft imports. Each feature's client logic lives in its own service class; RealController and RigTuneController get one-line delegations only (C4).

## 4. Performance Profiles and share codes (P1)
Sources: docs/research/v0.4/profiles.md §0-6, §8-9.
- Interpretation (recorded in DESIGN): "optional-mod on/off" means Distant Horizons rendering (`dh.client.advanced.debugging.rendererMode` DEFAULT/DISABLED) and Iris shaders (`iris.enableShaders`) as **settings**. No jar enable/disable in v0.4 (it needs a restart and a new helper op).
- A profile is a value map over the managed keyset: the share table keys (below) plus the local-only `sodium.performance.chunk_builder_threads` and `dh.common.multiThreading.numberOfThreads`. Never `vanilla.graphicsPreset`, `iris.shaderPack` or any other key.
- **A switch is an ordinary Apply.** It builds `Action.SetSetting(key, current, target)` recommendations for the keys that are present in `SettingsBridge.read` (a key is never created), pass `SettingKeys.changeable`/`safeValue` and differ by `SettingValues.same`, and runs them through a new overload `RealController.apply(selected, entryId)` (`apply(selected)` delegates). Vanilla keys apply now; Sodium/DH/Iris keys are staged for the helper. One journal entry of kind `apply`; Undo last/this/all unchanged (the released 0.3.0 UndoPlanner undoes switch entries, profiles §3). The label ("Profile: Battery") lives in profiles.json keyed by the journal entry id.
- `PendingActions.merge`: a `PATCH_*` op on the same path and single key replaces the older one (into `Merged.replaced`, so `Staging` marks the older journal change DISCARDED through `HistoryUpdates.discard`). Two switches before a restart leave one op per key. Client side only.
- Guards: refused while downloading and while `BenchmarkController.running()`; `graphicsPreset` never included.
- **Templates** Max FPS, Balanced, Quality, Battery and Recording are computed on demand by pure `core/profile/ProfileTemplates`, in layers: the baseline ("My settings", auto-saved from the managed keys the first time Profiles opens; re-savable) → the rules' value entries evaluated with the template's goal and forced facts (a `Recommender.settingTargets(...)` extraction; `recommend()` output unchanged) → the template's overrides from rules-v2 `profileTemplates` → every clamp (rules + template) last → the filters above. A document without the section (a v1 document or an old cache) → the bundled rules' section.
  - Max FPS: goal performance; `maxFps` 260 (unlimited); VSync off.
  - Balanced: goal balanced (the same values as applying every current setting recommendation).
  - Quality: goal quality; the heap and DH clamps still apply.
  - Battery: goal performance + facts `onBattery`/`hasBattery` (the rules then give maxFps 60, VSync on, inactivity `afk`); shaders off (Iris present), **DH rendering off** (`rendererMode` DISABLED, DH present), clouds off, render distance ≤ 8, simulation distance ≤ 6, particles at least Decreased.
  - Recording (stable frame pacing): goal balanced; `maxFps` = `$recordingFps` (60 when the display is ≥ 60 Hz or unknown, otherwise its rate rounded down to 10, at least 30); VSync on only when the display is ≤ 60 Hz; inactivity `minimized` (no 30 FPS AFK throttle during idle shots); Sodium chunk updates `ALWAYS`, or vanilla `prioritizeChunkUpdates` 0 without Sodium (even frame times over pop-in).
- Rules: a new optional top-level rules-v2 section `profileTemplates: {"templates": [{"id", "goal", "facts"?, "settings": [SettingRule…], "requires"?}]}` (shape in profiles §4.2, plus Battery's DH entry). `$recordingFps` is resolved only in the template layer. update_rules.py validates it (known ids, goal vocabulary, `facts` ⊆ {onBattery, hasBattery}, settings entries as SettingRule, keys in the managed keyset) and leaves it out of rules-v1.json; RULES_SCHEMA.md documents it.
- **Share code** `RT1-` + base64url without padding of (body ‖ CRC32 big-endian). Body: `fmt` u8 = 1, `nameLen` u8 ≤ 64, UTF-8 name, `count` u8 1..64, then `count` pairs of (uvarint key index into the frozen, append-only `core/profile/ShareKeys` v1 table, uvarint value). Values: enum index, bounded int (value − min), bool, `maxFps` (value/10 − 1; the reserved wire value 26 means "match display refresh" and resolves on import to the importing display's `$refreshRateCap`, or 60 when its refresh is unknown), quarter steps for `entityDistanceScaling`. No strings, paths, mod ids or floats on the wire; the thread counts, `graphicsPreset` and `shaderPack` aren't shareable. Typical code: 102 characters.
- **Strict decoding**, in order (profiles §5.3): raw input > 4096 chars → reject; strip ASCII whitespace; require `^RT[0-9]+-[A-Za-z0-9_-]{8,}$` and ≤ 700 chars; version ≠ 1 → "made by a newer RigTune"; strict base64url (no padding, no invalid characters, zero spare bits); CRC; `fmt` 1; strict UTF-8; exactly `count` pairs and no trailing bytes; canonical varints ≤ 5 bytes and < 2^31; a duplicate key → reject; an unknown key index → skipped and counted ("N settings need a newer RigTune"); a known key out of range → reject. The name is sanitised: NFC; Cc, Cf (bidi overrides, zero-widths, U+FEFF), Co, Cs, Cn, Zl and Zp dropped; whitespace collapsed; ≤ 32 code points; empty → "Imported profile". It's rendered only as a literal and never used in a path (profile ids are `p-<uuid>`).
- Import **always** shows Preview first: PreviewScreen gains an overload with confirm buttons (Apply / Save only / Cancel). Only keys present in this instance take part (Sodium keys only with Sodium loaded and the key in its file; DH/Iris keys through their patchers, which refuse missing keys); `SettingsBridge.problems` and the stagers run before Preview. Nothing is written before a click, and the clipboard is read only on Paste. The player's own profiles and the templates switch in one click (toast "Switched to Battery. Undo it in History.").

Pure `core/profile/BatteryPrompt` decides: an AC → battery edge, no offer in the last 10 minutes, not snoozed ("Don't offer again"), no benchmark running, Battery not already active; battery → AC offers the previous profile. The offer is a notice (C3, first priority) with a "Switch to Battery" action plus a SystemToast. **Never auto-switch.** Prompt state lives in profiles.json.

## 5. Stutter Doctor (P1)
Sources: docs/research/v0.4/stutter.md §0-9.
- Data sources: the **benchmark always records** into the same analyser (capture on during its sweeps; one line on the result screen, e.g. "2 spikes; likely causes: garbage collection"). The **session monitor** is opt-in: `settings.json` `stutterMonitor`, default off, toggled in RigTuneSettingsScreen and on StutterScreen. It is on-device, pausable (Pause/Resume on StutterScreen), runs only while a world is loaded and stops on world exit: the session summary goes to stutter.json and the buffers are released; the next world starts a new session while the setting is on.
- Capture (`client/stutter/`): the existing `DebugScreenOverlayMixin` (`logFrameDuration(J)V`, identical on 26.2 and 26.3) gains one call, `StutterMonitor.onFrame(d)`: allocation-free primitive rings allocated on enable (~1.8 MiB, research §2.5), ~21 ns per frame measured, one volatile read when off. **Phase timers** (packets/ticks/render/limiter, `@Inject INVOKE` pairs in `Minecraft.runTick`/`renderFrame`) are UNVERIFIED injection points: they ship only if the first real run shows them injecting with plausible values on both versions; otherwise the mixin is removed and attribution uses the no-phase rules (research §4.2).
- GC: `GcListener` adds a NotificationListener to every `GarbageCollectorMXBean` only while capture is on (removed on stop, so the JVM builds no notifications when off). `gcAction == "end of GC cycle"` is concurrent (context, **never a pause**); everything else is a pause; sub-kinds FULL, EXPLICIT (`System.gc()`) and STALL_HINT (ZGC "Allocation Stall", Shenandoah "Allocation Failure"). Clock: anchor `nanosAtUptimeZero` on enable; offset = min(receive uptime − `endMs`) over the session; pause interval = [start + offset, end + offset + 1 ms]. The receive time is never used as the pause time (delivery lag reached 96 ms under load). Until the first notification: "GC timing not calibrated yet".
- Signals: `ClientChunkEvents.CHUNK_LOAD` count; Sodium 0.9.2's builder counters via reflection (`SodiumWorldRenderer.instanceNullable()` → `renderSectionManager` → `getBuilder()` → scheduled/busy/total), with vanilla `SectionRenderDispatcher.getCompileQueueSize()` as fallback; absent or changed members switch the signal off (logged once), never a crash. `ServerLifecycleEvents.BEFORE_SAVE/AFTER_SAVE` (singleplayer autosave; a save without AFTER_SAVE is closed after 10 s). `ClientLevelEvents.AFTER_CLIENT_LEVEL_CHANGE` (join/dimension; the next 10 s are "world loading", excluded). END_CLIENT_TICK: teleport (> 64 blocks in one tick; the next 10 s are "after teleport"), fast movement (> 20 blocks/s), menus and an unfocused window (excluded). A 4 Hz `ThreadSampler` daemon ("RigTune stutter sampler") groups thread CPU by name (Render thread, Server thread, Worker-Main-*, IO-Worker-*, Chunk Render Task Executor #*, DH-*, other) through ThreadMXBean without safepoints. Distant Horizons is only inferred from DH- thread CPU (low/medium confidence, labelled so). No system-wide CPU load (the JDK call takes 110-125 ms on Windows).
- Detection and attribution run off-thread when StutterScreen opens (copies of the rings; "Analysing…"). Spike: d > max(2 × b, b + 8 ms, 20 ms), b = median of the previous 120 non-spike gameplay frames (an EWMA until 30 exist); spikes < 100 ms apart merge into one hitch; severity minor < 50 ms, major 50-100, severe 100-500, freeze ≥ 500. Lost time e = d − b is apportioned in the order GC overlap → packets → ticks → render (measured, each capped at what's left); world save, DH, CPU contention, teleport, fast movement and world loading are **tags that never claim milliseconds**; the unexplained remainder is always shown. Fewer than 3 spikes or less than 2 minutes of gameplay → "not enough data".
- Advice: a new top-level rules-v2 section `stutterAdvice` (AdviceRule shape; each entry `requires: ["stutter-doctor"]`). Stutter condition keys (`stutterShareAtLeast`, `stutterTaggedShareAtLeast`, `gcFullPausesAtLeast`, `gcStallsAtLeast`, `gcExplicitPausesAtLeast`, `liveSetPercentAtLeast`, `heapRaiseRoomMbAtLeast`, `cpuContentionShareAtLeast`, `spikesPerMinuteAtLeast`, `gcCollector`) are `Condition` fields that `ConditionEvaluator` evaluates against optional `StutterFacts` in its context and returns UNKNOWN without them, so they can never fire in the main list; the updater accepts them only inside `stutterAdvice`. `core/stutter/StutterAdvisor` evaluates the section (its supported features: `stutter-doctor`; the main Recommender doesn't know that feature). Seeds per research §5.2: `ram-stutter-gc-heap`, `stutter-gc-explicit`, `stutter-sodium-defer`, `stutter-dh-threads`, plus an info entry for chunk-loading-dominant sessions. Any GC-choice wording comes only from item 6's conclusion (single source); memory advice ids start with `ram-` (launcher steps); `-XX:+DisableExplicitGC` is never suggested. The section is stripped from v1.
- UI: StutterScreen (hub entry): a header (session length, gameplay time, frames, average FPS, 1 % low, spikes by severity, lost time), a time-weighted frame-time histogram (9 buckets), likely causes (claimed-ms shares, "not explained X %", then tag counts such as "7 of 12 spikes happened during world saves (not measured)"), the 10 worst spikes with a confidence marker, fired advice, and Start/Pause/Stop, Clear, Copy summary (clipboard only) and Done.

## 6. JVM and GC advice (P1)
Sources: docs/research/v0.4/jvm-gc.md (final, 2026-09-26: 33 clean interleaved runs on 26.2, RD 16, -Xmx4G; contaminated runs listed and excluded in §4.1/§4.4). Where this section and the final doc differ, the final doc wins.
- Read on-device, once per session on `Probes.EXECUTOR` (`client/probe/JvmProbe`, like LauncherProbe; every call wrapped, and a JVM without `com.sun.management` (OpenJ9) turns the check off): `RuntimeMXBean.getInputArguments()` (everything the JVM saw, `JAVA_TOOL_OPTIONS` included, not the class path), `HotSpotDiagnosticMXBean.getVMOption(name)` (effective value + origin), the GC bean names (collector family; typed or ergonomic from the `Use*GC` origins), `Runtime.maxMemory()`, `InitialHeapSize`, `Runtime.version()`, `java.vendor`. **Raw arguments are never shown, logged or shared** (they hold paths with the Windows user name); only flag names from RigTune's own table or the bare `-XX:` name.
- Pure `core/jvm/`: `JvmArgs` (typed entries, k/m/g units, last-wins duplicates; launcher-injected arguments recognised and ignored: Modrinth's agent/IPC/log4j, Prism's `-Duser.language`/`--add-opens`, ATLauncher's `MetaspaceSize`, the version JSON's natives, brand and `HeapDumpPath`); `JvmFlagClassifier` → `JvmFinding`s: IGNORED (`getVMOption` finds no such option, e.g. `ZGenerational`, removed in 24: a future Java won't start with it), OVERRIDDEN (a boolean reads back differently, e.g. `UseNUMA`/`UseLargePages` on Windows), plus the curated harmful/server-set/cost rows of research §2; and facts in `HardwareProfile.flags` (`jvm-gc-g1|zgc|shenandoah|parallel|serial|epsilon|other`, `jvm-gc-typed`, `jvm-ignored-flags`, `jvm-young-gen-fixed`, `jvm-server-flags`, `jvm-explicit-gc-disabled`, `jvm-probed` (amendment J-M1)) that `ConditionEvaluator` accepts under the `jvm-` prefix. The runtime check needs no per-JDK table (it keeps working on Java 26/27); the curated table is re-checked with each new Java the game ships with. Flags that stop the JVM from starting (CMS, `AggressiveOpts`, `PermSize`, two collectors, `-Xms` > `-Xmx`) can't be seen in a running game: README help only.
- Measured conclusion (research §4, medians): G1 default 1931 FPS / 1 % low 610 / 27 pauses, 84 ms total, max 6.5 ms / 1.3 GB committed; the official/ATLauncher default set 1937 / 616; G1 + compact headers 1915 / 580; Aikar's set 1926 / 622 / 6 pauses, 10 ms / 4.1 GB committed; ZGC 1922 / 627 / pauses < 1 ms / 3.9 GB committed; capped at 140 FPS G1 and ZGC matched (1 % low 126 vs 127); ZGC at 2 GB slightly lower (564 vs 627, 3 runs). **Java's defaults are the baseline.** On this machine every launcher-style set (the official/ATLauncher default, Aikar's server set, compact object headers) measured the same FPS, 1 % low and p99 as plain G1 within run-to-run noise; generational ZGC the same frame rates with sub-millisecond pauses, but its heap stays committed near `-Xmx` (3852 of 4096 MB vs about 1.3 GB for G1). So RigTune never recommends adding GC flags or switching collector as an FPS gain: it sizes `-Xmx` (the existing `ram-*` rules), names ignored, harmful or costly flags, and leaves the launchers' default sets and a working ZGC alone. Item 5's GC wording follows this.
- Advice: rules-v2 `advice` with `jvm-` ids, `requires: ["jvm-flags"]` (0.2.0/0.3.0 skip them; `Recommender.SUPPORTED_FEATURES` becomes `{"jvm-flags"}` in 0.4) and `"v1": false`: `jvm-ignored-flags` (info), `jvm-young-gen-fixed` (`-Xmn`/`NewSize` under G1: warning), `jvm-stop-the-world-gc` (typed Serial/Parallel: warning), `jvm-no-gc` (Epsilon: critical), `jvm-server-flags` (Aikar markers or ≥ 4 of its distinctive flags, only on PCs with ≤ 16 GB RAM where keeping the whole heap committed matters: info; measured: same frame rates, the whole heap stays committed), `jvm-explicit-gc-disabled` (info), `jvm-zgc-small-heap` (ZGC, heap ≤ 3 GB: info), `jvm-zgc-small-pc` (ZGC, RAM ≤ 8 GB, heap ≥ 4 GB: info). Claims quote Java's own documentation (research §2 citations). Under each `jvm-` advice the client adds "Found in your Java arguments: <flag names>" and the detected launcher's Java-arguments steps (`LauncherAdvice.JVM_ADVICE_PREFIX`; `rigtune.launcher.jvm_steps.{modrinth_app,prism,atlauncher,official}` from each launcher's source where open; the official labels UNVERIFIED; CurseForge gets the generic text). Heap advice keeps v0.3's memory steps (Prism's Memory box overrides an `-Xmx` typed in its Java Arguments).
- UI: JvmScreen (hub "JVM & memory"): Java version and vendor, the collector and whether it was typed, max and initial heap, the findings and the fired `jvm-`/`ram-` advice with their steps. The share report gains one line, "Java: 25.0.3 (Azul Systems), G1, 2 argument notes", with no argument text.
- AC6.1 JvmArgsTest: units and signs, last-wins duplicates, `-D` markers, junk tokens, an empty list. AC6.2 JvmFlagClassifierTest over real command lines (research §1.1): the user's Modrinth line (`-Xmx6144M` plus injected arguments), the official launcher's logged default line, ATLauncher's defaults and Prism's line → no findings; Aikar's set → `jvm-server-flags`; `-XX:+ZGenerational` with a lookup that lacks it → IGNORED; `-XX:+UseNUMA` reading back false → OVERRIDDEN; `-Xmn1G` → young-gen-fixed; `-XX:+UseParallelGC` from `JAVA_TOOL_OPTIONS` → stop-the-world; ergonomic G1 → nothing; no HotSpot bean → no facts and no exception. ## 7. Benchmark history and regression alerts (P1)
Sources: docs/research/v0.4/bench-history-a11y.md Part A, external-review.md §2/§3.
- **Comparable** = same MC version, scene, render and simulation distance (the knob values), context (width, height, fullscreen, shaders + pack, DH rendering, protocol) and mod set. New optional `Context` fields (additive constructor overload): `modSetHash` (SHA-256 over the sorted (mod id, version) pairs of the loaded mods; local only) and `journalCursor` (id of the newest history.json entry at the time of the run). Runs without `modSetHash` (0.3.0 runs, or runs a 0.3.0 rewrite stripped) compare only with each other. `BenchmarkHistory.comparable(latest, max)` feeds the trend; `chart()` stays for old callers.
- Noise floor = 2 × max(latest.cv or 5 %, 1.4826 × MAD(comparable 1 % lows) / median), and at least 3 comparable runs; a delta is shown only past it, otherwise "in line with your usual". Pure `core/benchmark/BenchmarkTrend` (median, MAD, `noiseFloor`, `Regression(median, latestLow, deltaPercent, baselineRunId)`). Research: same-session 1 %-low CV 1.7-12.3 % (median 4.2 %), so the 5 % default stays; retune once real cross-session history exists.
- **Regression** = the latest run's 1 % low below the comparable median by at least the floor. The alert is anchored at the most recent comparable run before it: "1 % lows 18 % below your usual 543 FPS since Sep 24". Below it, "Changes since then (may be related):" lists the History entries between the two runs (walked by `journalCursor`, else by timestamps) with HistoryModel's labels, plus a RigTune version change without an apply entry; if `modSetHash` differs without a matching journal change: "Something outside RigTune changed too (the mod set differs)"; if nothing was recorded: "No change recorded; possibly a driver, OS or other change". When the latest run isn't comparable (conditions differ), no delta is claimed: "Performance changed under different conditions (<the differing keys>); cause unknown." An improvement is never an alert. A benchmark never names a bottleneck.
- Where it shows: BenchmarkResultScreen (under the gain line) and BenchmarkHistoryScreen (hub entry): a per-context trend chart of comparable runs only (up to 10: bars, a thin 1 %-low/average polyline and the flat median line), the note "N comparable runs; M with different conditions not shown", and a context selector over the contexts present. A regression also raises a notice (C3), shown once per regression until acknowledged (awareness.json `acknowledgedRegressions`).
- "Last benchmark" line: the tier badge's tooltip (2j) and the share report show the latest run with its context ("1 % low 543 FPS · RD 12 · 2560×1440 · shaders off · Sep 24"), and "needs a rerun (<what changed>)" when the current resolution, fullscreen, shaders/pack, DH, mod set, render/simulation distance or MC version no longer match it; a stale result also raises the lowest-priority notice.
- AC7.1 BenchmarkHistoryTest: `comparable()` returns only matching runs (each key varied in a mixed fixture), oldest first, capped; runs without `modSetHash` only with each other. AC7.2 BenchmarkTrendTest: median and MAD on fixed arrays; the floor truth table (below → no alert; at/above → alert; n < 3 → no alert whatever the delta); an improvement is never an alert. AC7.3 ChangeWindowTest: a history fixture gives the right labels and order for a window by cursor and by timestamps; a RigTune version change; a differing hash without a journal match; an empty window. AC7.4 BenchmarkCompatibilityTest: a 0.4 file with the new Context fields loads in the pinned 0.2.0 reader and a new pinned 0.3.0 reader (`v030/core/benchmark/`) without a `.bad`, every other field equal. AC7.5 BenchmarkResultScreenTest (truth table of lines) and BenchmarkHistoryGameTest (seeded benchmarks.json: 4 comparable runs + a regressed latest run; history.json with a mod update in between): the regression line, "Changes since then (may be related)" naming the update, the trend chart and the "not shown" note; after changing the seeded context's resolution, the "needs a rerun" marker; screenshots at 3 sizes.
