# Minecraft 26.4: what it breaks in RigTune (survey, 2026-11-06)

Input for sizing the 0.6 port (issue #49). Measured against **26.4-snapshot-7** (released 2026-11-03, the newest
snapshot on 6 Nov). The node was added locally with the fixed `tools/add_mc_version.py 26.4-snapshot-7
--prerelease-ok` (Fabric API 0.165.4+26.4 beta, Mod Menu 22.0.0-alpha.3 from snapshot-6, Iris kept from 26.3, no
Sodium), built with `./gradlew :26.4-snapshot-7:build --continue`, then removed. Nothing about the node was committed.
`tools/mc_apidiff.py 26.3 26.4-snapshot-7 --sets main,client,gametest` added the reference-level check.

## Summary

- **`main` compiles unchanged.** Its 545 classes are byte-identical to the 26.3 build. All the breaks are in `client`
  (99 javac errors in 24 files). `gametest` didn't compile because it depends on `client`, but apidiff finds nothing
  new in it: its two 26.4 renames (`getUncachedNoiseBiome`, `getBaseHeight`) are already handled by the
  `//? if >=26.4-alpha` blocks from snapshot-1.
- **One big mechanical change.** The GUI extract pass no longer passes `mouseX, mouseY, partialTick`: they moved onto
  `GuiGraphicsExtractor`. It accounts for 88 of the 99 errors (41 overrides and their `super` calls).
- **Five small changes**: `AbstractWidget.visible` is protected, `FormattedText.getString()` takes a max length, Fabric
  API's `HudElement` lost its `DeltaTracker` parameter, `CycleButton` was split (binary-only), and OSHI was upgraded.
- **OSHI: Minecraft still bundles it.** 26.4-snapshot-6 upgraded it from 6.9.0 to OSHI 7.7.2, which drops
  `oshi.SystemInfo`. RigTune doesn't need its own OSHI dependency, jar-in-jar, licence notice or extra jar size; it
  needs one `//? if` for the new entry point.
- **Size: about 12 agent-hours in total**, in two phases. The compile port (about 4 h) can be done now. The rest waits
  for 26.4 pre-releases and Sodium/Iris builds (see "Port size").

## The breaks

Line numbers are in the generated 26.4-snapshot-7 sources, which line up with `src/` (the appendix has every one).
"G" is `net.minecraft.client.gui.GuiGraphicsExtractor`.

### 1. The extract pass lost its mouse and partial-tick parameters (88 errors)

| 26.3 | 26.4-snapshot-7 |
|---|---|
| `Screen.extractRenderState(G, int mouseX, int mouseY, float partialTick)` | `Screen.extractRenderState(G)` |
| `AbstractSelectionList.Entry.extractContent(G, int, int, boolean hovered, float)` | `extractContent(G, boolean hovered)` |
| `AbstractSelectionList.extractItem(G, int, int, float, E)` | `extractItem(G, E)` |
| `AbstractWidget.extractWidgetRenderState(G, int, int, float)` (abstract) | `extractWidgetRenderState(G)` |
| `AbstractWidget.extractRenderState(G, int, int, float)` (final) | `extractRenderState(G)` (final) |
| none | `G.mouseX()`, `G.mouseY()`, `G.partialTicks()`, `G.deltaTracker()`, `G.extractWithoutMouse(Runnable)` |

RigTune has 19 screen overrides, each with a `super.extractRenderState(graphics, mouseX, mouseY, partialTick)` call,
22 list-entry `extractContent` overrides, `RowList.extractItem`, `RowFocus.extractWidgetRenderState` and three direct
`widget.extractRenderState(...)` calls (`ButtonRow:56`, `RigTuneScreen:850`, `RigTuneSettingsScreen:285`). Of the 41
screen and entry overrides, only 10 use the mouse position or partial tick for more than the `super` call. On 26.4
those 10 read them from `graphics.mouseX()` and friends.

Fix shape: **shared helpers, not 45 `//? if` blocks around signatures.**

- A `RigTuneScreenBase extends Screen` holds the only version-dependent `extractRenderState` override (one
  `//? if >=26.4-alpha` block: on 26.4 it reads the mouse and partial tick from `graphics`, before that it receives
  them). It calls a version-neutral `extractScreen(G, int mouseX, int mouseY, float partialTick)` plus a
  `extractVanilla(G, int, int, float)` helper that calls `super` with the right signature. The 19 screens change
  `extends Screen` to `extends RigTuneScreenBase` and rename the method and the `super` call, with no conditionals.
  `ProfilesScreen.NameScreen` is one of them.
- A `RowEntry<E> extends ContainerObjectSelectionList.Entry<E>` does the same for `extractContent`, giving the 22 entry
  classes `extractRow(G, int, int, boolean, float)`. Every RigTune entry extends
  `ContainerObjectSelectionList.Entry`, directly or through a screen's own abstract row (`ButtonRow` extends
  `StutterScreen.Row`), and every list extends `RowList`.
- `RowList.extractItem` and `RowFocus.extractWidgetRenderState`: one `//? if` block each.
- A `Widgets.extract(AbstractWidget, G, int, int, float)` helper with one block, for the three direct calls.

### 2. `AbstractWidget.visible` became protected (2 errors)

26.4 adds `isVisible()`/`setVisible(boolean)` and makes the field protected. 26.2 and 26.3 have no `isVisible()`.
Used in `RigTuneClient:295` and `:318`, the entry button's click-through and overlap checks. Fix: a
`Widgets.visible(AbstractWidget)` helper with one block (`isVisible()` on `>=26.4-alpha`, `.visible` before).

### 3. `FormattedText.getString()` became `getString(int maxLength)` (3 errors)

26.4 bounds text visits (`FormattedText.DEFAULT_MAX_ITERATION = 65536`, `visit` became `visitUnbounded` plus bounded
overloads). `Component.getString()` still exists, so only the calls on a plain `FormattedText` break:
`BenchmarkResultScreen:402` and `StutterScreen:713,716` (all on `font.substrByWidth(...)` results). Fix: a tiny
`Texts.plain(FormattedText)` helper with one block (`getString(FormattedText.DEFAULT_MAX_ITERATION)` on 26.4).

### 4. Fabric API `HudElement.extractRenderState(G, DeltaTracker)` became `extractRenderState(G)` (1 error)

In Fabric API 0.165.x for 26.4, `HudElement` extends the new vanilla `Updatable` (a default `update(DeltaTracker)`),
and the render method takes only the graphics. `RigTuneClient:100` registers the benchmark progress overlay as a
`(graphics, delta) -> {...}` lambda that doesn't use `delta`. Fix: one `//? if` around the lambda header.

### 5. `CycleButton` was split into `AbstractCycleButton` (0 compile errors; a recompile is enough)

`withValues`, `withTooltip` and `OnValueChange` moved to `AbstractCycleButton$Builder<Value, B>` (self-typed) and
`AbstractCycleButton$OnValueChange`. RigTune's builder chains (`RigTuneScreen`, `RigTuneSettingsScreen`,
`BenchmarkHistoryScreen`, `BenchmarkMenuScreen`, `TryItScreen`) still compile. They only break at the binary level,
so the 26.3 jar would crash on 26.4 even if the version range allowed it. No source change is needed.
`mc_apidiff` lists the five methods as MISSING; the javac run is what shows they're source-compatible.

### 6. OSHI 7: `oshi.SystemInfo` is gone (4 errors)

Library lists from the Mojang version JSONs:

| Version | OSHI | JNA |
|---|---|---|
| 26.3, 26.4-snapshot-1 | `com.github.oshi:oshi-core:6.9.0` | 5.17.0 |
| 26.4-snapshot-6, -7 | `com.github.oshi:oshi-common:7.7.2` + `com.github.oshi:oshi-core-ffm:7.7.2` | 5.19.1 |

**Minecraft did not stop bundling OSHI.** It moved to OSHI 7, which splits the API (`oshi-common`: `oshi.hardware.*`,
plus a native-free `oshi.nativefree.SystemInfo`) from the implementation (`oshi-core-ffm`: `oshi.ffm.SystemInfo`, on
Java's FFM API instead of JNA). Both register as `oshi.spi.SystemInfoProvider` services. Minecraft's own
`SystemReport` now calls `oshi.spi.SystemInfoFactory.create()`, which returns a `SystemInfoProvider`
(`getHardware()`, `getOperatingSystem()`). Every `oshi.hardware` member RigTune uses still resolves on 7.7.2; only
`new SystemInfo()` (`HardwareProbe:188`, `PowerWatcher:127`, and their imports) breaks.

So the probe needs **no OSHI dependency of its own**: no jar-in-jar, no licence notice (OSHI is MIT either way), no
jar size. Fix: one helper, e.g. `Oshi.hardware()` returning a `HardwareAbstractionLayer`, with `//? if` imports and
body (`SystemInfoFactory.create().getHardware()` on `>=26.4-alpha`, `new SystemInfo().getHardware()` before), used by
both classes.

Runtime checks that still need a real 26.4 client (they can't be done from a compile):

- The FFM provider needs native access. Minecraft's launch arguments already include
  `--enable-native-access=ALL-UNNAMED` (26.3's do too), so no new warning is expected, but launchers that build their
  own arguments (Prism, MultiMC, ATLauncher, GDLauncher) are worth one smoke test each.
- When the FFM provider isn't available, `SystemInfoFactory` may fall back to the native-free one, which can report
  less. Check that GPU names, VRAM, CPU and memory, and the battery filter (the fake "System Battery" on desktops, see
  docs/PROGRESS.md "Lessons") read the same as on 26.3 on Windows and Linux.
- `HardwareProbe` reads all its hardware through this call inside a `try` (`OSHI unavailable` is logged, and the
  probe goes on with what the JVM knows), so a wrong entry point would fail quietly. The port's test should assert
  that the card, CPU and RAM come from OSHI. `PowerWatcher.oshiBatteries()` has no `try` of its own.

## Other changes to review (not breaks)

From `mc_apidiff` (71 referenced classes differ; the full report is reproducible with the commands above):

- `Options` keys: `key.socialInteractions` became `key.otherPlayers`; `options.graphicsApi.tooltip.vulkan` is gone; a
  new experimental Windows option `preferDXGIPresent`. RigTune reads `Options` by reflection (`Options$FieldAccess`,
  `graphicsPreset`, `processOption`), and those names still resolve. Check whether a rule should mention DXGI present.
- Runtime default: 26.4 makes Vulkan the default renderer (tools/MC_VERSIONS.md, "Adding a version", step 3), so review
  the `vulkan-backend`, `ixeris` and `vulkanmod` rules and the Vulkan game-test leg.
- `AbstractWidget.isHoveredOrFocused()` became `isHighlighted()`, and `GuiGraphicsExtractor.fill/blit/blitSprite` take
  a `GuiPipeline` instead of a `RenderPipeline`. RigTune uses neither, but they matter for any new UI code.
- `KeyEvent` gained a `repeat` component. RigTune's game tests don't construct `KeyEvent` (apidiff finds no reference).
- Not checked: the `e2e`, `e2eUndo` and `e2eDowngrade` driver mods (not part of `build`; they compile against the old
  release jars and use `Button`, `AbstractSelectionList`, `MouseButtonEvent`), plus Sodium, Iris and Distant Horizons
  names in strings (not on the classpath). The port should compile the drivers once (`e2e.yml` does).

## Port size

About **12 agent-hours** in total, in two phases:

1. **Now, against the newest snapshot (about 4 h, one worker).** The helpers and `//? if >=26.4-alpha` blocks above,
   until `:26.4-snapshot-N:build` passes on a scratch node and `./gradlew build` still passes for 26.2 and 26.3. Commit
   only `src/`, as tools/MC_VERSIONS.md "Snapshot canary" says. This closes #49 on the next green canary run. Risk: the
   remaining weekly snapshots can still move this API (it moved between snapshot-1, which was clean in
   docs/v0.3/verification/mc-tooling/, and snapshot-6), so budget about 1 h per later snapshot that breaks something.
2. **Once 26.4 has a pre-release, and Sodium and Iris builds (about 8 h, one or two workers).** Add the real `26.4`
   node (`add_mc_version.py 26.4`; DESIGN.md says pre-release nodes aren't shipped). Then: `runClientGameTest` on
   OpenGL and Vulkan (2-3 h, one client at a time); the OSHI runtime checks above on Windows and Linux; the mc_apidiff
   review of the changed classes, the Vulkan-default rules and `Options` keys; regenerate the rules; and update the
   docs, the Modrinth body and the CHANGELOG (about 1 h). Add time for game-test fixes if the extract-pass change moved
   hover or tooltip behaviour (unknown until the tests run).

Can't be done until then: shipping a 26.4 jar (needs the release, or at least a pre-release to test against), anything
with Sodium (production smoke test, benchmark numbers, Sodium rules), the Iris API check, and a stable Fabric API and
Mod Menu for the release node. Whether to drop 26.2 in 0.6 (docs/STATUS.md release plan) doesn't change the size much:
the helpers carry one `//? if` each either way.

## Why the canary saw only one 26.4 snapshot

The canary's resolve step picked the newest snapshot every week; run 41831747063 (4 Nov) logged
`Testing Minecraft 26.4-snapshot-7`. Its green "skip" was `add_mc_version.py` refusing the node: "no Mod Menu build
for 26.4-snapshot-7 yet". The same refusal skipped snapshots 2, 3, 4 and 5 (30 Sep to 21 Oct; snapshot-3's alpha.2
came out on 12 Oct, after that week's run). The only build was snapshot-6 on 28 Oct, which opened #49. Mod Menu
doesn't build every snapshot, and it is compile-only for RigTune, so `add_mc_version.py` now uses the newest Mod
Menu build for an earlier pre-release of the same version when the snapshot has none (a release still needs its own).
`tools/tests/fixtures/snapshot-canary/manifest-2026-11-04.json` is the 4 Nov manifest shape for the resolve step's
test.
