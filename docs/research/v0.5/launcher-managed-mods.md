# Launcher-managed mods: why the Modrinth App's Update failed, and "RigTune never fights the launcher" (v0.5 P0.4)

Research only, 2026-09-27 (r-launchers). Nothing in the repo was changed except this file; no Gradle, no Minecraft, no git. The user's Modrinth App data and instance were only read (bounded listings, the launcher logs, the instance's `config/rigtune/*.json`); `app.db` was only opened as copies (`scratchpad/mrapp/app.db` = before the user's fix, `scratchpad/mrapp/postfix/app.db` = after, both re-copied into `scratchpad/r-launchers/db/` so the coordinator's copies stay untouched). Pinned sources: Modrinth App **modrinth/code v0.21.5, commit 22ccdc1** (the installed version); Prism Launcher 11.1.0 (ea87ffc); MultiMC 0.6.16 (c6b6096); PolyMC 7.1 (9b01b80); ATLauncher v3.4.41.3 (1dac5d8); GDLauncher Carbon `develop` 35533d7 (no tags); CurseForge app and the official launcher from support pages and community sources (closed source). The same pins as docs/research/v0.4/launcher-steps.md. §3 merges my own reading with three sub-agent reports (`scratchpad/r-launchers/sub-*-handback.md`); which is which is marked there.

## Summary

**Root cause.**
1. RigTune 0.1-0.4 updates a mod by renaming the old jar to `<old>.jar.disabled` and putting the new one at Modrinth's file name, assuming a launcher simply follows `.disabled` renames (docs/DESIGN.md "Apply pipeline").
2. The Modrinth App 0.21 keeps its own row per file plus a project link; for an old (pre-0.21, "unmanaged") row it does follow the rename, so the old version stays linked, disabled, with an update pending to exactly the file name RigTune wrote, while RigTune's jar becomes a second, unlinked row at that name.
3. The app refuses any update whose target file name already has a row ("The updated filename belongs to another content item", `content_mutation.rs:266-278`), Update all stops at the first refusal, and rows are never pruned, so it stays broken until the old copy is deleted **in the app**.

**Recommended design (v0.5).**
1. A pure `ModFilesPolicy.of(launcher, instance evidence, opt-in)` decides per instance: **LAUNCHER** (mod-file actions become advice) for the Modrinth App, the CurseForge app, ATLauncher, and any launcher whose `mods/.index/` holds packwiz `*.pw.toml` files (Prism, PolyMC); **UPDATES_IN_LAUNCHER** for GDLauncher (updates only); **RIGTUNE** (one-click, as 0.4) for the official launcher, MultiMC and Unknown without metadata; **PENDING** (treated as LAUNCHER) while detection hasn't answered.
2. Advice means: Add, Update, Disable, RigTune's own self-update and the Undo of an *applied* mod-file change keep their place in the list with the launcher's own click steps, and no jar is renamed, added or removed (a report transform like `ModrinthOffAdvice`, a skip reason in `UndoPlanner`, a guard in `RealController.apply`).
3. Everything that isn't a jar stays one-click in every launcher: vanilla options, Sodium/DH/Iris config patches, Profiles, the benchmark, and cancelling RigTune's own staged ops and downloads.
4. A per-instance opt-in, Settings → Mod files → "Let RigTune change them anyway" (`settings.json` `modFilesByRigTune`, default off), restores 0.4 behaviour, with honest wording about the launcher losing track.
5. File-op groups left in `pending.json` by 0.1-0.4 are held at exit in an advice instance (the helper runs config patches only) and offered for cancelling.
6. A repair notice built only from RigTune's own records (`history.json` incl. 0.1.0's legacy import, `last-apply.json`, the mods folder) lists the old copies to delete **in the launcher**, with its steps; RigTune never reads or writes another program's database.
7. The helper stops calling "download gone, target present" its own change (realworld's RW-1 fix), so History and Undo never claim a jar the launcher installed.
8. The Modrinth App's game-settings sync can overwrite RigTune's option changes before a launch and copy them to other instances; nothing RigTune may read shows whether it's on, so RigTune detects the effect (values at exit vs at the next start) and names the app's switch, plus a one-line note and a README section.
9. Offline, undoable, no file-format change; 0.4.0 reads everything, and a downgrade to 0.4.0 behaves like 0.4.0 (it applies held groups at its exit).
10. For 0.1-0.4 players: one rules warning shown only to old clients (`modVersion` of `rigtune` `<0.5.0-`), plus a known-issue section with the repair steps in the README and on the Modrinth page.

## 1. The Modrinth App: how it tracks an instance's content

Everything here is from modrinth/code **tag v0.21.5, commit 22ccdc1** (paths under `packages/app-lib/src/`), the two read-only DB copies (`pre` = before the user's fix, `post` = after; queried from copies in `scratchpad/r-launchers/db/`), the app's own logs (`%APPDATA%/ModrinthApp/launcher_logs/`, read only) and a bounded, read-only listing of the instance folder and its `config/rigtune/`.

**Version.** `Modrinth App.exe` reports ProductVersion 0.21.5, and the 2026-09-25 09:02 log says "Creating pre-migration app database backup from version 0.21.4 before opening with version 0.21.5". So the user's app was upgraded 0.21.4 → 0.21.5 minutes before RigTune 0.1.0's apply (the helper renames are stamped 2026-09-24 23:09 UTC = 09:09 local). The coordinator's copy of `content_mutation.rs` is byte-identical to the v0.21.5 file.

### 1.1 The data model (two kinds of file row)
- `instance_files` has one row per content file, keyed by `(instance_id, relative_path)`, where `relative_path` is always the **canonical** path (`.disabled` stripped) and `enabled` says which form is on disk (`content_store/domain/paths.rs:92-106`, `file_path_on_disk`).
- `instance_content_entries` links a file row to a Modrinth project/version (`file_id`, `project_id`, `version_id`, `source_kind`, `enabled`). `instance_content_update_checks` caches "the newest version for this entry".
- `store_instance_files` (0.21's new content store) binds a file row to a blob (`materialization_kind` reflink/hardlink/copy). Two kinds of rows follow:
  - **store-managed** rows (a binding exists): everything installed, updated or re-installed **through the app since 0.21**. In this instance: 9 of the 57 mod rows before the fix (ImmediatelyFast, architectury, Entity Culling 1.11.1, Fabric API, Iris, ShulkerBoxTooltip, Sodium, both Xaero maps), all `copy`; 12 of 54 after it.
  - **unmanaged** rows (no binding): everything older, and everything another program put there. 0.21.5 never converts them: `try_shared_file` has its reflink/hardlink body commented out and always returns `None` (`content_store/adapters/filesystem.rs:193-209`), so `can_share_content` is always false (`:340-351`), so every legacy adoption ends `Deferred { "Content links are unavailable in this directory" }` (`instances/commands/content_mutation.rs:145-152`, `migrate_legacy_content.rs:167-175`). The log repeats that warning for every old jar on every start (176× on 09-27). This is 0.21.5 behaviour on every PC, not a quirk of this one.
- Content entries are created **only** by the app's own installs: `upsert_entry_for_file` is called from the Install commit only (`content_mutation.rs:670-681`; its only definition `apply_content_install.rs:747-771`; the only other writer is the whole-instance snapshot restore, `adapters/sqlite/content_rows.rs:777-812`). Nothing creates an entry for a file the app found on disk.

### 1.2 Discovering files another program added
- `sync_instance_content_files` (`instances/commands/sync_content_files.rs:32-338`) runs on every Content-tab load, before every launch (`launcher/mod.rs:1134`), on update checks, and from the file watcher, which queues it for any event under `mods/`, `resourcepacks/`, `shaderpacks/`, `datapacks/` (`instances/watcher.rs:264-277`, `:30-93`).
- It scans only top-level files whose name ends in `.jar` (or `.jar.disabled`) in `mods/` (`instances/adapters/filesystem.rs:27-54`, `:92-111`). So **`*.jar.rigtune-pending`, `*.jar.rigtune-superseded` and `mods/update/` are invisible to the app** (and so is `config/`: the watcher emits nothing for it, `watcher.rs:250-256`).
- A new jar gets a new `instance_files` row (sha1 from the hash cache) and **no content entry** (`sync_content_files.rs:235-283`). DB proof: the 11 files RigTune 0.1.0 wrote on 2026-09-24 23:09 UTC (bbe, moreculling, asynclogger, fastquit, Ixeris, structure_layout_optimizer, ResourcefulConfig, entityculling 1.11.2, modmenu 20.0.3, YACL 3.9.7, zoomify 2.16.3) all have rows with `added_at` = that minute and no entry, still two days later.
- **Linking by hash, for display and updates only.** The Content list takes project/version from the entry, else from the Modrinth hash lookup (`list_content.rs:1242-1255`, `file_metadata_from_entry_or_cache`); that is why the app shows icons for RigTune's jars. The update check runs over **all** file rows by sha1, entry or not, missing or not (`check_content_updates.rs:88-130`); it stores a result only for rows with an entry (`:170-181`) but returns updates for entry-less ones too. So the app does offer updates for RigTune-added jars, and updating one works: the install path renames the row and creates the entry (`content_mutation.rs:633-684`).

### 1.3 `.disabled` renames done by another program
- **Unmanaged row:** followed. `normalize_legacy_content_files` flips the row's `enabled` (path stays canonical) and the entry's `enabled` (`sync_content_files.rs:490-563`). DB proof: `modmenu-20.0.2.jar`, `yet_another_config_lib_v3-3.9.6…jar`, `zoomify-2.16.1…jar` are `enabled=0`, entry `enabled=0`, each with an update check pointing at exactly the version RigTune had installed next to it (`iRo7AZXf`, `DoR7RYgi`, `2Qr8jSFc`).
- **Store-managed row:** not followed. The file status is `Conflict` when the opposite form exists (`content_store/commands/instance_files.rs:38-66`), so the row becomes `missing=1` and stays `enabled=1` (`sync_content_files.rs:179-213`; the repair toggle there only runs for rows that are already disabled). The `.disabled` file itself is skipped with "Ignoring content at the inactive form of a managed path" (`:225-234`); the rename detector needs the same enabled state, so it doesn't match either (`:398-405`). DB proof: `entityculling-fabric-1.11.1-mc26.2.jar` is `copy`-bound, `enabled=1, missing=1`, entry intact, update check `RWjup6Jf` (= 1.11.2); the 09-25 and 09-27 logs warn about its `.disabled` file 2× and 43×; the file is still on disk today. In the app the old Entity Culling simply vanished.

### 1.4 Pruning: never
- A sync only sets `missing=1` (`sync_content_files.rs:288-312`, `content_rows::set_instance_file_missing`); the only row deletion outside whole-instance operations is the app's own **Remove/Delete** (`content_mutation.rs:709-731` → `content_rows.rs:1043`). DB proof: DH 3.2.0 has been `missing=1` since 2026-09-20 (7 days), entityculling 1.11.1 since 09-24, `rigtune-0.1.0.jar` since 09-27; all still there after the fix.
- Missing rows are hidden: the Content list skips them (`list_content.rs:800-802`), and so "Update all", which only updates listed, unlocked items (`apply_content_update.rs:460-483`), never touches them. The install-candidates query ignores them too (`list_content.rs:131-139`).

### 1.5 What the app's own mutations assume (why Update failed)
- **Update / Update all** (`apply_content_update.rs:67-208`): the new file goes to `mods/<Modrinth's primary filename>` (`apply_content_install.rs:461-495`), i.e. exactly the file name RigTune downloads. `prepare_install` then refuses when that path differs from the old one and **any** row, missing or not, is registered at it: "The updated filename belongs to another content item" (`content_mutation.rs:266-278`). RigTune's new jar is exactly such a row. Update all downloads everything, then installs one by one with `?`, so the first collision aborts the rest (`apply_content_update.rs:163-205`).
- An update keeps the old row's enabled state (`content_mutation.rs:279-286`; `apply_content_update.rs:96-102`): updating a disabled old copy gives a disabled new one, which must then be switched on.
- Toggle/remove/install refuse when both `X` and `X.disabled` exist ("Both … exist; resolve the duplicate before continuing", `content_store/commands/file_changes.rs:72-80`), when a store-managed file's bytes changed ("The content file was changed outside the app", `:103-110`; "Content was changed outside the app; resolve the conflict first", `content_mutation.rs:410-414`), or when a file differs from a registered one only in case (`:238-253`). A fresh **install** onto a path that already has a row takes that row over (`:254-260`, `:655-681`), so installing the same version RigTune already put there just links it.
- The app never blocks a launch because of any of this (`validate_instance` is commented out, `launcher/mod.rs:1141`).

So the fix that worked was **deleting the old disabled copy in the app** (one click per mod); RigTune's new jars were kept and still have no entry (the app updates and links them the first time it updates them, §1.2). The two store-managed cases (Entity Culling 1.11.1, DH 3.2.0) never blocked Update all, because their rows were already missing and hidden; they remain as phantom rows with a stray `entityculling-fabric-1.11.1-mc26.2.jar.disabled` on disk (harmless to Fabric, ignored by the app).

**Two secondary findings for the coordinator:**
1. **RigTune now claims a jar the app installed.** `ApplyExecutor.enable` treats "download gone, target present" as done (`src/main/java/.../core/apply/ApplyExecutor.java:674-681`), and the duplicate check only reads jars whose download still exists (`:331-351`). Because the user deleted the `.rigtune-pending` file and the app installed the same file name, `history.json` now lists "enable DistantHorizons-3.3.2…jar APPLIED" in the legacy-import entry. RigTune 0.4.0's **Undo everything** would therefore disable the app's DH 3.3.2 (a store-managed row → it goes missing and vanishes from the app) and disable Entity Culling 1.11.2 (same). This is realworld's RW-1 (`docs/research/v0.5/real-world-2026-09-27.md`), with a prototype fix; see §5.4.
2. Mods' own updaters desync the app too (most likely the DH swap above). Nothing for RigTune to do beyond the existing `Staging.dropQueuedUpdates` rule; worth one README line.

### 1.7 Which external changes are safe (Modrinth App 0.21.5)
| change by another program | effect on the app | verdict |
|---|---|---|
| edit `options.txt`, `config/**` | none (config not watched; options.txt only feeds synced options, §2) | **safe** |
| write `mods/*.jar.rigtune-pending` / `.rigtune-superseded`, `mods/update/` | invisible (not scanned) | safe |
| add a jar | entry-less row; shown with icon via hash; app updates it later by hash, which links it | tolerated (cosmetic; the app can't tell where it came from) |
| rename an **unmanaged** jar to `.disabled` | followed; the old row keeps its entry and its pending update | safe on its own; **fatal next to an added jar at the update's file name** (update pair) |
| rename a **store-managed** jar to `.disabled` | row goes missing, mod vanishes from the app; the `.disabled` file is ignored and later blocks toggles/installs of that path | **desyncs** |
| delete a jar | row goes missing (kept for ever, hidden); a later update *to* that file name is refused | **desyncs** (slowly) |
| RigTune update = disable old + add new under Modrinth's file name | old row (entry, update pending to that exact name) + new row at that name ⇒ **Update / Update all fail** ("belongs to another content item") | **breaks the app** |
| RigTune Undo of that update (rename back) | old row re-enabled, new row disabled; the new row still sits at the update's file name ⇒ still fails | does **not** repair |

RigTune cannot tell a store-managed row from an unmanaged one without reading `app.db`, so v0.5 must treat every jar in a Modrinth App instance as the app's.

## 2. The Modrinth App's synced game options

**Is it on here? No.** Both copies: `sync_feature_settings.game_options` `globally_enabled=0` (new_instance_default 1), `instance_sync_preferences(game_options)=0` for the instance, and every `synced_game_option_*` / `instance_game_option_*` table is empty. Only `screenshots` sync is globally on. The instance's `instance_launch_overrides` blob has hooks and visible tabs but no `force_fullscreen`; the global `mc_force_fullscreen=0`. `%APPDATA%/ModrinthApp/synced-options/` holds only empty `hotbars/` and `servers/` folders, so the folder's existence is not a signal.

**When it reads or writes `options.txt`** (when on; participation = instance preference AND global switch AND a supported game version AND not pending, `api/instance/synced_options/orchestration.rs:1437-1450`, `game_options/write_shared_settings.rs:27-39`):
- **Before every launch from the app:** `launcher/mod.rs:1118-1132` calls `sync_before_launch` (`game_options/launch_overrides.rs:26-37`), which writes every enabled shared value into `options.txt` (`write_shared_settings.rs:178-234`). It doesn't capture the file's current values first, so a change made while the app wasn't watching is **overwritten** for the synced keys.
- **Whenever `options.txt` changes while the app runs** (also while the game runs: game options may apply while running, `synced_options/files.rs:85-94`): the watcher (`instances/watcher.rs:163-181`, `:313-327`) → `reconcile_changed_file` (`orchestration.rs:1137-1186`) → `capture_instance_options` reads the changed values into the shared store and **writes them into every other participating instance** (`write_shared_settings.rs:236-288`, `:306-364`).
- At game exit nothing extra for game options (`reconcile_instance_with_state` skips them, `orchestration.rs:1062-1109`).
- Independently of sync, if "force fullscreen" is set (globally, or per instance), `fullscreen` is written before each launch (`api/instance/run.rs:238-243`, `launch_overrides.rs:42-76`).
- Synced by default when the feature is on (catalog `default_on`, `game_options/catalog/video.rs`): `graphicsPreset/graphicsMode`, `ao`, `gamma`, `fov`, `guiScale`, `particles`, `renderClouds`, `entityShadows`, `bobView`, `enableVsync`, `fullscreen`, `maxFps`, `inactivityFpsLimit`, `biomeBlendRadius`, `prioritizeChunkUpdates`, `cutoutLeaves`, `improvedTransparency`, `vignette`, … and every unknown key discovered in an options.txt (`read_instance_changes.rs:343-353`). **Not** by default: `renderDistance`, `simulationDistance`, `entityDistanceScaling`, `mipmapLevels`, `textureFiltering`, `maxAnisotropyBit`, `cloudRange`, `weatherRadius`, `chunkSectionFadeInTime` (the player can switch each on). Modpack updates are written to keep game settings (`game_options/pack_updates.rs:1`); not traced further.

**Consequences for RigTune** (only when the player has turned it on):
1. RigTune's settings change (and its Undo) is written by Minecraft into `options.txt`; with the app open it is captured and **copied to every other synced instance**, which RigTune doesn't journal there.
2. If the app was not running when the file changed, the next launch from the app puts the shared values back: a silent revert of RigTune's change (or of its Undo) for the synced keys.
3. RigTune's History/Undo stays consistent inside the instance (it journals before/after), but "you changed it since" will fire if the app overwrote a key.

**Can RigTune see whether it's on? No, not from anything it may read.** The switches live only in `app.db` (`sync_feature_settings`, `instance_sync_preferences`), which RigTune must not open. The `synced-options/` folder exists as soon as any sync feature was set up (here: hotbars and servers, both off) and only holds backups (`orchestration.rs:1230-1260`), so it proves nothing.

**What RigTune does about it (settings stay one-click everywhere):**
1. **Detect the effect, not the switch.** At `CLIENT_STOPPING` RigTune stores the current values of the vanilla keys it has ever changed (from `history.json`) in `awareness.json` (a new optional field; the file keeps unknown fields and 0.4 ignores it). At the next start, before the player can change anything, it compares `options.txt` with that snapshot. Any difference was made outside Minecraft: the Modrinth App's `sync_before_launch`, its fullscreen override, a hand edit, or another instance's fan-out while this game was closed. `fullscreen` is left out (F11 and the launcher's override both touch it).
2. When keys changed that way, one notice (a NoticeSource): "N settings were changed outside the game since you last played (e.g. render clouds: Fast → Fancy)." In a Modrinth App instance it adds: "The Modrinth App's game settings sync does this: App settings → Synced settings → Sync game options, or this instance → Instance settings → Sync overrides → Unsync game settings." Buttons: **Apply RigTune's values again** (an ordinary Apply of the journaled `after` values, one journal entry) and **Keep**. It never reverts anything by itself.
3. **The fan-out to other instances can't be seen from inside this one.** One line wherever RigTune applies settings in a Modrinth App instance (Preview's "written now" section and the Apply status): "If the Modrinth App syncs game settings, it copies these to your other synced instances." Plus a README section. RigTune installed in those other instances detects the change there (point 1).
4. Undo is unaffected inside the instance (it journals before/after); a key the app overwrote shows "You changed it since" in the Undo screen, which is true from RigTune's point of view.
5. Labels are from `apps/app-frontend/src/locales/en-US/index.json` at v0.21.5 (`app.settings.tabs.synced-options` "Synced settings", `app.settings.synced-options.game-settings` "Sync game options", `instance.settings.tabs.settings-overrides` "Sync overrides", `instance.settings.tabs.synced-options.game-settings` "Unsync game settings"). The behaviour is source-traced, **UNVERIFIED** in a running app; not P0 for this user (off here).

## 3. Other launchers

Sources: Prism/MultiMC/PolyMC and ATLauncher/Carbon read at the pinned commits (files and sparse clones in `scratchpad/r-launchers/sub-*`; the Prism files were spot-checked byte-identical against tag 11.1.0); CurseForge and the official launcher are closed source, so only support pages and community sources (dates and URLs in `sub-cf-handback.md`). ### 3.1 Prism Launcher 11.1.0 (ea87ffc): tolerant until its own Update runs
- **Record:** packwiz metadata `mods/.index/<slug>.pw.toml`, written by its downloader before the jar (`launcher/modplatform/packwiz/Packwiz.cpp:146-247`, slug file name `:67-73`; `ResourceDownloadTask.cpp:67-72`) [both]. Fields: `name`, `filename`, `side`, `[download] url, hash-format, hash`, `[update.modrinth] mod-id, version` or `[update.curseforge] file-id, project-id`, plus `x-prismlauncher-*` [both]. Instances where the player only dropped files in have no `.index/`.
- **Files it didn't install:** status `NO_METADATA` (`minecraft/mod/tasks/ResourceFolderLoadTask.cpp:70-92`); **Check for Updates** / **Verify Dependencies** first create metadata by hash (Modrinth, then CurseForge) and force `filename` to the name on disk (`ui/dialogs/ResourceUpdateDialog.cpp:305-380`, `modplatform/EnsureMetadataTask.cpp:480-486`) [both].
- **`.disabled`:** Prism's own convention; a `.disabled` file is matched to its metadata through the name without the suffix, so a jar RigTune disabled shows as disabled with its metadata (`Resource.cpp:52-56`, `ResourceFolderLoadTask.cpp:93-105`) [both].
- **Orphans:** metadata without a file is deleted on the first load after the Mods page starts watching, once per open (`ResourceFolderLoadTask.cpp:113-124`, `ResourceFolderModel.cpp:56-59`, `:418-426`) [both].
- **Its update on RigTune's pair:** downloads the new version to `mods/<its file name>`, then `uninstallResource(oldFilename, true)`, which strips `.disabled` when matching and calls `destroy(…, attempt_trash = false)` → `FS::deletePath`: **RigTune's disabled old jar is deleted for good, not trashed** (`ResourceDownloadTask.cpp:74-79`, `:110-121`; `ResourceFolderModel.cpp:210-228`; `Resource.cpp:253-263`) [both]. When Prism's version is the one RigTune installed, the download overwrites RigTune's identical jar and the result is clean; when a **newer** version exists, RigTune's jar (no metadata) stays next to Prism's new one: **one mod twice, Fabric refuses to start** [sub; the code path confirmed by me]. RigTune's journal then points at a deleted `.disabled` file (Undo skips it, FILE_GONE).
- **Its own rename:** when both `x.jar` and `x.jar.disabled` exist, a load renames the disabled one to `x.jar.duplicate` (`launcher/FileSystem.cpp:1680-1705`, from `ResourceFolderLoadTask.cpp:74-80`) [me].
- **options.txt:** only touched by Copy Instance and ATLauncher-pack import, never at launch/exit (search, **UNVERIFIED** as exhaustive) [sub].
- **Steps:** the instance → **Edit...** → **Mods** → select → **Remove** / **Enable** / **Disable** / **Check for Updates** / **Reset Update Metadata** (`ExternalResourcesPage.ui:92-218`, `MainWindow.ui:391-403`) [both].
- **Verdict:** with `.index/` present, RigTune's update pairs turn the next Prism update into a permanent delete and possibly a double mod: **LAUNCHER**. Without `.index/`, nothing tracks the files: **RIGTUNE**.

### 3.3 GDLauncher Carbon (develop 35533d7): add/disable fine, update not
- **Record:** SQLite `ModFileCacheRow { instance_id, filename (without .disabled), filesize, enabled, addon_type, metadata_id }`, unique `(instanceId, filename)` (`crates/carbon_repos/src/repos/mod_file_cache.rs:24-33`, `:489-497`); metadata found by `(sha512, murmur2)` [both].

## 4. Recommended design: "RigTune never fights the launcher"

### 4.1 The rule
When the instance's launcher keeps its own record of the mod files (§3.7), RigTune renames, adds or removes **no jar** unless the player opted in for this instance: every Add, Update and Disable recommendation, RigTune's own self-update, and the Undo of an *applied* mod-file change become advice with that launcher's click steps (for GDLauncher only the update-shaped ones). Settings (vanilla options, Sodium/DH/Iris config patches, Profiles, the benchmark) stay one-click in every launcher: none of them tracks config files, and the Modrinth App's options sync is handled in §2. RigTune's own files (`pending.json`, `*.rigtune-pending`, `*.rigtune-superseded`, `config/rigtune/**`) are ignored by every launcher checked (§1.2, `Utils.java:1597-1599`, packwiz only indexes `*.pw.toml`), so cancelling staged work stays one-click too.

### 4.2 The policy (core, pure)
`core/launcher/ModFilesPolicy` (new): `enum { RIGTUNE, LAUNCHER, UPDATES_IN_LAUNCHER, PENDING }` and `static ModFilesPolicy of(@Nullable LauncherInfo launcher, InstanceEvidence evidence, boolean optIn)`, in the order of the §3.7 table. `InstanceEvidence` is a record the client fills: `boolean packwizIndex` (at least one regular file `*.pw.toml` directly in `<modsDir>/.index/`, read with a bounded directory listing: stop after the first match or 256 entries, regular files only, no symlink following, like `InstanceFiles`' rules). `LauncherProbe` computes it on `Probes.EXECUTOR` with the rest of the detection. `LauncherInfo` itself is unchanged.
- **Timed-out detection = PENDING, not Unknown.** Today `LauncherProbe.withTimeout` completes with `LauncherInfo.UNKNOWN` (`LauncherProbe.java:57-58`); v0.5 completes it with a distinct "not yet" value (e.g. `null` → PENDING), which behaves like LAUNCHER until the real answer arrives and the next rebuild lifts it. Only a completed detection with no signal is Unknown.
- **Unknown without `.index/` = RIGTUNE (as 0.4).** Every launcher known to keep a per-file record is detected from a signal it always sends (`theseus`, ATLauncher's and GDLauncher's brands, `minecraftinstance.json`) or from `.index/`. What remains (the dev environment, HMCL, SKLauncher, TLauncher, PojavLauncher, scripts) runs the game from a plain folder as far as known (**UNVERIFIED** each), and RIGTUNE keeps 0.4's behaviour and every existing test.
- `RigTuneController.modFiles()` exposes the policy to screens (f-firstapply's first-run panel reads it; agreed by message 2026-09-27).

## 5. Repair for players already in this state

### 5.1 What RigTune can know from its own records (never another program's database)
- `history.json` (0.2+; the 0.1.0 apply arrives as the `legacy-import` entry, `LegacyImport.java`; this instance has exactly that entry with 17 file changes) gives, per group: DISABLE (`file`, `resultFile`) and ENABLE (`file`, `modId`) changes with status APPLIED; `last-apply.json` the helper's per-op outcome; `pending.json` the still-staged groups; `unfinished-groups.json` the renames 0.4+ actually did.
- The mods folder (RigTune's own `Folder`/`JarInfo`) tells which of those files still exist and which mod id each jar declares.
- **Update pair still in effect:** an APPLIED group with one DISABLE `o` and one ENABLE `n` of the same mod id (legacy-import disables have `modId` null here, e.g. "disable None modmenu-20.0.2.jar": read the `.disabled` jar's id), where `resultFile(o)` (or `o.jar.disabled`) **and** `n` are both in `mods/`. That is the state that breaks the Modrinth App's Update all when `o`'s row is unmanaged (and GDLauncher's and Prism's update of that mod, §3). RigTune can't tell unmanaged from store-managed rows; the steps cover both.
- **Added jar:** an APPLIED ENABLE without a DISABLE in its group, still present (not RigTune itself). Harmless in the Modrinth App (§1.2).
- **Disabled-only:** an APPLIED DISABLE whose `.disabled` file exists. Harmless when unmanaged; a store-managed one has vanished from the app; in ATLauncher its record is gone.
- Changes whose file is gone (the player already deleted them in the app, as here for modmenu/YACL/zoomify) count as repaired.
- **This instance today:** one pair still in effect (Entity Culling: `…1.11.1-mc26.2.jar.disabled` + `…1.11.2-mc26.2.jar`; but 1.11.2 is now the app's own reinstall and 1.11.1's row is store-managed and hidden, so nothing to do in the app); 7 adds (nothing to do); the DH group is "applied" in history although the app installed that jar (§1.6 finding 1, realworld RW-1).

### 5.2 The notice (only under LAUNCHER / UPDATES_IN_LAUNCHER, only while something is in effect)
Title: "Mod changes from an older RigTune: help <launcher> catch up". Modrinth App body for pairs: "RigTune changed these mods without the Modrinth App. If the app's Update or Update all fails with "The updated filename belongs to another content item", do this **in the app** (not in File Explorer: the app keeps its own list): open this instance → **Content** → filter **Disabled** → select the old copy → **Delete**: <o₁>, <o₂> … RigTune's newer versions stay and keep working. If an old copy isn't listed, the app has already hidden it: nothing to do." Adds: "RigTune also added: <n₁> … The app lists them as your own files and will update them itself; nothing to do." Buttons: **Copy list** (clipboard, file names only) and **Dismiss** (per set of pairs, stored with the existing dismissed-notice ids in `awareness.json`).
- Why "delete the old copy" rather than "delete the new one, update the old one, switch it on": it is one step per mod, it is what fixed this instance (§1.6: Update all succeeded at 10:28:34 right after), and it keeps the version RigTune installed. The other order also works (the update keeps the disabled state, `content_mutation.rs:279-286`, hence the extra "switch it on"); give it as the alternative for players who want the app to own every file.
- Labels: "Content" (`app.instance.tab.content`), "Disabled" filter (`content.filter.disabled`), "Delete {itemType}" (`content.confirm-deletion.header`), "Update all" (`content.page-layout.update-all`), "Upload files" (`content.page-layout.upload-files`), from `apps/app-frontend` and `packages/ui` `locales/en-US/index.json` at v0.21.5. The row's own delete control is an icon whose tooltip wasn't found in the locale files (**UNVERIFIED**), hence "select → Delete", which uses the verified selection bar.
- Other launchers, with their own labels from §3: Prism: **Edit...** → **Mods** → select the old disabled copy → **Remove** (before any **Check for Updates**); GDLauncher: **Mods** → the old disabled copy → **Delete**; ATLauncher: nothing to do for pairs (its record already follows the new jar), but a mod RigTune disabled is invisible there: re-enable it by renaming `x.jar.disabled` back or through RigTune's Undo with the opt-in; CurseForge: **UNVERIFIED** steps (remove the mod in the profile and reinstall it there).

### 5.3 What RigTune does itself: only its own files
- **Stale `.rigtune-pending` downloads and held groups:** offered for cancelling (§4.3 "Exit / helper"). The launchers ignore them, so this is housekeeping, not repair.
- **Pending groups for mods the launcher has since installed or updated:** the helper abandons a group when another jar declares the mod id (`ApplyExecutor.java:331-351`) and, with RW-1, when the target is already there without RigTune's record; v0.5 holds them anyway in an advice instance.
- **Not** renaming, moving or deleting the old `.disabled` copies itself. It would unblock Update all (a moved-away unmanaged row goes missing and hidden, §1.4) but leaves phantom rows, is again RigTune changing mod files behind the app's back, and can't be timed against the app's own syncs. Coordinator decision if wanted: an explicit button "Move RigTune's old disabled copies to config/rigtune/moved-mods/", journaled and undoable.
- **Never** touching `app.db` or any launcher's metadata.

### 5.4 Stop claiming jars RigTune didn't put there (owned by realworld: RW-1)
`ApplyExecutor.enable` records "download missing, target present" as `SKIPPED_ALREADY_DONE` (`:674-681`), so a jar the launcher installed under the same file name becomes an APPLIED RigTune change (this instance: DH 3.3.2). My check of `UndoPlanner.move` (`:806-832`) agrees with realworld's run of the planner (`real-world-2026-09-27.md` §2.3): Undo here would disable the app's Entity Culling 1.11.2 and re-enable 1.11.1, which re-creates the update collision in the app (1.11.1's store-managed row turns healthy again with its update to 1.11.2's file name, while 1.11.2's row goes missing). The DH group is skipped only because `fabric-26.2.jar` is gone. realworld's prototype (§2.4 there: count it as done only when `unfinished-groups.json` or the previous `last-apply.json` proves the rename, else ABANDONED "installed another way") is the fix; this design adds nothing to it and depends on it for History being right. The Undo rule in §4.3 covers RW-2 even before RW-1 lands.

## 6. Players who never update (0.1.x-0.4.x)

What the rules can and cannot do (from `docs/RULES_SCHEMA.md`, the pinned v0.1.0 copy under `src/test/java/.../v010/`, `rules/rules-v2.json` revision 16):
- **Updates: nothing honest.** 0.1.x offers every Modrinth update, ticked, whatever the rules say (`v010/core/recommend/Recommender.java:211-231`). 0.2-0.4 have `skipUpdateWhen` (v2), but only for mods that have a ModRule (28 of them), and the client then shows "<mod> updates itself: Its own auto-updater is on" (`Recommender.java:411-416`), which would be false. Don't.
- **Additions: can be unticked.** `defaultSelected: false` on every ModRule (v1 and v2) keeps them offered but unticked in 0.1-0.4 (`v010 Recommender.java:204`; RulesV1DifferentialTest allows "ticks none that was unticked"). It would untick them in 0.5 too, for every launcher, and adds are the least harmful change in the Modrinth App (§1.7). Not recommended.
- **There is no launcher condition** (no key or flag tells rules which launcher runs the game; `RULES_SCHEMA.md` Condition table), so nothing can target Modrinth App players only.
- **What works: one warning, shown only to old clients.** An AdviceRule, kind `warning`, `when: {"modVersion": {"rigtune": "<0.5.0-"}}` (a legacy-v2 key, known to 0.2.0+ per `tools/update_rules.py:71-73`; FALSE on 0.5.0 and its pre-releases), with a `v1` override `{"when": {"always": true}}` for 0.1.x (which can only be below 0.5). Text (English literal, short): "Using the Modrinth App, CurseForge, ATLauncher, GDLauncher, or Prism with mod updates? Untick RigTune's Install, Update and Disable items and make those changes in the launcher: RigTune's mod-file changes can make the launcher's updates fail. Already happened? In the Modrinth App: Content → Disabled → delete the old copies. RigTune 0.5 does this for you." More conservative for v1 (an advice, no appliable change). **Needs a test** that 0.2.0/0.3.0/0.4.0 evaluate `modVersion` on RigTune itself (today's `ModScanner.scan` skips only built-ins, `ModScanner.java:36-55`, `:72-74`, so `rigtune` is listed with its version; **UNVERIFIED** for the pinned old copies) before it ships.
- `minModVersion: "0.5.0"` shows "Update RigTune" (MEDIUM) on 0.1-0.4 with a generic reason (`Recommender.java:465-474`, `v010 :306-311`). Reasonable once 0.5.0 is out; note that RigTune's own self-update in a Modrinth App instance makes the same kind of pair for `rigtune` itself.
- **README / Modrinth listing (known issue):** "RigTune 0.1-0.4 in the Modrinth App (and other launchers that keep their own mod list): when RigTune updated or added mods, the app's Update / Update all can fail with "The updated filename belongs to another content item". Fix: in the Modrinth App open the instance → Content → Disabled → delete the old copies of the mods RigTune updated (RigTune's new versions stay). Don't delete files in File Explorer: the app keeps its own list. RigTune 0.5 no longer changes mod files in these launchers; it tells you what to change there." Plus the §1.6 DH note (mods that update themselves can cause the same) and the §2 note on the app's game-settings sync.
