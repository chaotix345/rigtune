# Launcher-managed mods: why the Modrinth App's Update failed, and "RigTune never fights the launcher" (v0.5 P0.4)

Research only, 2026-09-27 (r-launchers). Nothing in the repo was changed except this file; no Gradle, no Minecraft, no git. The user's Modrinth App data and instance were only read (bounded listings, the launcher logs, the instance's `config/rigtune/*.json`); `app.db` was only opened as copies (`scratchpad/mrapp/app.db` = before the user's fix, `scratchpad/mrapp/postfix/app.db` = after, both re-copied into `scratchpad/r-launchers/db/` so the coordinator's copies stay untouched). Pinned sources: Modrinth App **modrinth/code v0.21.5, commit 22ccdc1** (the installed version); Prism Launcher 11.1.0 (ea87ffc); MultiMC 0.6.16 (c6b6096); PolyMC 7.1 (9b01b80); ATLauncher v3.4.41.3 (1dac5d8); GDLauncher Carbon `develop` 35533d7; CurseForge app and the official launcher from their own support pages (closed source). The same pins as docs/research/v0.4/launcher-steps.md.

## Summary

**Root cause.**
1. RigTune 0.1-0.4 updates a mod by renaming the old jar to `<old>.jar.disabled` and putting the new one at Modrinth's file name, assuming a launcher simply follows `.disabled` renames (docs/DESIGN.md "Apply pipeline").
2. The Modrinth App 0.21 keeps its own row per file plus a project link; for an old (pre-0.21, "unmanaged") row it does follow the rename, so the old version stays linked, disabled, with an update pending to exactly the file name RigTune wrote, while RigTune's jar becomes a second, unlinked row at that name.
3. The app refuses any update whose target file name already has a row ("The updated filename belongs to another content item", `content_mutation.rs:266-278`), Update all stops at the first refusal, and rows are never pruned, so it stays broken until the old copy is deleted **in the app**.

**Recommended design (v0.5).**
1. New `LauncherInfo.modFiles()`: the Modrinth App, the CurseForge app, ATLauncher and GDLauncher keep their own record of the instance's mod files (`LAUNCHER`); Prism/MultiMC, the official launcher and Unknown are `FOLDER` (see §3.7 and §4.2 for why).
2. In a `LAUNCHER` instance RigTune changes **no jar**: Add, Update, Disable, RigTune's own self-update and the Undo of an *applied* mod-file change become advice with that launcher's own click steps (a report transform like `ModrinthOffAdvice`, plus a skip reason in `UndoPlanner`).
3. Everything that isn't a jar stays one-click: vanilla options, Sodium/DH/Iris config patches, Profiles, the benchmark, cancelling RigTune's own staged ops and downloads.
4. An explicit per-instance opt-in, Settings → Mod files → "Let RigTune change them", restores 0.4 behaviour, with honest wording about what it does to the launcher's list.
5. A detection that timed out counts as `LAUNCHER` until it answers; a finished detection with no signal (Unknown) stays one-click as in 0.4.
6. File-op groups left in `pending.json` by 0.1-0.4 are held at exit (the helper runs config patches only) and offered for cancelling.
7. A repair notice built only from RigTune's own records (`history.json` incl. 0.1.0's legacy import, `last-apply.json`, the mods folder) lists the old copies to delete **in the launcher**, with its steps; RigTune never writes another program's data.
8. RigTune stops journaling a jar it found already in place as its own change (`ApplyExecutor.enable`), so a later Undo can't disable a jar the launcher installed.
9. Offline, undoable, no file-format change; 0.4.0 reads everything, and a downgrade to 0.4.0 simply behaves like 0.4.0.
10. For 0.1-0.4 players: one rules warning shown only to old clients (`modVersion` of `rigtune` `<0.5.0-`), plus a known-issue section with the repair steps in the README and on the Modrinth page.

**Per launcher** (details and evidence in §3):

## 1. The Modrinth App: how it tracks an instance's content

Everything here is from modrinth/code **tag v0.21.5, commit 22ccdc1** (paths under `packages/app-lib/src/`), the two read-only DB copies (`pre` = before the user's fix, `post` = after; queried from copies in `scratchpad/r-launchers/db/`), the app's own logs (`%APPDATA%/ModrinthApp/launcher_logs/`, read only) and a bounded, read-only listing of the instance folder and its `config/rigtune/`.

**Version.** `Modrinth App.exe` reports ProductVersion 0.21.5, and the 2026-09-25 09:02 log says "Creating pre-migration app database backup from version 0.21.4 before opening with version 0.21.5". So the user's app was upgraded 0.21.4 → 0.21.5 minutes before RigTune 0.1.0's apply (the helper renames are stamped 2026-09-24 23:09 UTC = 09:09 local). The coordinator's copy of `content_mutation.rs` is byte-identical to the v0.21.5 file.

### 1.1 The data model (two kinds of file row)
- `instance_files` has one row per content file, keyed by `(instance_id, relative_path)`, where `relative_path` is always the **canonical** path (`.disabled` stripped) and `enabled` says which form is on disk (`content_store/domain/paths.rs:92-106`, `file_path_on_disk`).
- `instance_content_entries` links a file row to a Modrinth project/version (`file_id`, `project_id`, `version_id`, `source_kind`, `enabled`). `instance_content_update_checks` caches "the newest version for this entry".
- `store_instance_files` (0.21's new content store) binds a file row to a blob (`materialization_kind` reflink/hardlink/copy). Two kinds of rows follow:
  - **store-managed** rows (a binding exists): everything installed, updated or re-installed **through the app since 0.21**. In this instance: 9 of the 57 mod rows before the fix (ImmediatelyFast, architectury, Entity Culling 1.11.1, Fabric API, Iris, ShulkerBoxTooltip, Sodium, both Xaero maps), all `copy`; 12 of 54 after it.
  - **unmanaged** rows (no binding): everything older, and everything another program put there. 0.21.5 never converts them: `try_shared_file` has its reflink/hardlink body commented out and always returns `None` (`content_store/adapters/filesystem.rs:193-209`), so `can_share_content` is always false (`:340-351`), so every legacy adoption ends `Deferred { "Content links are unavailable in this directory" }` (`instances/commands/content_mutation.rs:145-152`, `migrate_legacy_content.rs:167-175`). The log repeats that warning for every old jar on every start (176× on 09-27). This is 0.21.5 behaviour on every PC, not a quirk of this one.
- Content entries are created **only** by the app's own installs: `upsert_entry_for_file` is called from the Install commit only (`content_mutation.rs:670-681`; its only definition `apply_content_install.rs:747-771`; the only other writer is the whole-instance snapshot restore, `adapters/sqlite/content_rows.rs:777-812`). Nothing creates an entry for a file the app found on disk.

### 1.2 Discovering files another program added
- `sync_instance_content_files` (`instances/commands/sync_content_files.rs:32-338`) runs on every Content-tab load, before every launch (`launcher/mod.rs:1134`), on update checks, and from the file watcher, which queues it for any event under `mods/`, `resourcepacks/`, `shaderpacks/`, `datapacks/` (`instances/watcher.rs:264-277`, `:30-93`).
- It scans only top-level files whose name ends in `.jar` (or `.jar.disabled`) in `mods/` (`instances/adapters/filesystem.rs:27-54`, `:92-111`). So **`*.jar.rigtune-pending`, `*.jar.rigtune-superseded` and `mods/update/` are invisible to the app** (and so is `config/`: the watcher emits nothing for it, `watcher.rs:250-256`).
- A new jar gets a new `instance_files` row (sha1 from the hash cache) and **no content entry** (`sync_content_files.rs:235-283`). DB proof: the 11 files RigTune 0.1.0 wrote on 2026-09-24 23:09 UTC (bbe, moreculling, asynclogger, fastquit, Ixeris, structure_layout_optimizer, ResourcefulConfig, entityculling 1.11.2, modmenu 20.0.3, YACL 3.9.7, zoomify 2.16.3) all have rows with `added_at` = that minute and no entry, still two days later.
- **Linking by hash, for display and updates only.** The Content list takes project/version from the entry, else from the Modrinth hash lookup (`list_content.rs:1242-1255`, `file_metadata_from_entry_or_cache`); that is why the app shows icons for RigTune's jars. The update check runs over **all** file rows by sha1, entry or not, missing or not (`check_content_updates.rs:88-130`); it stores a result only for rows with an entry (`:170-181`) but returns updates for entry-less ones too. So the app does offer updates for RigTune-added jars, and updating one works: the install path renames the row and creates the entry (`content_mutation.rs:633-684`).

### 1.3 `.disabled` renames done by another program
- **Unmanaged row:** followed. `normalize_legacy_content_files` flips the row's `enabled` (path stays canonical) and the entry's `enabled` (`sync_content_files.rs:490-563`). DB proof: `modmenu-20.0.2.jar`, `yet_another_config_lib_v3-3.9.6…jar`, `zoomify-2.16.1…jar` are `enabled=0`, entry `enabled=0`, each with an update check pointing at exactly the version RigTune had installed next to it (`iRo7AZXf`, `DoR7RYgi`, `2Qr8jSFc`).
- **Store-managed row:** not followed. The file status is `Conflict` when the opposite form exists (`content_store/commands/instance_files.rs:38-66`), so the row becomes `missing=1` and stays `enabled=1` (`sync_content_files.rs:179-213`; the repair toggle there only runs for rows that are already disabled). The `.disabled` file itself is skipped with "Ignoring content at the inactive form of a managed path" (`:225-234`); the rename detector needs the same enabled state, so it doesn't match either (`:398-405`). DB proof: `entityculling-fabric-1.11.1-mc26.2.jar` is `copy`-bound, `enabled=1, missing=1`, entry intact, update check `RWjup6Jf` (= 1.11.2); the 09-25 and 09-27 logs warn about its `.disabled` file 2× and 43×; the file is still on disk today. In the app the old Entity Culling simply vanished.

### 1.4 Pruning: never
- A sync only sets `missing=1` (`sync_content_files.rs:288-312`, `content_rows::set_instance_file_missing`); the only row deletion outside whole-instance operations is the app's own **Remove/Delete** (`content_mutation.rs:709-731` → `content_rows.rs:1043`). DB proof: DH 3.2.0 has been `missing=1` since 2026-09-20 (7 days), entityculling 1.11.1 since 09-24, `rigtune-0.1.0.jar` since 09-27; all still there after the fix.
- Missing rows are hidden: the Content list skips them (`list_content.rs:800-802`), and so "Update all", which only updates listed, unlocked items (`apply_content_update.rs:460-483`), never touches them. The install-candidates query ignores them too (`list_content.rs:131-139`).

### 1.5 What the app's own mutations assume (why Update failed)
- **Update / Update all** (`apply_content_update.rs:67-208`): the new file goes to `mods/<Modrinth's primary filename>` (`apply_content_install.rs:461-495`), i.e. exactly the file name RigTune downloads. `prepare_install` then refuses when that path differs from the old one and **any** row, missing or not, is registered at it: "The updated filename belongs to another content item" (`content_mutation.rs:266-278`). RigTune's new jar is exactly such a row. Update all downloads everything, then installs one by one with `?`, so the first collision aborts the rest (`apply_content_update.rs:163-205`).
- An update keeps the old row's enabled state (`content_mutation.rs:279-286`; `apply_content_update.rs:96-102`): updating a disabled old copy gives a disabled new one, which must then be switched on.
- Toggle/remove/install refuse when both `X` and `X.disabled` exist ("Both … exist; resolve the duplicate before continuing", `content_store/commands/file_changes.rs:72-80`), when a store-managed file's bytes changed ("The content file was changed outside the app", `:103-110`; "Content was changed outside the app; resolve the conflict first", `content_mutation.rs:410-414`), or when a file differs from a registered one only in case (`:238-253`). A fresh **install** onto a path that already has a row takes that row over (`:254-260`, `:655-681`), so installing the same version RigTune already put there just links it.
- The app never blocks a launch because of any of this (`validate_instance` is commented out, `launcher/mod.rs:1141`).

So the fix that worked was **deleting the old disabled copy in the app** (one click per mod); RigTune's new jars were kept and still have no entry (the app updates and links them the first time it updates them, §1.2). The two store-managed cases (Entity Culling 1.11.1, DH 3.2.0) never blocked Update all, because their rows were already missing and hidden; they remain as phantom rows with a stray `entityculling-fabric-1.11.1-mc26.2.jar.disabled` on disk (harmless to Fabric, ignored by the app).

**Two secondary findings for the coordinator:**
1. **RigTune now claims a jar the app installed.** `ApplyExecutor.enable` treats "download gone, target present" as done (`src/main/java/.../core/apply/ApplyExecutor.java:674-681`), and the duplicate check only reads jars whose download still exists (`:331-351`). Because the user deleted the `.rigtune-pending` file and the app installed the same file name, `history.json` now lists "enable DistantHorizons-3.3.2…jar APPLIED" in the legacy-import entry. RigTune 0.4.0's **Undo everything** would therefore disable the app's DH 3.3.2 (a store-managed row → it goes missing and vanishes from the app) and disable Entity Culling 1.11.2 (same). v0.5 must not treat "target already there, no rename recorded in `unfinished-groups.json`" as RigTune's own change (proposal in §5.4).
2. Mods' own updaters desync the app too (most likely the DH swap above). Nothing for RigTune to do beyond the existing `Staging.dropQueuedUpdates` rule; worth one README line.

### 1.7 Which external changes are safe (Modrinth App 0.21.5)
| change by another program | effect on the app | verdict |
|---|---|---|
| edit `options.txt`, `config/**` | none (config not watched; options.txt only feeds synced options, §2) | **safe** |
| write `mods/*.jar.rigtune-pending` / `.rigtune-superseded`, `mods/update/` | invisible (not scanned) | safe |
| add a jar | entry-less row; shown with icon via hash; app updates it later by hash, which links it | tolerated (cosmetic; the app can't tell where it came from) |
| rename an **unmanaged** jar to `.disabled` | followed; the old row keeps its entry and its pending update | safe on its own; **fatal next to an added jar at the update's file name** (update pair) |
| rename a **store-managed** jar to `.disabled` | row goes missing, mod vanishes from the app; the `.disabled` file is ignored and later blocks toggles/installs of that path | **desyncs** |
| delete a jar | row goes missing (kept for ever, hidden); a later update *to* that file name is refused | **desyncs** (slowly) |
| RigTune update = disable old + add new under Modrinth's file name | old row (entry, update pending to that exact name) + new row at that name ⇒ **Update / Update all fail** ("belongs to another content item") | **breaks the app** |
| RigTune Undo of that update (rename back) | old row re-enabled, new row disabled; the new row still sits at the update's file name ⇒ still fails | does **not** repair |

RigTune cannot tell a store-managed row from an unmanaged one without reading `app.db`, so v0.5 must treat every jar in a Modrinth App instance as the app's.

## 2. The Modrinth App's synced game options

**Is it on here? No.** Both copies: `sync_feature_settings.game_options` `globally_enabled=0` (new_instance_default 1), `instance_sync_preferences(game_options)=0` for the instance, and every `synced_game_option_*` / `instance_game_option_*` table is empty. Only `screenshots` sync is globally on. The instance's `instance_launch_overrides` blob has hooks and visible tabs but no `force_fullscreen`; the global `mc_force_fullscreen=0`. `%APPDATA%/ModrinthApp/synced-options/` holds only empty `hotbars/` and `servers/` folders, so the folder's existence is not a signal.

**When it reads or writes `options.txt`** (when on; participation = instance preference AND global switch AND a supported game version AND not pending, `api/instance/synced_options/orchestration.rs:1437-1450`, `game_options/write_shared_settings.rs:27-39`):
- **Before every launch from the app:** `launcher/mod.rs:1118-1132` calls `sync_before_launch` (`game_options/launch_overrides.rs:26-37`), which writes every enabled shared value into `options.txt` (`write_shared_settings.rs:178-234`). It doesn't capture the file's current values first, so a change made while the app wasn't watching is **overwritten** for the synced keys.
- **Whenever `options.txt` changes while the app runs** (also while the game runs: game options may apply while running, `synced_options/files.rs:85-94`): the watcher (`instances/watcher.rs:163-181`, `:313-327`) → `reconcile_changed_file` (`orchestration.rs:1137-1186`) → `capture_instance_options` reads the changed values into the shared store and **writes them into every other participating instance** (`write_shared_settings.rs:236-288`, `:306-364`).
- At game exit nothing extra for game options (`reconcile_instance_with_state` skips them, `orchestration.rs:1062-1109`).
- Independently of sync, if "force fullscreen" is set (globally, or per instance), `fullscreen` is written before each launch (`api/instance/run.rs:238-243`, `launch_overrides.rs:42-76`).
- Synced by default when the feature is on (catalog `default_on`, `game_options/catalog/video.rs`): `graphicsPreset/graphicsMode`, `ao`, `gamma`, `fov`, `guiScale`, `particles`, `renderClouds`, `entityShadows`, `bobView`, `enableVsync`, `fullscreen`, `maxFps`, `inactivityFpsLimit`, `biomeBlendRadius`, `prioritizeChunkUpdates`, `cutoutLeaves`, `improvedTransparency`, `vignette`, … and every unknown key discovered in an options.txt (`read_instance_changes.rs:343-353`). **Not** by default: `renderDistance`, `simulationDistance`, `entityDistanceScaling`, `mipmapLevels`, `textureFiltering`, `maxAnisotropyBit`, `cloudRange`, `weatherRadius`, `chunkSectionFadeInTime` (the player can switch each on). Modpack updates are written to keep game settings (`game_options/pack_updates.rs:1`); not traced further.

**Consequences for RigTune** (only when the player has turned it on):
1. RigTune's settings change (and its Undo) is written by Minecraft into `options.txt`; with the app open it is captured and **copied to every other synced instance**, which RigTune doesn't journal there.
2. If the app was not running when the file changed, the next launch from the app puts the shared values back: a silent revert of RigTune's change (or of its Undo) for the synced keys.
3. RigTune's History/Undo stays consistent inside the instance (it journals before/after), but "you changed it since" will fire if the app overwrote a key.

**What RigTune must do:** nothing that touches the app's data. RigTune cannot see the switch without reading `app.db`, which it must not. v0.5 should (a) on start, compare the vanilla keys of its newest applied entries with `options.txt` and, when several were put back to their *before* values by something else, show one notice: "Some settings RigTune changed were put back by something outside the game. In the Modrinth App, game settings sync can do this: App settings → Synced settings → Sync game options, or this instance's settings → Sync overrides → Unsync game settings." (labels from `apps/app-frontend/src/locales/en-US/index.json`: `app.settings.tabs.synced-options`, `app.settings.synced-options.game-settings`, `instance.settings.tabs.settings-overrides`, `instance.settings.tabs.synced-options.game-settings`); (b) say once, in the Modrinth App's settings help, that changes to synced options apply to every synced instance. It is not P0 for this user (off); **UNVERIFIED** end to end (not exercised in a live app).

## 3. Other launchers

Read from source at the pins in the header (Prism/MultiMC/PolyMC and ATLauncher/Carbon files fetched or sparse-cloned into `scratchpad/r-launchers/sub-*`; CurseForge and the official launcher are closed source, so only their own support pages). What RigTune does in each case: add = new `<n>.jar`; update = `<o>.jar` → `<o>.jar.disabled` + new `<n>.jar` (Modrinth's name); disable = `<x>.jar.disabled`; Undo = the reverse renames.

### 3.1 Prism Launcher 11.1.0 (ea87ffc): tolerant
- **Record:** optional packwiz metadata `mods/.index/<slug>.pw.toml` written by its downloader/updater: `name`, `filename`, `side`, `[download] url, hash-format, hash`, `[update.modrinth] mod-id, version` or `[update.curseforge] file-id, project-id` (`launcher/modplatform/packwiz/Packwiz.cpp:175-240` write, `:295-360` read; file name from the slug, `:62-73`).
- **Files it didn't install:** listed with status `NO_METADATA` (`launcher/minecraft/mod/tasks/ResourceFolderLoadTask.cpp:70-92`). **Check for Updates** first creates metadata for them by hash (Modrinth, then CurseForge: `ui/dialogs/ResourceUpdateDialog.cpp:305-380`, `modplatform/EnsureMetadataTask.cpp`), then updates them. So RigTune's jars become Prism-managed on the first update check.
- **`.disabled`:** Prism's own convention (`minecraft/mod/Resource.cpp:52-56` parse, `:225-250` toggle). A `.disabled` file is matched to its metadata through the name without the suffix (`ResourceFolderLoadTask.cpp:93-105`), so a jar RigTune disabled shows as disabled with its metadata.
- **Pruning:** metadata whose file is gone is deleted on the first folder load after the Mods page starts watching (`ResourceFolderLoadTask.cpp:113-124`, `ResourceFolderModel.cpp:61-63`).
- **Its update on RigTune's pair:** downloads the new version straight to `mods/<Modrinth filename>` (overwriting RigTune's identical copy), rewrites the slug's metadata, then uninstalls the old file, matching the `.disabled` form (`launcher/ResourceDownloadTask.cpp:74-120`; `ResourceFolderModel.cpp:210-228`). No refusal, no duplicate in the normal case. Edge case: RigTune's new jar and the old disabled copy share one slug file, so which one Prism links first depends on the order of the update dialog (**UNVERIFIED**, no failure path found).
- **Its own rename:** at load, when both `x.jar` and `x.jar.disabled` exist, Prism renames the disabled one to `x.jar.duplicate…` (`launcher/FileSystem.cpp:1680-1705`, called from `ResourceFolderLoadTask.cpp:74-80`). Harmless for Fabric; RigTune's journal then can't find that `.disabled` file and Undo skips it (FILE_GONE), which is the safe side.
- **options.txt/config:** nothing found that writes them at launch or exit (**UNVERIFIED**: not searched beyond the mod code).
- **Steps (labels from `ExternalResourcesPage.ui`/`ModFolderPage.cpp`, `MainWindow.ui`):** right-click the instance → **Edit...** → **Mods** → select → **Remove** / **Enable** / **Disable** / **Check for Updates**.
- **Verdict:** RigTune's renames don't break Prism: its records self-heal and its updater tolerates them. `FOLDER`.

## 4. Recommended design: "RigTune never fights the launcher"

### 4.1 The rule
When the detected launcher keeps its own record of the instance's mod files (§3 table: **Modrinth App, CurseForge app, ATLauncher, GDLauncher**, plus the Prism/MultiMC-family decision below), RigTune changes **no jar** unless the player has opted in for this instance: every Add, Update and Disable recommendation, RigTune's own self-update, and the Undo of an *applied* mod-file change become advice with that launcher's click steps. Settings (vanilla options, Sodium/DH/Iris config patches, profiles, benchmark) stay one-click: no launcher tracks them (§1.7, §3). RigTune's own files (`pending.json`, `*.rigtune-pending`, `*.rigtune-superseded`, `config/rigtune/**`) are invisible to every launcher checked, so cancelling staged work stays one-click too.

### 4.2 Launcher classes
`LauncherInfo.modFiles()` (new, core, pure): `LAUNCHER` for MODRINTH_APP, CURSEFORGE, ATLAUNCHER, GDLAUNCHER; `FOLDER` for OFFICIAL and UNKNOWN; PRISM and MULTIMC per §3's verdict (recommendation: `FOLDER` with a per-launcher caveat, see §3.7). A **timed-out** detection is not Unknown: LauncherProbe gets a separate "not known yet" result, and until the real answer arrives RigTune treats the instance as `LAUNCHER` (mod-file items shown as advice, no Apply of them); the next rebuild after detection lifts it. Only a completed detection with no signal is Unknown.

**Unknown defaults to `FOLDER` (one-click, as in 0.4).** Why: (1) every launcher we know to keep a per-file record is detected from a signal it always sends (the Modrinth App's `theseus` brand, ATLauncher's and GDLauncher's brands, CurseForge's `minecraftinstance.json`), and a timeout is handled above; (2) what's left (the dev environment, HMCL, SKLauncher, TLauncher, PojavLauncher, scripts) runs the game from a plain folder as far as we know (UNVERIFIED for each); (3) `FOLDER` keeps every existing test and the 0.4 behaviour for those players. The alternative (Unknown → advice) costs those players one-click mod changes to guard against launchers nobody has named; say so as a coordinator decision.

### 4.4 Offline, undoable, compatible
- **Offline:** the decision uses only the launcher probe (local) and settings.json; with Modrinth off, `ModrinthOffAdvice` still runs after `LauncherModAdvice` and finds nothing left to change; the steps need no network.
- **Undoable:** v0.5 in a `LAUNCHER` instance only writes settings (journaled as today) and cancels its own staged ops (journaled DISCARDED as today). No new journal kind, no new status.
- **0.1.x-0.4.x files:** read as today; nothing in `history.json`, `pending.json`, `last-apply.json`, `unfinished-groups.json` changes format. `settings.json` gains one optional field; 0.4.0 ignores it and drops it when it rewrites the file, which turns the opt-in off, the safe side (the same pattern as `stutterMonitor`, `ClientSettings.java` comment). A downgrade to 0.4.0 **does** apply held file ops at its next exit and offers file changes again (0.4's behaviour); state that in the changelog. `-Drigtune.helper.holdFileOps` is only read by the 0.5 helper, which always runs from a copy of the current jar (`HelperLauncher`).

## 5. Repair for players already in this state

### 5.1 What RigTune can know from its own records (never another app's DB)
- `history.json` (0.2+; the 0.1.0 apply arrives as the `legacy-import` entry, `LegacyImport.java`; this instance has exactly that entry with 17 file changes) gives, per group: DISABLE (`file`, `resultFile`) and ENABLE (`file`, `modId`) changes with status APPLIED; `last-apply.json` gives the helper's per-op outcome; `pending.json` the still-staged groups; `unfinished-groups.json` the renames 0.4+ actually did.
- The mods folder (RigTune's own `Folder`/`JarInfo`) tells which of those files still exist and which mod id each jar declares.
- **Update pair still in effect:** an APPLIED group with one DISABLE `o` and one ENABLE `n` of the same mod id (legacy-import disables have `modId` null here, e.g. "disable None modmenu-20.0.2.jar": read the `.disabled` jar's id), where `resultFile(o)` (or `o.jar.disabled`) **and** `n` are both in `mods/`. That is exactly the state that breaks the Modrinth App's Update all when `o`'s row is unmanaged. RigTune can't tell unmanaged from store-managed; the steps cover both.
- **Added jar:** an APPLIED ENABLE without a DISABLE in its group, still present (not RigTune itself). Harmless in the Modrinth App (§1.2).
- **Disabled-only:** an APPLIED DISABLE whose `.disabled` file exists. Harmless when unmanaged; a store-managed one has vanished from the app.
- Changes whose file is gone (the player already deleted them in the app, as here for modmenu/YACL/zoomify) count as repaired.
- **This instance today:** one pair still in effect (Entity Culling: `…1.11.1-mc26.2.jar.disabled` + `…1.11.2-mc26.2.jar`, but 1.11.2 is now the app's own reinstall and 1.11.1's row is store-managed, hidden: nothing to do in the app); 7 adds (nothing to do); the DH group is "applied" in history although the app installed that jar (§1.6 finding 1).

### 5.2 The notice (only in a `LAUNCHER` instance, only while something is in effect)
Title: "Mod changes from an older RigTune: help the Modrinth App catch up". Body for pairs: "RigTune changed these mods without the Modrinth App. If the app's Update or Update all fails with "The updated filename belongs to another content item", do this **in the app** (not in File Explorer: the app keeps its own list): open this instance → **Content** → filter **Disabled** → select the old copy → **Delete**: <o₁>, <o₂> … RigTune's newer versions stay and keep working. If an old copy isn't listed, the app has already hidden it: nothing to do." Adds: "RigTune also added: <n₁> … The app lists them as your own files and will update them itself; nothing to do." Buttons: **Copy list** (clipboard, file names only), **Dismiss** (per set of pairs, stored in `awareness.json`'s dismissed ids, the existing notice mechanism).
- Why "delete the old copy" and not "delete the new one, update the old one, switch it on": it is one step per mod, it is what fixed this instance (§1.6: Update all succeeded at 10:28:34 right after), and it keeps the version RigTune installed. The other order also works (the update keeps the disabled state, `content_mutation.rs:279-286`, so it needs the extra "switch it on"); give it as the alternative for players who want the app to own every file.
- Labels: "Content" (`app.instance.tab.content`), "Disabled" filter (`content.filter.disabled`), "Delete {itemType}" (`content.confirm-deletion.header`), "Update all" (`content.page-layout.update-all`), "Upload files" (`content.page-layout.upload-files`) from `apps/app-frontend` and `packages/ui` `locales/en-US/index.json` at v0.21.5. The row's own delete control is an icon; its tooltip text was not found in the locale files (**UNVERIFIED**; hence "select → Delete", which uses the verified selection bar).
- Other launchers get the same notice with their own steps from §3, only where §3 says their state breaks.

### 5.3 What RigTune does itself: only its own files
- **Stale `.rigtune-pending` downloads and held groups:** offered for cancelling (4.3 "Exit / helper"). They are invisible to the app (§1.2), so this is housekeeping, not repair.
- **Pending groups for mods the launcher has since installed or updated:** the helper already abandons a group when another jar declares the mod id (`ApplyExecutor.java:331-351`); v0.5 holds them anyway in a `LAUNCHER` instance.
- **Not** renaming, moving or deleting the old `.disabled` copies itself. It would unblock Update all (a moved-away unmanaged row goes missing and hidden, §1.4) but leaves phantom rows, is again RigTune changing mod files behind the app's back, and can't be done while the app is in the middle of a sync. Coordinator decision if wanted: an explicit button "Move RigTune's old disabled copies to config/rigtune/moved-mods/", journaled and undoable.
- **Never** touching `app.db` or any launcher's metadata.

### 5.4 Stop claiming jars RigTune didn't put there
In `ApplyExecutor.enable` (`:674-681`) "download missing, target present" is recorded as `SKIPPED_ALREADY_DONE`, so a jar the launcher installed under the same file name becomes an APPLIED RigTune change (this instance: DH 3.3.2). Verified consequence with `UndoPlanner.move` (`:806-832`): 0.4.0's **Undo everything** here would disable the app's Entity Culling 1.11.2 and re-enable 1.11.1 (both files exist), which re-creates the update collision (1.11.1's row becomes healthy again with its update to 1.11.2's file name, while 1.11.2's store-managed row goes missing); the DH group is skipped only because `fabric-26.2.jar` is gone. Proposal: when `unfinished-groups.json` has no rename record for the op (0.4+ records every rename before doing it), report it as ABANDONED "already there, not RigTune's" (History: "Not applied"), and never journal it APPLIED. Needs a check against the L2 crash-safe replay for 0.2/0.3 runs (they had no rename record); ask the apply-pipeline owner.

## 6. Players who never update (0.1.x-0.4.x)

What the rules can and cannot do (from `docs/RULES_SCHEMA.md`, the pinned v0.1.0 copy under `src/test/java/.../v010/`, `rules/rules-v2.json` revision 16):
- **Updates: nothing honest.** 0.1.x offers every Modrinth update, ticked, whatever the rules say (`v010/core/recommend/Recommender.java:211-231`). 0.2-0.4 have `skipUpdateWhen` (v2), but only for mods that have a ModRule (28 of them), and the client then shows "<mod> updates itself: Its own auto-updater is on" (`Recommender.java:410-416`), which would be false. Don't.
- **Additions: can be unticked.** `defaultSelected: false` on every ModRule (v1 and v2) keeps them offered but unticked in 0.1-0.4 (`v010 Recommender.java:204`; RulesV1DifferentialTest allows "ticks none that was unticked"). It would untick them in 0.5 too, for every launcher; adds are also the least harmful change in the Modrinth App (§1.7). Not recommended.
- **There is no launcher condition** (no key or flag tells rules which launcher runs the game; `RULES_SCHEMA.md` Condition table), so nothing can target Modrinth App players only.
- **What works: one warning, shown only to old clients.** An AdviceRule, kind `warning`, `when: {"modVersion": {"rigtune": "<0.5.0-"}}` (a legacy-v2 key, known to 0.2.0+ per `tools/update_rules.py:71-73`; FALSE on 0.5.0 and its pre-releases), with a `v1` override `{"when": {"always": true}}` for 0.1.x (which can only be below 0.5). Text (English literal, keep it short): "Using the Modrinth App, CurseForge app, ATLauncher or GDLauncher? Untick RigTune's Install, Update and Disable items and make those changes in the launcher: RigTune's mod-file changes can make the launcher's Update all fail. Already happened? In the Modrinth App: Content → Disabled → delete the old copies. RigTune 0.5 handles this for you." More conservative for v1 (an advice, no appliable change). **Needs a test** that 0.2.0/0.3.0/0.4.0 read `modVersion` of RigTune itself (ModScanner must list `rigtune` with its version; **UNVERIFIED** for the pinned old copies) before it ships.
- `minModVersion: "0.5.0"` shows "Update RigTune" (MEDIUM) on 0.1-0.4 with a generic reason (`Recommender.java:465-474`, `v010 :306-311`). Reasonable once 0.5.0 is out; note that RigTune's own self-update in a Modrinth App instance makes the same kind of pair for `rigtune` itself.
- **README / Modrinth listing (known issue):** "RigTune 0.1-0.4 in the Modrinth App (and other launchers that keep their own mod list): when RigTune updated or added mods, the app's Update / Update all can fail with "The updated filename belongs to another content item". Fix: in the Modrinth App open the instance → Content → Disabled → delete the old copies of the mods RigTune updated (RigTune's new versions stay). Don't delete files in File Explorer: the app keeps its own list. RigTune 0.5 no longer changes mod files in these launchers; it tells you what to change there." Plus the §1.6 DH note: mods that update themselves (Distant Horizons' auto-updater) can cause the same.

## 8. Decisions for the coordinator
