## 1. Self-update E2E on both 26.2 and 26.3

### 1.1 How the harness launches the game today (Windows-only assumptions)

`tools/e2e/self_update_e2e.py`, main checkout:
- `preflight` (`:886-893`) refuses anything but Windows and needs PowerShell 7.
- **Process list:** `java_processes` (`:181-192`) runs `pwsh Get-CimInstance Win32_Process`.
  - A process counts as this run's only when its command line contains the run folder's unique name (`:196`).
  - `kill_own` uses `taskkill /PID /F` (`:199-202`), one process at a time, never a tree.
- **Helper command lines:** `start_watcher` (`:492-502`) runs a `pwsh` loop every 200 ms. It records every `ApplyHelper` command line, which the classpath check (AC5.2) needs. `after_update` parses it with the default `;` separator (`e2e_checks.py:83`).
- **Gradle:** `gradle()` (`:167-179`) runs `cmd /c gradlew.bat` (it already falls back to `./gradlew` elsewhere).
  - The game is Loom's `ClientProductionRunTask` `:<mc>:e2eClient` (build.gradle `:437-456`): a production client on the scratch instance, `mods` = the driver jar only, JVM args from a file, 1280x720.
- **Fake Modrinth:** `java FakeModrinth.java`, a JDK-only HTTPS server, on 127.0.0.1 port 443 (`--port` default 443).
  - The game reaches it through `-Djdk.net.hosts.file` (e2e_env.py `:29-38`). Only api.modrinth.com, cdn.modrinth.com, raw.githubusercontent.com, localhost and the machine name resolve, all to 127.0.0.1, so Mojang is offline.
  - TLS: a keytool self-signed certificate with SANs for the three hosts and a PKCS12 truststore passed as `-Djavax.net.ssl.trustStore*` (`:41-74`).
  - `RedirectProbe.java` checks all of it before the first launch.
- **Seeded run:** `run_update` (`:578-587`) holds `mods/fabric-26.2.jar` open from the old version's launch until its helper is done.
  - Windows opens it without `FILE_SHARE_DELETE`, so the helper's rename fails with a sharing violation, like DH's updater did in the real failure.
  - Linux has no equivalent: an open handle doesn't block a rename.
- **Lock:** `DEFAULT_LOCK = "C:/Dev/Worktrees/.gametest-lock"` (`:36`).

### 1.2 What Linux CI needs (each item measured on ubuntu-24.04)

- **Xvfb comes free.** Loom 1.17.21 (what `loom_version=1.17-SNAPSHOT` resolves to, `./gradlew buildEnvironment`): its `ClientProductionRunTask` wraps the game in `xvfb-run -a` when the `CI` variable is set on Linux.

- **Harness Linux path** (commit 25243b63):
  - `posix_java_processes()` reads `/proc/*/cmdline`; `kill_own` sends SIGKILL; the helper watcher is a Python thread with the same 200 ms poll and file format.
  - `after_update(..., separator=os.pathsep)`.
  - The seed's hold becomes `sudo -n chattr +i` from the old launch until the helper is done, then `chattr -i`.

That is the same outcome the Windows sharing violation gives, and the same classifier path in 0.4+ (`ApplyExecutor.isSharingViolation`: any plain `FileSystemException`).
- **26.3 under Xvfb** needs `SDL_OPENGL_FORCE_SRGB_FRAMEBUFFER=skip` (as build.yml sets it for the GL legs).
- **Log filter** (commit 1f4b6b3a): the downgrade checks (`rigtune_log_problems`) failed on Linux only, on these lines:

  - `HARMLESS_ERRORS` gained the first two. The cursor block is dropped only when the third line is that X11 message, so any other GL ERROR still fails the check (unit-checked).
- **Released jars:**
  - `RELEASED` and build.yml's pins gained `0.2.0+mc26.3` `98a2a2e1…a7d9`, `0.3.0+mc26.3` `cc43ebdf…8084`, `0.4.0+mc26.2` `801cd3b8…868a` and `0.4.0+mc26.3` `2d8328d7…99a7` (digests from `gh release view`).

- Nothing else differs: the drivers are portable (one `replace('\\', '/')`), `HelperLauncher` picks `java` or `java.exe` by `File.separatorChar`, and evidence paths are scrubbed the same way. RESULT.md's "Held open" sentence should name the hold mode (it still quotes the Windows reason on Linux).

### 1.5 The honest 26.3 equivalent of "seeded"

The seed is the user's real 0.1.0 state on 26.2: `pending.json` and `last-apply.json` read from their instance
(`seeds/v010-dh/source.json`). No real 26.3 state exists: 0.1.0 has no 26.3 build, and the user plays 26.2. The real
instance hasn't been played since 2026-09-25 (docs/v0.4/verification/real-instance.md).

The honest equivalent is a **generated seed**: the same failure shape, written by the released oldest 26.3 jar itself,
never by hand. A new harness option `--generate-seed` (phase `seed`):
1. Fresh instance: `rigtune-0.2.0+mc26.3.jar`, fabric-api and a fake DH 3.3.0 as `mods/fabric-26.3.jar`.
2. The fake Modrinth serves a fake DH 3.3.2 as its update. The self-update driver applies only that recommendation.
3. The harness holds `fabric-26.3.jar` (`chattr +i`, or open on Windows), so the 0.2.0 helper fails the group and keeps
   it pending at attempt 1 of 3.
4. A fake DH-updater jar goes into `mods/update/…/`, as in `seed.json`.

Then the normal seeded `update` and `verify` phases run: the old side updates RigTune while the group fails again, and
0.5.0 drops the group with the notice (3a), marks its journal entries DISCARDED and logs the per-op WARN (3e). RESULT.md
must label it "state generated by rigtune-0.2.0+mc26.3 (sha256 98a2a2e1…), not a real user's".

Run the same generator on 26.2 from 0.4.0: most people updating to 0.5 will come from 0.4.0, and the real 0.1.0 seed
doesn't cover 0.4's journal and `unfinished-groups.json`.

### 1.7 Design: files, job shape, time budget

Files:
- `tools/e2e/self_update_e2e.py`, `tools/e2e/e2e_checks.py`, `tools/e2e/tests/test_e2e_v04.py`, and build.yml's pins: take
  commits 25243b63 and 1f4b6b3a from `research/v05-verify` (not the experiment workflow).
- `tools/e2e/e2e_matrix.py` (new, like `tools/gametest_matrix.py`): one table of scenarios. It prints the GitHub matrix for
  `--tier push|release`, with old jars and sha256 taken from `RELEASED`, so there is a single source of pins.
  - Unit test: every `RELEASED` entry is used, and the node list is derived from `versions/*/`, so a new node gets its legs.
- `.github/workflows/e2e.yml` (new, reusable, `workflow_call` + `workflow_dispatch`).
- build.yml: one new job, `e2e`.
- release.yml: split into three jobs.

```yaml
# .github/workflows/e2e.yml (shape)
on:
  workflow_call:
    inputs:
      tier: { type: string, required: true }        # push | release
      jars-artifact: { type: string, required: true } # the jars built earlier in the calling run
  workflow_dispatch:
    inputs:
      tier: { type: choice, options: [push, release], default: release }
jobs:
  matrix:
    runs-on: ubuntu-24.04
    outputs: { matrix: "${{ steps.m.outputs.matrix }}" }
    steps:
      - uses: actions/checkout@v7
      - id: m
        run: echo "matrix=$(python3 tools/e2e/e2e_matrix.py --tier '${{ inputs.tier }}')" >> "$GITHUB_OUTPUT"
  e2e:
    needs: matrix
    name: e2e ${{ matrix.id }} (${{ matrix.mc }})
    runs-on: ubuntu-24.04            # pinned like the game-test legs
    timeout-minutes: 20
    strategy: { fail-fast: false, matrix: "${{ fromJSON(needs.matrix.outputs.matrix) }}" }
    env: { SDL_OPENGL_FORCE_SRGB_FRAMEBUFFER: skip, GH_TOKEN: "${{ github.token }}" }
    steps:
      - checkout, setup-java 25 (microsoft), gradle/actions/setup-gradle
      - uses: actions/download-artifact@v7   # the exact bytes CI built (or release.yml staged); no rebuild
        with: { name: "${{ inputs.jars-artifact }}", path: "${{ runner.temp }}/jars" }
      - run: gh release download "${{ matrix.tag }}" -p '${{ matrix.asset }}' -D "$RUNNER_TEMP/jars"  # skipped for undo
             && echo "${{ matrix.sha256 }}  $RUNNER_TEMP/jars/${{ matrix.asset }}" | sha256sum -c -
      - run: sudo sysctl -w net.ipv4.ip_unprivileged_port_start=443
      - run: python3 tools/e2e/self_update_e2e.py --lock none --mc "${{ matrix.mc }}" --name "${{ matrix.id }}"
             --new-jar <jar from the artifact> ${{ matrix.args }} --work "$RUNNER_TEMP/e2e"
             --evidence "$RUNNER_TEMP/evidence/${{ matrix.id }}"
      - if: always()   # RESULT.md, checks.json, screenshots, e2e.log, gradle-*.log, instance*/logs, crash-reports
        uses: actions/upload-artifact@v7
```

- **build.yml:**
  ```yaml
  e2e:
    needs: java
    uses: ./.github/workflows/e2e.yml
    with:
      tier: ${{ github.event_name == 'pull_request' && github.base_ref == 'main' && startsWith(github.head_ref, 'feat/v') && 'release' || 'push' }}
      jars-artifact: rigtune-jars
  ```
  The java job already uploads `rigtune-jars`.
- **release.yml** becomes three jobs:
  - `build`: today's steps up to staging `release-files`, uploaded as an artifact.
  - `e2e`: `uses: ./.github/workflows/e2e.yml`, tier `release`, `jars-artifact: release-files`.
  - `publish`: `needs: [build, e2e]`; downloads `release-files`, creates the GitHub release, publishes to Modrinth, verifies.
  - The published bytes are then the E2E-tested bytes by construction (section 5 explains why a rebuild isn't).
- **Time budget:**
  - Push tier: 2 jobs × about 2 min of runner time, finished long before the 8.5 min game-test legs.
  - Release tier: about 17 jobs (7 upgrades, 1 real seed, 2 generated seeds, 4 undo, 2 downgrade, 1 helper-kill): about 55 runner-minutes. Wall time is about 6-7 min, bounded by the 5.5 min undo+profiles legs and 20 concurrent jobs on a public repo.
  - Local Windows: one run (seeded, real handle), about 2 min under one lock hold.

### 1.8 Local runs and vanilla 26.3's native startup crash

Locally, production 26.3 clients die before "OpenAL initialized":
- `NTSTATUS 0xC0000005`, once `0xC0000374`.
- 6 of 7 RigTune launches, and 3 of 5 launches of a control with no RigTune and no harness (docs/v0.3/verification/README.md finding 6; docs/v0.4/verification/smokes/26.3-modrinth/README.md).
- `ALSOFT_DRIVERS=null` helped in 2 of 3 tries, not always.

Policy for any local 26.3 client:
- Set `ALSOFT_DRIVERS=null`.
- Classify a launch as an environment crash when all of these hold:
  - gradle exits non-zero;
  - the JVM exit value is -1073741819 or -1073740940, or no `hs_err` is written;
  - `latest.log` has no "OpenAL initialized"/"Sound engine started".
- Then restart the whole scenario from a fresh instance (a crash mid-phase can leave staged state), up to 5 attempts, each listed in RESULT.md.
- Recommendation: don't run the 26.3 E2E locally at all. CI covers it.

Linux CI avoids the crash because the crash window is never reached there:
- Under Xvfb there is no audio device. The 26.3 E2E log shows `Error starting SoundSystem. Turning off sounds & music / java.lang.IllegalStateException: Failed to open OpenAL device`, so the sound engine never starts.
- It renders on Mesa llvmpipe, not the AMD driver.
- The 26.3 game-test legs have been green across all recent runs.

The honest corollary: CI says nothing about that Windows crash. It isn't RigTune's: the control without RigTune
crashes too.

### 1.9 Interactions with r-ci

- The E2E needs no live network: FakeModrinth serves the jars and rules. Its only external inputs are:
  - `gh release download` of pinned, sha256-checked jars;
  - the Gradle cache, which needs Sodium from maven.modrinth for the profile legs.

## 2. The LAN-guest path (AC8.5), and Realms

### 2.1 How RigTune classifies a connection

`client/server/ServerLimitsTracker.java`:
- `kind()` (`:144-152`): `SINGLEPLAYER` when `minecraft.hasSingleplayerServer()` (the player's own world, Open to LAN or not), else `REALM` when `data.isRealm()`, else `LAN_GUEST` when `data.isLan()`, else `REMOTE`.
- `address()` (`:154-167`): a LAN guest is keyed by host only (`ServerLimitsStore.lan(host)`), because "an Open-to-LAN game gets a new random port each time". A Realm is keyed `realm(name)`.

Where the type comes from (javap of the 26.2 client jar; the four facts marked * re-checked on 26.3, same result):
- (*) `ServerData.Type.LAN` is set in exactly one place: `ServerSelectionList$NetworkServerEntry.join()` does `new ServerData(motd, address, ServerData.Type.LAN)` and then `JoinMultiplayerScreen.join(ServerData)`. So only a click on a server in the LAN list makes a LAN guest.
- The gametest API's `TestDedicatedServerContext.connect()` builds `ServerData.Type.OTHER` (fabric-client-gametest-api-v1 6.0.8, `lambda$connect$0`). That's why today's ServerLimitsGameTest covers only REMOTE.
- LAN discovery: `LanServerDetection$LanServerDetector` joins multicast group `224.0.2.60` on port 4445 (`MulticastSocket(4445)`, `joinGroup`). `LanServerList.addServer` builds `sourceHostAddress + ":" + port` from the ping.
- (*) The pinger is public: `LanServerPinger(String motd, String serverAddress)` with `MULTICAST_GROUP = "224.0.2.60"`, `PING_PORT = 4445` and a 1500 ms interval. `IntegratedServer.publishServer` starts exactly `new LanServerPinger(getMotd(), Integer.toString(port))`.
- (*) `IntegratedServer.initServer` calls `setUsesAuthentication(true)` (javap). So a real Open-to-LAN host checks the guest's Mojang session. An offline test client can't join one, and two clients on this PC would also break the one-client rule.

### 2.2 The test: `LanGuestGameTest` (gametest source set; every CI leg and local)

### 3.2 Design

**(a) `BatteryFlowGameTest`** (every CI leg, local too; no product change):
- A fake `PowerWatcher.Battery` backed by an `AtomicBoolean` (deviceName "RigTune test battery", chemistry "Li-ion", capacities 100/100, so `realBattery` accepts it).
- Started with the real `PowerWatcher.start(List.of(fake), false, service::powerChanged, executor, 1)` on a single-thread scheduled executor named like the product's.
- Steps:
  1. Flip to discharging. Within 5 s (two 1 s polls): the Battery notice with actions [switch, snooze], nothing switched.
  2. The toast is present: `mc.gui.toastManager().getToast(SystemToast.class, <battery toast id>)`. `ToastManager.getToast(Class, Object)` exists on 26.2 and 26.3 (javap).
  3. Take the offer: Battery active, 60 FPS.
  4. Flip to AC: the back-offer names the previous profile. Take it: the previous profile is active.
- Variants:
  - a wiggle shorter than the debounce: no edge;
  - no active profile before Battery (PF-1, after its fix: the back-offer targets My settings);
  - snooze;
  - a 10-minute cooldown, via a `lastPromptAt` fixture;
  - a benchmark running: no offer;
  - a listener exception doesn't stop the polls.
- The only product-visible change is making the toast id reachable (`public static final SystemToastId BATTERY_TOAST_ID`), or reading it by reflection in the test. Behaviour is identical.

**(b) Linux release-tier leg with real OSHI:**
- The runner kernel has no `test_power` module: `modprobe: FATAL: Module test_power not found in directory /lib/modules/6.17.0-1022-azure`, even after `linux-modules-extra`.
- What works instead (measured, run 36288792339):
  - `sudo mount -t tmpfs -o mode=0777 tmpfs /sys/class/power_supply` with a hand-written `BAT0/uevent`.
  - OSHI 6.9.0, the game's version, sees 0 sources by default: its udev enumeration ignores the tmpfs.
  - With `-Doshi.os.linux.allowudev=false` OSHI reads the file: `BAT0 | device=RigTune fake battery chemistry=Li-ion max=5000000 … discharging=false charging=true`. After the test rewrote `STATUS=Discharging`, the same objects' `updateAttributes()` gave `discharging=true`, and RigTune's `realBattery` = true, `onBattery` = true. Back to `Charging` gave `onBattery` false.
  - `isPowerOnLine()` is always false for a Linux battery entry (it has no ONLINE key), so on Linux `onBattery` follows `isDischarging()`. That matches the product code's `!powerOnLine && discharging`.
- In game (run 36289370916): with that mount (`STATUS=Discharging`) and `--jvm-arg=-Doshi.os.linux.allowudev=false`, the production client's own startup probe logged `hasBattery=true, onBattery=true` (the Hardware line), and the self-update scenario still passed 20/20.
- The leg:
  - runs the gametest with `-Drigtune.gametest.fakeBattery=/sys/class/power_supply/BAT0/uevent` (set only there);
  - asserts `PowerWatcher.isRunning()`;
  - rewrites STATUS and waits for the real 30 s polls: about 60-90 s per edge, about 4 min for AC → battery → AC.
- It covers `startIfBattery`, the OSHI adapter and the real thread.
- Caveats:
  - `allowudev=false` moves all of OSHI's Linux reads to sysfs files. A real Linux laptop goes through udev: same OSHI `PowerSource` fields, but a different enumeration path.
  - The JVM argument exists only on this CI leg.

**(c) A real laptop** (manual, the one thing CI can't do):
- A Windows laptop with a 0.5.0 build: unplug, then the notice and toast within about 60 s. Take it, plug in, get the back-offer.
- 10 minutes for whoever owns a laptop (this PC is a desktop; OSHI reports only the fake "System Battery", which `realBattery` filters).
- UNVERIFIED until someone does it: Windows `WindowsPowerSource` (SetupAPI/IOCTL) state changes on unplug, and the poll cost on a laptop.

Unit tests to add (PowerWatcherTest/BatteryPromptTest):
- an update() that fails on every battery doesn't count as AC;
- two batteries, one discharging, count as on battery;
- a wiggle within the debounce produces no edge;
- `stop()` before the startup probe completes means `startIfBattery` starts nothing;

### 4.3 What parses wrong, and what stays UNKNOWN when it arguably shouldn't

**Wrong: R1 and R2**, AMD's legacy-branch strings `Context 22.20.x.YYMMDD`:
- `ADRENALIN` (`DriverVersionParser.java:23`, `\bContext\s+(\d{1,3})\.(\d{1,2})\.(\d{1,2})\.\d{1,9}`) reads them as Adrenalin 22.20.24 and 22.20.44.
- Month 20 isn't a month. R2's Windows driver is 31.0.12044.3: `22.20.x` is AMD's internal branch number, which Ryzen/Vega iGPUs on the legacy driver still report in 2026. These are the low-end laptops RigTune targets.
- Impact today: low. There is no AMD driver rule, and the change notice would just print 22.20.24 → 22.20.44. A future `driverVersion {vendor: amd, …}` rule would compare nonsense.
- **Fix:** restrict the month, `\bContext\s+(\d{1,3})\.([1-9]|1[0-2])\.(\d{1,2})\.\d{1,9}(?![.\d])`.
- Tried in the worktree and reverted: R1 and R2 become UNKNOWN, no other vector changes, and `DriverVersionParserTest`, `ConditionEvaluatorDriverVersionTest` and `ChangeDetectorTest` pass.
- Add R1-R4 as vectors.

**UNKNOWN by design, keep:**
- Row 22, Intel Windows Vulkan `Intel Corporation 101.8861`: the driverInfo is the last two parts of the GL build (`… - Build 32.0.101.8861`), which isn't comparable with the GL form's four parts.
  - The existing assertion `1.3.296 Intel Corporation 101.5595` is UNKNOWN, and the real shape confirms the guess.
  - The v0.4 research expected driverName "Intel proprietary Windows driver"; the real one is "Intel Corporation".

- Row 14 (Mesa compatibility profile): MC always gets a core profile. Relaxing `MESA_GL` to `(Core|Compatibility) Profile` is harmless but optional.

3. Assert each Modrinth version's `game_versions`, `loaders` and `version_type` in the verify step (today it checks bytes only).
