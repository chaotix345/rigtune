## a. History's "Undo last" / "Undo all" stay active with nothing to undo

**Location:** `src/client/java/io/github/chaotix345/rigtune/client/ui/HistoryScreen.java:129-141`.

**Root cause:** `undoThis` (line 129-137) explicitly sets `undoThis.active = !loading && entry != null && entry.undoable()`. The two buttons built right after it (138-141, "Undo last" / "Undo all") have no `.active` assignment at all, so they keep `Button`'s default `active = true` unconditionally, even when `view.entries()` has nothing undoable (or is empty). This matches the verification note verbatim ("Cause: `client/ui/HistoryScreen.java:138-141` builds both buttons without an `active` condition, while `undoThis.active` (line 136) checks the entry" — docs/v0.3/verification/README.md:239). It is not a new bug in v0.4: the main RigTune screen's own Undo last/all buttons had the same always-active behaviour in 0.2, so this was carried over deliberately (ws-b.md: "Undo last and Undo all stay always active, as they were on the main screen; the Undo screen explains an empty or unavailable plan") and only reclassified as a low finding in the final v0.3 verification pass.

**Minimal fix:** `HistoryModel.Entry` already carries a per-entry `undoable` flag (`core/history/HistoryModel.java:73,116`, computed from `UndoPlanner.undoable(entries)`). In `HistoryScreen.init()`, compute `boolean anyUndoable = view != null && view.entries().stream().anyMatch(HistoryModel.Entry::undoable);` once, and set the "Undo last" and "Undo all" buttons' `.active` to `!loading && anyUndoable`, exactly like `undoThis` two lines above. No core change needed; `UndoPlanner.undoable()` already implements "is there anything an Undo last/Undo all could act on" (an undo entry, or one with only skips/superseded changes, isn't in the set).

**Test:** Unit: extend `HistoryScreenTest` (or add a `HistoryModelTest` case) asserting `view.entries().stream().noneMatch(Entry::undoable)` for an empty/fully-undone history. Game test: extend `HistoryGameTest` with an empty-history screenshot asserting both buttons render inactive (the class already captures `history-empty`; add a `.active` check via the screen's public button list, as `RigTuneScreen`'s existing button-state assertions do).

**Compatibility risk:** None. Pure client-side UI change; no format touched. Safe for 0.1.x/0.2.x/0.3.x files and for a downgrade to 0.3.0 (0.3.0's screen just has the old always-active behaviour back).

## b. Preview shows raw options.txt values instead of friendly labels

**Location:** `src/client/java/io/github/chaotix345/rigtune/client/ui/PreviewScreen.java:192`:
```java
target.row(Component.translatable("rigtune.preview.setting", s.key(), value(s.oldValue()), value(s.newValue())), ...);
```
`s` is a `core/preview/ApplyPreview.Setting(recId, file, key, oldValue, newValue)` built by `PreviewPlanner` (`core/preview/PreviewPlanner.java:105,118`) straight from `SettingsBridge`/the config-file readers — i.e. the raw option key (`graphicsMode`) and its raw stored values (`0`/`1`/etc.), with no label lookup anywhere in the preview pipeline. Verified example from the final verification run (docs/v0.3/verification/README.md:241): Preview shows `particles: 0 → 1`, `textureFiltering: 1 → 0`, `biomeBlendRadius: 2 → 1`, while the main recommendation list for the same options shows "Particles: All → Decreased", "Texture Filtering: RGSS → None", "Biome Blend: 5x5 → 3x3".

**Where the main list's labels come from:** `core/recommend/SettingValues.java`:
- `SettingValues.name(SettingLabel, key)` (line 112-114) — the rules' `settingLabels` entry's `name` when present, else a caption derived from the key's last segment (`SettingValues.label()`, line 91-95), prefixed with the owning mod's name for `sodium.*`/`distanthorizons.*`/`iris.*` keys.
- `SettingValues.valueLabel(SettingLabel, value)` (line 116-130) — the label's `values` map (exact match, then a numeric-aware fuzzy match via `SettingValues.same()`), falling back to the raw value.
- `SettingValues.describe()` (line 106-109) builds each recommendation's title as `"<name>: <before> → <after>"` with these two calls — this is what the main list actually renders (`Recommendation.title()`/`titleText()`), so the main list never touches raw keys/values at render time; the friendly text is baked in when the `Recommendation` is built.
- The Undo/History screens reuse the same idea live: `client/undo/GameState.java` (`label()`/`valueLabel()`, lines 47-76) wraps `SettingValues.name`/`valueLabel` for mod keys and `Options`' own captions for vanilla keys (`SettingsBridge.captions`), exposed to core as `UndoPlanner.State`; `HistoryModel.Labels.of(UndoPlanner.State)` (`core/history/HistoryModel.java:41-53`) is the same abstraction handed to `HistoryModel.build()`.

**Minimal fix:** Preview needs the same `Map<String, SettingLabel>` (the rules' `settingLabels`, already loaded wherever the report/recommendations are built) plus vanilla captions, to run `s.key()`/`s.oldValue()`/`s.newValue()` through the same `SettingValues.name`/`valueLabel` (or reuse `GameState.label`/`valueLabel` directly, since `PreviewScreen` is client-side like `GameState`). Two ways to keep this a small change:
1. **Preferred:** give `PreviewScreen` a `HistoryModel.Labels`-shaped helper (the same interface History already uses) built from a `GameState` snapshot at preview time, and call `labels.label(key)` / `labels.value(key, value)` when rendering each `ApplyPreview.Setting` row instead of the raw `s.key()`/`s.oldValue()`/`s.newValue()`. `ApplyPreview.Setting` already carries the raw key, so no core/`PreviewPlanner` change is needed at all — this is purely how `PreviewScreen` renders the row (mirrors how `HistoryScreen`'s `describe()` calls `labels.label`/`labels.value` instead of using `JournalChange`'s raw key/value directly).
2. Fallback: keep the raw value visible too (`"graphicsMode (Graphics): Fast → Fancy [1 → 0]"`) if some users want to cross-check the literal file value — not necessary given History/Undo don't do this either.

**Test:** Unit: a `PreviewScreenTest`-equivalent (or extend the existing Preview unit tests) asserting a rendered `ApplyPreview.Setting` row for a rules-labelled key produces the same text as `SettingValues.describe()` would for that key/value pair; a key with no rule label still falls back to the caption-derived name (parity with `SettingValues.label()`). Game test: extend `PreviewGameTest`'s canned-preview case with a `vanilla.graphicsMode`/`sodium.*` row and assert the rendered text matches the main list's label/value strings for the same key (screenshot diff already exists for the canned case; add the label assertion next to the existing row-text checks).

**Compatibility risk:** None — this is a rendering-only change in `PreviewScreen`, using data (`RulesDocument.SettingLabel`, `Options` captions) that's already loaded for the main screen. No file format touched, nothing persisted, so 0.1.x/0.2.x/0.3.x journals/pending.json and a downgrade to 0.3.0 are unaffected (0.3.0 simply keeps showing raw values, as today).

## c. History names mod files, not mod names

**Location:** `src/main/java/io/github/chaotix345/rigtune/core/history/JournalChange.java:9-10` (the `file`/`resultFile`/`modId` fields, no name field) and its construction sites `src/main/java/io/github/chaotix345/rigtune/core/history/StagedChanges.java:47-50` (staged Add/Update/Disable → `JournalChange.file(...)`) and `LegacyImport.java:64,70` (0.1.x import). `HistoryScreen.describe()` (`client/ui/HistoryScreen.java:306-314`) renders `change.file()` (a bare jar file name) for ADDED/DISABLED/REENABLED/UPDATED rows because that's all `JournalChange` has.

**Gson tolerance — verified, not assumed:** `Journal.java` (current and v0.3.0, identical) builds its `Gson` with plain `new GsonBuilder().setPrettyPrinting().disableHtmlEscaping().create()` (`Journal.java:33`) over a `record HistoryFile(int formatVersion, List<JournalEntry> entries)`; `JournalEntry` and `JournalChange` are plain Java records with no custom `TypeAdapter`, no `@SerializedName`, no strict-mode flag, in every one of v0.1.0, v0.2.0 and the current tree (`git show v0.1.0:.../JournalEntry.java`, `git show v0.2.0:.../JournalEntry.java` are byte-identical to current, all Gson record-reflection based). I did not rely on this by inspection alone: I compiled and ran a standalone test against the **actual Gson jars this project resolves** (`gson-2.10.1.jar` and `gson-2.14.0.jar`, both present in the Gradle cache) using a record shaped like `JournalEntry`/`JournalChange`:
  - Decoding JSON with an extra top-level field and an extra field inside a nested list element (as a `modName` addition would look to 0.2.0/0.3.0) parsed successfully on **both** Gson versions, with the unknown fields silently dropped — no exception, no strict-mode failure.
  - Decoding JSON that's *missing* a record component present in the target record (the reverse direction: an old journal read by a newer record with an added optional field) also parsed successfully on both versions, with the missing component defaulting to `null` (for a reference type) rather than throwing.
  This is the same mechanism `PendingActions`/`Op` (v0.1.0's `core/apply/PendingActions.java:21-40`, also a plain Gson record with the same `GsonBuilder`) rely on, and the same one already used in production by `rigtune.json`'s `lastWarnedApply` (a new optional field added in v0.3, explicitly documented as "0.2.0's Gson ignores it" — ws-b.md) and by `BenchmarkRecord.Context` (review-6.md's compat review, line 25, independently confirms this same Gson-tolerance behaviour for `ClientState.java`/`rigtune.json` and for `BenchmarkRecord.Context`/`benchmarks.json`). So adding an **optional** `modName` field to `JournalChange` is safe for 0.2.0 and 0.3.0 reading a 0.4-written `history.json` (field ignored) and for 0.4 reading a 0.1.0/0.2.0/0.3.0 `history.json` (field defaults to `null`, which the History screen already needs to handle as "fall back to the file name").

**Where a display name can come from at staging time:**
- **Additions:** `Action.AddMod(String slug, String projectId, String title)` (`core/model/Action.java:10`) already carries the Modrinth project's **title** at recommendation-build time. Likewise `Action.UpdateMod`'s `UpdateInfo(modId, projectId, currentVersion, newVersionId, newVersionNumber, ModFile file)` (`core/model/UpdateInfo.java:3`) has no title field, but the recommendation that wraps it (`Recommendation.title()`) does.
- **Disables (and undo re-enables):** no Modrinth title is available (the mod is only ever referenced by its installed jar), but the jar itself is on disk at staging time. `ModJars` already has exactly this pattern for the mod id: `ModJars.modIdOf(Path jar)` (`core/apply/ModJars.java:28`) opens the jar, reads `fabric.mod.json` and returns its `"id"` (with the same file-gone / IO-error handling `StagedChanges.of()` already relies on via the `modIdOf` function parameter, line 36-37 / 49).
- **Minimal, uniform proposal:** rather than threading a new field through `PendingActions.Op`/`DownloadPlanner` (a bigger change touching the persisted pending.json format and the download pipeline), add a twin of `ModJars.modIdOf`, e.g. `ModJars.nameOf(Path jar)`, reading fabric.mod.json's `"name"` key instead of `"id"` (same size/IO-error/missing-file handling, same `null`-on-failure contract). Give `StagedChanges.of(...)` a second `Function<Path, String> modNameOf` parameter (mirroring the existing `modIdOf` parameter) and call it at the same two sites: `modNameOf.apply(Path.of(op.from()))` for `ENABLE_FILE` (the file readable at staging time is the `.rigtune-pending` download, `op.from()`, not `op.to()`, which doesn't exist yet), and `modNameOf.apply(Path.of(op.path()))` for `DISABLE_FILE` (the installed jar, still in place). This needs **no** change to `PendingActions`, `DownloadPlanner`, or the pending.json format at all — only `JournalChange` (new optional `modName` component) and `StagedChanges`/`LegacyImport` (best-effort; for 0.1.x-imported entries the jar is often already gone, exactly as `modIdOf` already documents at `ModJars.java:31-33`, so `modName` will legitimately be `null` there and the screen falls back to the file name, same as it does for a missing `modId` today).
- `HistoryScreen.describe()`/`HistoryModel` then prefer `change.modName()` when non-null, falling back to `change.file()` exactly as now.

**Test:** Unit: `JournalChangeTest`/`StagedChangesTest` asserting a staged enable/disable records the jar's fabric.mod.json `name` when readable, and falls back to `null` (→ file name shown) when the jar is missing/unreadable, mirroring the existing `modIdOf` fallback tests. A `JournalTest` case round-tripping a `history.json` with `modName` absent (old file) and present (new file) through Gson, asserting no exception either way (this is the one place where re-running my empirical Gson check as an actual project unit test, rather than only my scratch program, is worth doing). Game test: `HistoryGameTest` asserting a mod row shows "Sodium" instead of "sodium-fabric-...jar" for a known test-fixture jar.

**Compatibility risk:** Low, by design. Adding an optional record field to `JournalChange` is additive JSON; 0.2.0 and 0.3.0 (both plain-Gson-record parsers, verified above) silently ignore it on read, and if 0.2.0/0.3.0 subsequently rewrites history.json (e.g. after its own apply), the field is simply dropped from the entries it rewrites — the same accepted, documented behaviour as `rigtune.json`'s `lastWarnedApply`. A downgrade to 0.3.0 is therefore safe: history.json stays readable, only the mod name is lost (file names reappear), never a crash or refusal.

## d. The incompatibility check doesn't see changes an earlier Apply already staged

**Location:** `src/client/java/io/github/chaotix345/rigtune/client/RealController.java:518-519` (report-build time) and `:724-725` (download time): `installedProjects = new HashSet<>(data.projectIdsByModId().values())`, built from `OnlineDataFetcher.Result` over the **currently loaded** mods only. `core/modrinth/DependencyResolver` and `DownloadPlanner.plan()` (`core/modrinth/DownloadPlanner.java:94`) take exactly these `installedProjects`/`installedVersions` plus the in-memory `Batch` of *this* `plan()` call — nothing about `pending.json`'s already-staged-but-not-yet-applied ops (an earlier Apply in the same session, before the game exits) is folded in anywhere. This is exactly the known gap ws-a.md records: "Changes staged by an earlier Apply (already in pending.json, not in this batch) aren't part of the view, because pending.json has no Modrinth version ids (adding them would be a format change)", with two concrete consequences already documented there: an addition incompatible only with an old, already-updated version stays refused until the restart (safe, just annoying); the reverse (a later addition/update declaring an already-staged item incompatible) is **not** caught at all (unsafe: both could apply and conflict at runtime).

**Why pending.json can't just be looked up as-is:** `PendingActions.Op` (`core/apply/PendingActions.java`, unchanged since v0.1.0) carries `modId` for an `ENABLE_FILE` op (set via `Op.withModId`) but **no Modrinth project/version id**, and a `DISABLE_FILE` op carries neither a mod id nor a name. So today there's no way to map a staged-but-unapplied op back to "which Modrinth project does this represent" without re-reading the jar (for `modId`, already possible) and then re-resolving that id to a Modrinth project (an extra network round-trip DownloadPlanner doesn't currently make for already-staged ops).

**v0.1.0's pending.json parser — verified:** `git show v0.1.0:src/main/java/io/github/chaotix345/rigtune/core/apply/PendingActions.java` shows `PendingActions`/`Op` are plain records with the same bare `GsonBuilder` as `Journal` (no strict mode, no unknown-field rejection) — identical mechanism to item (c) above, and empirically confirmed by the same Gson test (records ignore unmapped JSON fields, default missing ones to `null`). An **optional** new field on `Op` is therefore safe for v0.1.0's helper to read (it ignores it) and safe for a v0.1.0-shaped or 0.3.0-shaped `pending.json` to be read by a v0.4 client (the field is simply absent/`null`).

**Which helper version actually runs a given pending.json — verified from source (matters for this design and for c/e too):** `HelperLauncher.launch()` is unchanged in shape from v0.1.0 to current (`git show v0.1.0:.../HelperLauncher.java:37-40` vs. current `HelperLauncher.java:37-53`): at the exit of *whichever* game session is currently running, it copies the classes/jar of `ApplyHelper.class`'s and `Gson.class`'s **current code source** (i.e. the mod version that was loaded and ran that session) into `config/rigtune/helper/`, and launches that copy. A mod-file swap only takes effect on the *next* Fabric launch, so: the helper that processes `pending.json` at any given exit is always the version that was **running during that session** — normally the same version that staged the entries in that same session. But `pending.json` entries can persist across sessions when the helper couldn't fully apply them (retried up to `MAX_FAILED_RUNS = 3` restarts, item f); if the user replaces the mod jar directly (not through RigTune's own self-update) between two sessions, the *next* session's helper — now the new version — is the one that picks up and retries whatever the *old* version staged (and vice versa for a manual downgrade). Since `Op`/`PendingActions` are plain tolerant Gson records in every version checked (v0.1.0 through current), this cross-version execution is already safe today and stays safe with an added optional field.

**Proposed design:** Add an **optional** `projectId` field to `Op` (`PendingActions.Op`, set only on `ENABLE_FILE` ops via a new `Op.withProjectId(String)`, populated by `DownloadPlanner.addMod`/`updateMod` from the `ModrinthVersion.projectId()` it already has in scope when it creates the op — `DownloadPlanner.java:182,215`). At the next `plan()` call (`RealController.java:518-527`/`724-`), before building `installedProjects`, read the *current* `pending.json`'s `ENABLE_FILE` ops that are not yet applied (i.e. still present — `Staging`/`RealController` already reads pending.json for `stagedJarsByModId()`) and fold their `projectId` (where present) into `installedProjects`, exactly as if that project were already installed. This reuses the resolver's existing "installed project" path (`DependencyResolver.java:161-163`, `refuseIncompatible`'s `installedProjects.contains(dep.projectId())` branch) with no resolver code change — only the *input set* changes. This closes the specific, unsafe half of the known gap (a later addition/update declaring an already-staged addition's project incompatible) using only additive, optional data. Staged `DISABLE_FILE` ops are harder to fold in symmetrically (they carry no mod id at all today, so `Staging` would also need a `withModId` there, similar to `withProjectId`); that half is lower value (it only makes an addition *more* permissive, never less safe) and can be left as a documented residual limitation, matching ws-a's "the installed mods' own declarations... is covered" framing (i.e., under-blocking here is the safe direction, same principle ws-a already used to justify what it does check).

**Test:** Unit: `DownloadPlannerTest`/`DependencyResolverTest` case with two sequential `plan()` calls sharing a `pending.json` between them (an addition staged first, whose project is later declared incompatible by a second addition's version) — assert the second `plan()` refuses instead of silently staging both. `RealControllerTest`-level or `client/DownloadInputsTest` case building `installedProjects` from a pending.json fixture with staged `ENABLE_FILE` ops carrying `projectId`. Game/E2E: an `e2e` scenario staging two sequential Applies before restarting, where the second is incompatible with the first's staged addition — assert it's refused.

**Compatibility risk:** Low. `Op.projectId` is an additive, optional Gson field: v0.1.0/0.2.0/0.3.0 helpers ignore it entirely (verified Gson behaviour, same as item c); a v0.4 pending.json is still fully executable by an older helper, and an older pending.json read by v0.4 just has `projectId == null` for every op (the new "staged view" folding then simply contributes nothing extra for those ops — falls back to today's behaviour, never less safe). A downgrade to 0.3.0 mid-session (pending.json partially applied with the new field present) is safe for the same reason.

## e. Two mutually incompatible updates in one batch: the later one is refused

**Location:** `src/main/java/io/github/chaotix345/rigtune/core/modrinth/DownloadPlanner.java:100-131` (`plan()`) and `:186-218` (`updateMod()`); `core/modrinth/DependencyResolver.java:138-188` (`checkUpdate`/`refuseIncompatible`).

**Root cause:** `plan()` reorders every `UpdateMod` recommendation before any `AddMod` (line 100-103, comment: "so the outcome doesn't depend on the order they were ticked in (A-H1)") — but this only decouples *update-vs-addition* ordering; updates are still processed against each other in whatever relative order they appear in `recs` (tick order). Each update is handled one at a time in the loop at line 104-129: `updateMod()` calls `resolver.checkUpdate(next, attempt.projects, attempt.batch.versions)` (line 205), which checks the new version against `attempt.batch.versions` — the versions **already committed** by earlier iterations of this same loop (`batch.commit(attempt)`, line 121, runs after each successful recommendation, before the next one is attempted). `DependencyResolver.refuseIncompatible()` (line 146-188) then checks both directions (the new version's own `incompatible` deps against `together = batch + version`, line 164-168; and the batch's existing versions declaring the new one incompatible, line 170-174) and throws `bothInstalled(...)` (`rigtune.download.incompatible_both`, line 211-213) for whichever update is processed **second**. So for two updates A and B whose new Modrinth versions mutually declare each other incompatible: whichever is earlier in the ticked/ordered list commits successfully (A's version enters `attempt.batch.versions`), and B's `checkUpdate` then finds A's version in the batch and throws — B is silently refused (`errors.add(rec.title() + ": " + e.getMessage())`, line 113-119) while A proceeds. Swap the tick order and the outcome flips. This is exactly ws-a.md's documented known gap: "Two updates in one batch that Modrinth marks incompatible with each other's new versions: the one planned later is refused, so which one goes in follows tick order among updates (AC3.2 iv covers only additions against updates)."

**Why this is the wrong behaviour:** it's non-obvious and effectively arbitrary from the user's point of view (they ticked both; the report doesn't say "A and B can't both apply, pick one" — B just fails with a generic per-item error line, easy to miss among a dozen other rows), and it isn't even guaranteed to be *stable*: `recs`' relative order for two `UpdateMod` entries is whatever order the caller (`RigTuneScreen.ticked()`) built the list in, not something the user consciously chose between A and B.

**Proposed fix — refuse both, explicitly:** before the main loop, do a pairwise pre-check across every ticked `UpdateMod`'s *target* version (`updateVersions.get(info.newVersionId())`, the same map `updateMod()` already uses at line 201) using the resolver's existing `declaresIncompatible()`/`matches()` helpers (`DependencyResolver.java:198-204`, already `static` and dependency-direction-aware) in both directions. When two updates' new versions are mutually incompatible, refuse **both** immediately with a message naming each other (reusing the existing `rigtune.download.incompatible_both` wording: "Modrinth marks %s and %s as incompatible, and both would be installed" — already accurate for this exact case, it just currently only reaches the second one), rather than letting one proceed silently. This mirrors the addition-vs-addition guard already in place two lines above `updateMod()` (`DownloadPlanner.java:134-139`, "The batch never stages both sides of a conflict: the later one fails" — except that comment's own behaviour has the same one-sided flaw for two *additions*, worth reconsidering at the same time: `addMod()`'s conflict check at line 135-138 only looks *backward* at `attempt.batch.added` for a `conflicts.test()` match, so it has an identical "later one silently loses" property, just via the rules' own `conflicts` predicate instead of Modrinth's `incompatible` dependency — the same joint-refusal fix should apply there too for consistency, though it's not separately called out in the deferred list). "Resolve jointly" (auto-pick one) was considered and rejected: there's no principled way to choose which of two updates the user "really wanted" without asking them, so a clear, symmetric refusal (with both mods named) is the safer, simpler, and more honest behaviour — the user re-ticks whichever one they want and re-applies.

**Test:** Unit: `DownloadPlannerTest` with two `UpdateMod` recommendations whose fixture Modrinth versions declare each other incompatible, in both tick orders — assert both are refused (in `errors`/`errorTexts`) in both orders, and that a third, unrelated update in the same batch still succeeds. Extend the existing addition-vs-addition conflict test the same way if that path is also fixed. Game test: not required (no UI difference beyond the existing "download refused" report rows), but `PreviewGameTest`/`ProductionSmoke` coverage of a refused-download row already exists and would cover the rendering.

**Compatibility risk:** None. Pure in-memory planning logic in `DownloadPlanner`/`DependencyResolver`; no format change, nothing persisted differently. Safe for every version's files and for a downgrade to 0.3.0 (0.3.0 just goes back to the tick-order-dependent behaviour).

## f. The helper's "Gave up after N attempt(s)" message prefix

**Location:** `src/main/java/io/github/chaotix345/rigtune/core/apply/ApplyExecutor.java:499` (per-run failure) and `:186` (cross-restart abandonment), surfaced verbatim into `last-apply.json`'s `OpResult.message()`, then into `core/history/ApplyFailures.java` (comment at line 64 already flags this: "mistaken for the helper's own retries inside a run"), then rendered by `HistoryScreen.failureText()` (`client/ui/HistoryScreen.java:320-328`).

**Root cause — two different counters, one word:** `ApplyExecutor` has two independent retry limits that both get described with "attempt(s)":
1. **In-run retries** (`RetryState`, `ApplyExecutor.java:112-138`, incremented inside `retrying()`, line 484-499): quick retries of one file operation *within a single helper run* (e.g. a locked-file rename), reported as `"Gave up after " + state.attempt() + " attempt(s): " + last` (line 499) — in every captured log/fixture in the repo this is **10** (`docs/v0.3/verification/...`, `docs/smoke/self-update/...`, `src/test/resources/v010/real-instance/last-apply.json`).
2. **Cross-restart attempts** (`ApplyExecutor.MAX_FAILED_RUNS = 3`, line 34; aliased as `ApplyFailures.MAX_ATTEMPTS`, `core/history/ApplyFailures.java:21`): how many separate game-restarts an op is retried before being marked ABANDONED (line 172-186), shown by History/latest.log as "(try n of 3 at restart)" (reworded from "(attempt n of 3)" in ws-g specifically to reduce this confusion — `docs/v0.3/design/ws-g.md:52`).

The result, unchanged since that ws-g rewording, is a sentence like `"Last attempt failed: Gave up after 10 attempt(s): java.nio.file.FileSystemException: ... (try 2 of 3 at restart)"` (verified live in `docs/v0.3/verification/final/a-gametest/a262-rigtune-log.txt:132` and `docs/v0.3/verification/README.md:35,102`) — the outer wording was fixed, but the inner "10 attempt(s)" prefix (from `ApplyExecutor.java:499`) still uses the same word, so the sentence reads as if there were "10" attempts and then contradictorily "2 of 3" right after. This is exactly the residual half of the tracked finding: "The helper's 'Gave up after 10 attempt(s): ' prefix is still there" (docs/v0.3/verification/README.md:231).

## g. MultiMC is shown as Prism; GDLauncher isn't recognised

**Location:** `src/main/java/io/github/chaotix345/rigtune/core/launcher/LauncherDetector.java:33-36` and `core/launcher/LauncherSignals.java:11-17`, `core/launcher/Launcher.java` (enum).

**Root cause:**
```java
if (present(properties, LauncherSignals.PRISM_INSTANCE) || present(properties, LauncherSignals.MULTIMC_INSTANCE)
        || present(env, LauncherSignals.INST_ID) || present(env, LauncherSignals.INST_NAME)) {
```

Any of four signals — the Prism-specific property, the MultiMC-legacy property, or either `INST_ID`/`INST_NAME` env var — maps unconditionally to `Launcher.PRISM`. There is no `Launcher.MULTIMC` value in the enum at all, and no branch anywhere checks for GDLauncher.

**How to tell MultiMC from Prism (and PolyMC) reliably:** Prism's `SystemProperties.java` sets `org.prismlauncher.instance.name` and `multimc.instance.title` **together**, from the same `if (name != null)` guard on the same `instanceName` parameter (lines 21-22 and 33-34) — so Prism *always* sets both when it sets either. Real MultiMC only ever sets `multimc.instance.title`/`INST_ID`/`INST_NAME`, never `org.prismlauncher.instance.name` (that property doesn't exist in the MultiMC codebase at all). So: **`org.prismlauncher.instance.name` present → definitely Prism (or a Prism-family fork that copied this file, e.g. current PolyMC builds if they rebased on it). `org.prismlauncher.instance.name` absent but `multimc.instance.title`/`INST_ID`/`INST_NAME` present → MultiMC** (or an older PolyMC that never picked up Prism's compatibility shim). I could not find PolyMC's own copy of this file via GitHub code search (zero hits for `multimc.instance.title` in `PolyMC/PolyMC`, which is more likely a search-indexing gap for a fork than evidence PolyMC lacks the property) — treat PolyMC's exact behaviour as **UNVERIFIED**; it should land in whichever bucket its actual `SystemProperties`-equivalent file matches once checked directly.

**Minimal fix:** in `LauncherDetector.detectOrThrow()`, check `PRISM_INSTANCE` (`org.prismlauncher.instance.name`) **first and on its own** → `Launcher.PRISM`; only if that's absent, fall through to `MULTIMC_INSTANCE`/`INST_ID`/`INST_NAME` → a **new** `Launcher.MULTIMC` value (needs a `Launcher` enum entry, a display name "MultiMC", and — per ws-c's own C-M2 pattern for Prism/Modrinth App/ATLauncher — its own RAM-advice click-steps string, since MultiMC's Java settings UI differs cosmetically from Prism's fork of it but is structurally the same "Edit instance → Settings → Java → Maximum Memory Usage" flow). Add a `GDLAUNCHER_BRAND = "GDLauncher"` constant and a `Launcher.GDLAUNCHER` branch parallel to the existing `ATLAUNCHER_BRAND`/`MODRINTH_BRAND` checks (`LauncherDetector.java:38-43`), with its own RAM-advice steps (needs its own click-through verification, out of scope of this research pass — mark as UNVERIFIED like CurseForge's/official's steps already are).

**Test:** Unit: extend `LauncherDetectorTest` with (a) a signals fixture carrying *only* `multimc.instance.title`+`INST_ID`/`INST_NAME` (no `org.prismlauncher.instance.name`) asserting `Launcher.MULTIMC`, (b) both Prism-specific and legacy-compat properties present (as real Prism sends) still asserting `Launcher.PRISM`, (c) `minecraft.launcher.brand=GDLauncher` asserting `Launcher.GDLAUNCHER`. Game test: `LauncherGameTest` already logs the raw signals and detected result per leg (per ws-c.md's AC5.3 evidence); add the two new fixture cases there for a real screenshot of the RAM-advice line under each new launcher.

**Compatibility risk:** None — detection is a pure, non-persisted runtime probe (`LauncherSignals`/`LauncherDetector`/`LauncherInfo` touch no file format at all). Safe for every journal/pending.json version and for a downgrade (0.3.0 just goes back to mis-detecting MultiMC as Prism and missing GDLauncher, as today).
