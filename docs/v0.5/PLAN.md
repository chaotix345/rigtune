# RigTune v0.5.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILLS: superpowers:writing-plans (your TDD task plan goes FIRST into `docs/v0.5/design/<ws>.md`, committed before any code), superpowers:test-driven-development (every task), superpowers:verification-before-completion (before reporting), superpowers:requesting-code-review (self-review). Steps use checkbox (`- [ ]`) syntax.

**Goal:** Ship RigTune v0.5.0 for MC 26.2 and 26.3 as docs/v0.5/SPEC.md defines it: a CI whose tests no longer depend on Modrinth, Maven or Mojang being up and can't go red for reasons outside the code (P0.1), every v0.4 leftover and audit/real-world finding fixed with a test (P0.2), the verification gaps closed (P0.3), a mod that never fights the launcher (P0.4), and five features (C20, C09, C16, C02, C18), without regressing 0.1.x-0.4.x players or a downgrade to 0.4.0/0.3.0.

**Architecture:** One Stonecutter codebase, one jar per MC version. Pure logic in `core/` (JUnit, no Minecraft imports); `client/` is the thin MC layer. Workstreams own disjoint files. Shared methods get **extension points** from the contracts commit (a report post-step list, apply/start hooks, an event-registration hook, per-owner skeleton methods), so a workstream adds or fills its own classes instead of editing a shared method; the few remaining shared-file edits go in marked places.

**Tech Stack:** Java 25, Fabric Loom 1.17.21 (pinned by ws-ci), Stonecutter 0.9.8, Gradle 9.5.1, Gson, JUnit 5; Python 3.11 stdlib for tools; GitHub Actions (ubuntu-24.04, Xvfb, a loopback-only namespace with loopback multicast for game tests); Minotaur for Modrinth.

**Spec:** docs/v0.5/SPEC.md (246 ACs; its "Amendments (plan review, 2026-09-27)" section overrides item text). This plan's own Amendments section is at the end. Research: docs/research/v0.5/*.md. "SPEC 2S" etc. = the SPEC's sub-item ids; "AC5.3" = its ACs. **R** = the v0.5 release rules revision: main's revision at release time + 1 (r17 if nothing else lands).

## Workstream protocol (every agent)
1. Read SPEC.md (the top, X1-X12, C3, C8, "Shared contracts", your items, the Amendments), this plan (Global Constraints, your section, Extension points, Hotspots, Ownership, Cross-workstream ACs, the Amendments), your research doc(s) and `docs/v0.5/design/ws-k.md` (the contracts as landed, the anchors, the footprint baseline), then the code you'll touch.
2. Write your TDD task plan into `docs/v0.5/design/<ws>.md` (tasks, files, test names, the red test for each fix, which ACs each task closes, your code-deciding run if any). Commit it before any code; push it **with your first code task** (the coordinator reads it in your worktree; no docs-only pushes).
3. Execute task by task with TDD (a test that fails first; for P0.2 fixes, reuse the audit-verify / realworld throwaway tests named in the SPEC), committing after each task. Batch pushes: push when a task (or a few small ones) is done, never every commit, and **never while a streak runs** (the coordinator announces streaks): CI capacity is shared by ~15 workstreams.
4. Game tests: only YOUR classes/methods (Ownership). CI green on every job and every leg; `gh run download <id>` and look at your screenshots. Your design doc lists the run ids and artifact names you looked at and what you checked.
5. Self-review: dispatch a code-reviewer subagent on your diff. Its findings go to the coordinator, who forwards them with decisions; keep working meanwhile. If nothing has arrived 20 minutes after the review finished, message the coordinator. Fix every forwarded high and medium.
6. Finish: merge `origin/feat/v0.5.0` into your branch (keep both sides' intent in hotspots), run your targeted tests in a build slot, push, CI green on every job, finish `docs/v0.5/design/<ws>.md` (deviations, residuals, UNVERIFIED, Docs text, footprint deltas, the AC table with evidence). Report in at most 15 lines: branch head, unit-test counts per version (from CI), CI run URL, AC status per item (verified / not, with evidence), anything UNVERIFIED.

## Local runs, the locks, CI polling
- **ONE Minecraft client at a time, machine-wide.** Before any local game launch (`runClientGameTest`, `runProductionClientGameTest`, autorun benchmarks, production smokes, E2E): `mkdir C:/Dev/Worktrees/.gametest-lock` (atomic; fails if held) and write `owner.txt` inside (`agent: <ws>`, `worktree: <path>`, `started: <date -Is>`, `expected_minutes: <n>`; the watchdog alarms only past it). If mkdir fails, do other work and retry at most every 2 minutes; give up after 45 minutes and report. Release it IN THE SAME COMMAND as the run, pass or fail: `<run>; rc=$?; rm -f C:/Dev/Worktrees/.gametest-lock/owner.txt; rmdir C:/Dev/Worktrees/.gametest-lock; exit $rc`. Long runs: `run_in_background` with the release chained in, then poll the log. Kill only your own orphaned clients (command line contains your worktree path); never touch other java processes (the user's `fabric-server-launcher.jar`, Gradle daemons). The game-test lock's holder needs no build slot.
- **Build slots: at most 4 concurrent `./gradlew` runs** (the PC has 31 GB and 16 threads; `-Xmx2G` daemons, both nodes, forked test JVMs). The coordinator creates `C:/Dev/Worktrees/.build-slots/` once. Take a slot by atomic mkdir and release it in the same command:
  `slot=; for n in 1 2 3 4; do mkdir "C:/Dev/Worktrees/.build-slots/slot-$n" 2>/dev/null && { slot="C:/Dev/Worktrees/.build-slots/slot-$n"; break; }; done; [ -n "$slot" ] || { echo "no build slot"; exit 75; }; printf 'agent: <ws>\nworktree: <path>\nstarted: %s\n' "$(date -Is)" > "$slot/owner.txt"; ./gradlew -Dorg.gradle.daemon.idletimeout=600000 <task>; rc=$?; rm -f "$slot/owner.txt"; rmdir "$slot"; exit $rc`
  No slot free: do other work and retry every 2 minutes. Run targeted tests (`./gradlew :26.2:test --tests '<your classes>'`, `:26.3:` too for version-specific code); the full build is CI's. A local red timing gate (FrameHookBudgetTest, ThreadSamplerTest) with a green CI is noted in your design doc, not debugged. (`org.gradle.daemon.idletimeout` is Gradle 9.5.1's property, checked in its `DaemonBuildOptions$IdleTimeoutOption`; that a command-line `-D` sets it for the daemon it starts is UNVERIFIED: the first agent checks `./gradlew --status` after 10 idle minutes and tells the coordinator.)
