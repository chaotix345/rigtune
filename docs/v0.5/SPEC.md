# RigTune v0.5.0: specification

Status: DRAFT (Phase 2). Each item has numbered acceptance criteria (AC). An item ships only when every AC is verified and the evidence is recorded (docs/v0.5/verification/, PROGRESS.md). Priorities: P0 must ship; P1 should ship (cut only in the order below, with a written reason); P2 is stretch and starts only when every P0 and P1 AC is green. **Cut P2 before compromising P0/P1 quality.** The coordinator's scope decisions (brief, 2026-09-27) are folded in; where a research doc differs, this spec wins; where this spec departs from the brief, it says so and why (Open questions, and C3 of the cross-cutting rules).

**Goal.** Make RigTune trustworthy in daily use: a CI that never goes red for reasons outside the code, every v0.4 leftover and audit finding fixed with a test, every v0.4 UNVERIFIED claim closed or honestly kept, a mod that never breaks the player's launcher, and five features that measure or explain what RigTune changes.

**Theme.** Rock-solid (zero flaky CI, every leftover fixed, verification gaps closed); "RigTune never fights the launcher" (a real bug in the user's Modrinth App instance); five brainstorm picks (docs/research/v0.5/brainstorm.md §3). Minecraft 26.2 and 26.3 only: 26.4 is out of scope (the weekly snapshot canary keeps running).

## Open questions

None of the brief's decisions was found impossible. The points below are decisions this spec makes where the brief left room or where the research disagrees with the brief; each has the recommended answer that the body already follows.

1. **Where FIRST_RUN sits in NoticePriority.** The brief lists the first-run guide 10th (after what's new). Recommended: 5th, above SERVER_LIMIT, right after P0.4's two notices, which can never be shown to a new player (C3 below). Evidence: SERVER_LIMIT is raised on every remote connection, not only busy servers (`client/notice/ServerLimitNoticeSource.java:43-47,66-67`, sp §1), so any notice below it sits behind "+1 more" on every server; the guide exists only until the first Apply and is the one notice that must be read before it; it can't coexist with LAUNCHER_REPAIR or TRY_IT (fa §2.5, §2.1). Coordinator to confirm.
2. **L10 (a mod staged for disabling still blocks as present).** lo recommends folding it into L9. Recommended: keep L10's over-blocking (2H, "Not fixed"). Folding staged disables into the incompatibility checks would let a later Undo of the disable leave both mods active: Undo's folder check covers `depends`, not incompatibility (DESIGN "Undo").
3. **SD-2 and BH-2 each have an S and an M fix in av.** Recommended: SD-2 S (both numbers over the held window, labelled) because M adds per-frame work to the frame hook; BH-2 M (an optional `stagedAtStart` context field) with S as the fallback for runs without the field, because S covers mod rows only and BH-2's scenario includes staged Sodium/DH/Iris settings.
4. **AW-1's own Re-scan action.** av leaves it open. Recommended: the notice's own Re-scan retires it (its job is done); a rescan from anywhere else keeps it (2W).
5. **NEW-1 (generational Shenandoah).** av marks the impact UNCERTAIN. Recommended: measure first, then either the GC-kind fix or fail closed on the live set (2S); never ship a guessed classifier.
6. **Prism/PolyMC under P0.4.** PROGRESS's r-launchers row (written from lm's first draft) says "Prism/PolyMC stay one-click"; the coordinator's final decision, the brief and the final lm (§3.1, §3.7) say advice mode when `mods/.index/*.pw.toml` exists, because Prism's own update then permanently deletes RigTune's `.disabled` jar and can leave one mod twice. Specified per the final decision; the PROGRESS row needs updating.
7. **P0.4's other open points** (lm §8 "Still open", decided by the coordinator): GDLauncher is fully advice-only (no updates-only mode, so `ModFilesPolicy` is RIGTUNE / LAUNCHER / PENDING); repair = "delete the old disabled copy in the app" first, the three-step order as fallback text; RigTune never moves its old `.disabled` copies; held groups are held and offered, never cancelled automatically; ATLauncher's `disabledmods/` later; the old-client warning only behind its compat test. All specified in section 4.
8. **The Modrinth App's game-settings sync.** The brief left it to r-launchers' findings; lm §2 detects the effect (values at exit vs next start) rather than reading the app's database. Specified as 4h, with its own notice slot.

## Cross-cutting rules (every item)

- **X1 On-device.** Every new feature works fully with RigTune's network switches off and opens no new connection. Each new game-test class runs its main case with `networkEnabled = false`, set through `GameTestNet` (1e).
- **X2 Undoable.** Anything that changes a setting goes through `RealController.apply` → journal → Undo (stutter fixes, Try It, per-server switches). Advice-only features write nothing outside their own file. In a launcher-managed instance RigTune changes no mod file unless the player opted in (4).
- **X3 Honest wording.** Estimates are called estimates; measured comparisons say "may be related" or "measured comparison, not proof"; numbers are always shown next to a verdict; no "fixed", "caused", "because of", "proves", "guarantee" (WordingTest, X5).
- **X4 Footprint gate: no new render-thread init work.** `renderThreadInitCpuMs` (max observed 131.1 of 150) and `clientStartedWallMs` (102.2 of 141) keep their budgets and stay strict (ci §4.4). Therefore:
  1. No v0.5 service, store, notice source, screen or feature class is constructed or class-loaded during `RigTunePreLaunch`, `onInitializeClient` or the CLIENT_STARTED handler. `RealController` is built in `onInitializeClient` (`RigTuneClient.java:73`) and builds its services and notice sources in its constructor (`RealController.java:170-181`), so the v0.5 services and notice sources sit behind one lazy holder, resolved on first use (a screen init, a worker task, an event callback), and the notice list adds them through one lazy wrapper.
  2. Event registrations in init are allowed (one lambda each); the lambda resolves the service on its first call. The CLIENT_STARTED handler may add at most executor submissions, never the work itself.
  3. Measured: `FootprintStats` records whether the lazy holder was resolved before `initEnd` and before the CLIENT_STARTED handler returned; `FootprintGameTest` fails the leg if it was (a deterministic check, every leg). The timing keys keep their budgets on every leg, and the 5-run streaks (1g) record their per-leg medians next to v0.4.0's (ci §4.4: p50 96.9 ms CPU).
  4. RW-16's timer on vanilla's `CrashReport.preload` runs in vanilla's own startup before RigTune's init and is two clock reads; RW-16's registry read runs on the worker (2L). New tick work (C09's `TryItService.tick`, RW-11's settings check) allocates nothing and stays inside the tick budgets (1d); no new frame-hook work anywhere. New work in the first 5 s after CLIENT_STARTED counts in `workerCpuMs5s` (300, unchanged). `rigtuneClassBytesIdle` and `leakSuspects` stay as budgeted.
- **X5 Localisation.** Every UI string is an `en_us.json` key inside its feature's prefix block (Shared contracts C5), inserted alphabetically; LangCheckTest (literal keys, `%s` only, `Text.of` English equal to en_us.json, no unused key, dynamic families registered) and PseudoLocaleTest pass. WordingTest: `rigtune.tryit.` joins the correlation prefixes (no "caused"/"because of"); `rigtune.stutter.fix.` values must not contain "fixed the", "proves" or "guarantee"; "limited by" and "bottleneck" stay banned everywhere. Rule-provided text stays English data.
- **X6 Accessibility.** Every new screen and list extends `RowList`; every row returns a `RowFocus` (Tab stop, narration, focus frame, 26.2 narration fix); text that isn't a list row uses `RowFocus.standalone`; buttons are ordinary widgets; every colour goes through `Palette.of` using existing literals only (PaletteTest); clicks compare `InputConstants.MOUSE_BUTTON_LEFT`, key presses `InputConstants.KEY_*`, never literals. Each new screen or row type gets an `A11yGameTest` walk (Tab reaches every row and button in order, the focused item's narration contains its text) and a high-contrast screenshot. The list is in C6.
- **X7 State files.** Every new file follows `core/store/JsonStateFile`'s rules: `formatVersion: 1`; atomic writes; a size cap; corrupt → `<name>.bad` (never replaced) and empty; a newer `formatVersion` → read-only, never written; an I/O error or a file over 4 × the cap → left alone; nothing throws; a read error never blocks startup; values type-checked (players edit these files); unknown fields at any depth survive. Files with more than one writer go through `StateStore` (one instance per file per process, a synchronized re-reading `update`).
- **X8 Threading.**
  - `settings.json` is written only through `SettingsSaver` (its own thread, flushed on quit); never raw on `Probes.EXECUTOR` (L6, P0.4's opt-in).
  - A file whose writes must stay ordered has one ordered chain: `stutter.json` and `stutter-fixes.json` share StutterService's io chain; `tryit.json` has TryItService's chain; both run on `Probes.EXECUTOR`. `server-profiles.json`, `awareness.json` and `profiles.json` go through their `StateStore.update` from whichever thread acts.
  - `Probes.EXECUTOR` (2 threads, shared) gets only short tasks: no network, no blocking waits. Network calls stay on `Probes.NETWORK`; v0.5 adds none.
  - The render thread does no new file I/O at init or CLIENT_STARTED (X4); notice sources' `current()` does no file I/O while nothing is pending; screens may read their own small files at init as ProfilesScreen does today.
  - The helper stays core + Gson; no new thread is added by any P1 feature.
- **X9 26.2 and 26.3.** Every item is built, unit-tested and game-tested on both nodes, the game tests on the three CI legs (26.2 OpenGL, 26.3 OpenGL, 26.3 Vulkan). Known differences (checked with javap in the research):
  - `InputConstants`: `MOUSE_BUTTON_LEFT` 0 on 26.2 and 1 on 26.3 (SDL3); `KEY_TAB` 258/43, `KEY_RETURN` 257/40, `KEY_ESCAPE` 256/41 (fa §4). Compare only with the constants.
  - `Screen.scheduleNarration()` and `updateNarratorStatus(…)` exist only on 26.3; use `triggerImmediateNarration(false)` (both). In game tests `ScreenNarrationCollector.update` takes a `NarrationTrigger` only on 26.3 (the `//? if >=26.3` idiom, `UiGameTest.java:479-483`).
  - `GuiGraphicsExtractor.fill(RenderPipeline, …)`'s pipeline type moved packages; use the 5-int `fill`.
  - 26.2 narrates the hovered list row first; `RowList`'s `//? if <26.3` block fixes it.
  - 26.3 under Xvfb needs `SDL_OPENGL_FORCE_SRGB_FRAMEBUFFER=skip` on the GL legs and the E2E; vanilla 26.3 crashes natively on this PC's audio stack in most local launches (vg §1.8): local 26.3 runs set `ALSOFT_DRIVERS=null` and use vg §1.8's retry policy, and the 26.3 E2E runs in CI only.
  - On 26.3's Vulkan backend `GpuInfo.driverVersion` is MC's composed string (2D).
  - Both nodes run Sodium 0.9.2; Distant Horizons isn't in CI on either; fabric-client-gametest-api 6.0.2 (26.2) and 6.0.7 (26.3), networking 6.3.4 and 6.3.8 (sp §4).
  - No item needs a new `//? if` block; one that turns out to need one records it in its design doc.
- **X10 Launcher mode.** Every new mutation path is settings-only (C20, C09, C16) or reads P0.4's managed-mode signal (C02's wording). No P1 feature adds a mod-file operation.
- **X11 Tests and fixtures.** Every fix lands with a test that fails before it (the audit-verify and realworld throwaway tests are the starting point: av "Method", rw "Proof"). Each workstream commits its "written by 0.5" fixtures under `src/test/resources/v050-written/<set>/` from its own tests (seed, don't drive: the v0.4 H-M1 rule); 3b consumes them.
- **X12 Screens fit** 640×480, 854×480 and 1280×720 at GUI scale 2 (plus 854×480 at scale 3 where a list must scroll): a layout check (every widget inside the screen, no overlaps) and screenshots in the game test, looked at by the owner.

## 1. Rock-solid CI (P0)
Sources: ci §1-7 (541 runs classified; evidence in the r-ci scratch folder); PROGRESS "r-ci" row (coordinator decisions); the user's approval of changing the per-call ns budgets and how they are measured (PROGRESS v0.5, 2026-09-27).

**Problem.** Since the full v0.4 suite existed, 14 of 84 runs (1 in 6) failed on the first attempt for reasons outside the code under test: 9 outages (Maven Central 403, Modrinth maven 520, Mojang downloads, plugin resolution, Modrinth API 502/503 and timeouts) and 5 flakes (per-call ns gates, a screenshot race, a hang). At that rate five green runs in a row happen 40 % of the time (ci §4.1). Live Modrinth also silently changes which code path the game tests exercise: from 16:39 to 19:19 UTC on 2026-09-26 every lookup failed with `Stream N cancelled` and every test still passed on the offline path (ci §1.3).

This lands first and alone (Phase 3, the foundation); every later workstream builds on it.

### 1a. No live network in tests
- A "Resolve dependencies" step runs `./gradlew --no-daemon` with the prefetch init script from `research/v05-ci` (`.github/ci/prefetch.init.gradle`, or an equivalent task in build.gradle) that resolves every resolvable configuration of each node, logging and skipping one that can't resolve. It runs inside a bash loop of at most 3 attempts with 30 s / 90 s back-off. It is the only step that may retry a download; tests are never retried (build.yml's no-retry rule stays).
- Every later `./gradlew` runs `--offline`. The game-test step runs inside `sudo unshare --net` with only loopback up (the `offline-gametest` job of ci-experiment.yml, ci Appendix), so a new live dependency fails every run instead of on outage days.
- `release.yml`, `snapshot-canary.yml` and `update-rules.yml` stay online; they aren't part of the 5-run acceptance.

- AC1a.1 A Python test over `.github/workflows/build.yml` asserts: the prefetch step is the only step with a retry loop; every `./gradlew` after it passes `--offline`; the game-test command runs under `unshare --net`; no step uses `continue-on-error` for a test (unit, python job).
- AC1a.2 Proof on a scratch branch: a game test that opens a connection to `api.modrinth.com` fails on all 3 legs, and the identical branch without that test passes (2 CI run URLs in docs/v0.5/verification/ci/README.md; branch deleted).

### 1b. A local fake Modrinth for the game tests

- `tools/gametest/modrinth-candidates.json` (committed): the rules' candidate projects with fixed ids and dates, per-node `game_versions`, at least one "requires" relation and one "incompatible with Sodium" relation.
- Per node, a catalog task writes `build/gametest-modrinth/catalog.json`: the installed mods from `configurations.productionGameTestMods` (real sha1s, so they match what the game loads) plus the candidates, each with a tiny deterministic jar. A `ModrinthFixture` BuildService, next to `RulesFixtureServer`, starts `FakeModrinth.java --catalog … --bind 127.0.0.1 --port 0 --log build/gametest-modrinth/requests.jsonl`, reads the port from its "listening" line and destroys the process in `close()`. `runProductionClientGameTest` gets `-Drigtune.modrinth.baseUrl=http://127.0.0.1:<port>` (the property already ships, `HttpModrinthClient.java:45,71-77`; no test-only switch).
- build.yml uploads `requests.jsonl` with each leg's logs and fails the leg if any request to the fake was answered 5xx.
- PreviewGameTest's wait for the real preview drops from 6000 to at most 1200 ticks.
- DESIGN "RigTune's own footprint" says the 5 s worker window runs "against the local fake Modrinth".

- AC1b.1 FakeModrinthTest: `/v2/versions?ids=` returns exactly the requested catalog versions and omits unknown ids; the real `HttpModrinthClient` parses the answer over loopback http (unit, both nodes).
- AC1b.2 On each of the 3 legs, `requests.jsonl` shows the start-up requests (`version_files`, `version_files/update`, `projects`, `project/{id}/version`) answered 200 and no 5xx, and the game-test log has no "Modrinth lookups failed; using offline data" line outside the classes that switch Modrinth off (CI).
- AC1b.3 PreviewGameTest's real preview completes within 1200 ticks on every leg in every streak run (CI).

### 1d. Footprint per-call nanosecond gates (user-approved change)

## 4. RigTune never fights the launcher (P0)
Sources: lm (final: commits 376c1104, 11194d2c and 15184a28), rw §2 (RW-1, RW-2, RW-14), the brief's P0.4 decisions and the coordinator's final decisions on lm §8 (2026-09-27). Where PROGRESS's r-launchers row (written from lm's first draft) still says "Prism/PolyMC stay one-click", this spec follows the coordinator's final decision and the final lm: Prism/PolyMC are one-click only without packwiz metadata, because with it Prism's own update permanently deletes RigTune's `.disabled` jar and can leave one mod twice (lm §3.1).

**Problem.** RigTune 0.1-0.4 updates a mod by renaming the old jar to `.jar.disabled` and adding the new jar under Modrinth's file name. The Modrinth App 0.21 keeps its own row per file: the old row stays linked and disabled, with an update pending to exactly the file name RigTune wrote, and RigTune's jar becomes a second, unlinked row at that name. The app then refuses the update ("The updated filename belongs to another content item", `content_mutation.rs:266-278`), Update all stops at the first refusal, and rows are never pruned, so it stays broken until the old copy is deleted **in the app** (lm §1). It happened in the user's instance for the 4 mods 0.1.0 updated on 2026-09-25. Other launchers break differently (lm §3): GDLauncher's update of the old copy fails; Prism's deletes RigTune's `.disabled` jar for good; ATLauncher drops its record of a mod RigTune disabled; CurseForge's toggle is a record flag, not a rename. And the 0.4 helper recorded the app's own DH install as a RigTune change (RW-1), which a later Undo would act on (RW-2).

**Decisions applied** (the coordinator's final decisions on lm §8): per-instance evidence; one simple rule, "a launcher that keeps a per-mod record → advice", so GDLauncher is fully advice-only for mod files (lm had suggested updates only; its installer refuses an update when a row exists at the target name, `installer/mod.rs:290-316,836-850`) and there is no updates-only mode; the repair's primary step is "delete the old disabled copy in the app", with the three-step order (delete the new copy, update the old one, switch it on) as the fallback text; RigTune never moves its own old `.disabled` copies; held pending file groups are **held and offered** (never cancelled automatically); ATLauncher's `disabledmods/` convention is a later option, not v0.5; the old-client warning ships only if a compat test proves it reaches only 0.1.x-0.4.x, and there is no `minModVersion` cut-off; RW-1's fix is tested against the helper's crash-replay cases; the real Modrinth App check is the user's step, asked at the RC.

## 5. C20 Stutter Doctor one-click fixes (P1)
Sources: sf §1-9; bs §3 P1.1 and §9.1 (the critic: no confidence gating existed).

**Problem.** Stutter Doctor names likely causes and gives advice, but the player has to find the setting, change it by hand, and has no measured answer to "did that help?".

**Scope.** One-click fixes for three allowlisted settings only (`FixSpec.KEYS`); every other advice stays advice:

| advice (r16) | fix | takes effect |
|---|---|---|
| `stutter-sodium-defer` | `sodium.performance.chunk_build_defer_mode` → `ALWAYS` ("Deferred", Sodium's default) | next restart (staged PATCH_JSON) |
| `stutter-chunk-loading` | `vanilla.renderDistance` −2, never below 6 | now |
| `stutter-dh-threads` | `dh.common.multiThreading.numberOfThreads` −2, never below 1 | next restart (staged PATCH_TOML); **cut first** |
| `ram-stutter-gc-heap`, `stutter-gc-explicit` | none: the heap is the launcher's; `System.gc()` comes from a mod RigTune can't name | – |

This lifts v0.4's deferral of "Apply buttons on stutter advice" (2R, L20).

**Required behaviour.**
- **Evidence gate: three layers, all required** for "Try this fix…" to appear:
  1. the advice fired (the unchanged 0.4 path, including its 3-spike, 2-minute minimum);
  2. the client floor `core/stutter/FixGate` (constants in code; rules can only add to them): a monitor session, never a benchmark capture; at least 8 hitches (with 8 → 0 at equal play time a perfect fix reaches p = 0.0039; sf §1.3); at least 300 s of gameplay; the setting precondition (the key exists in this instance, its mod is loaded, `SettingKeys.changeable`, the effective value from `EffectiveSettings` differs from the target, and for render distance a live LAN/Realm/remote server doesn't already send no more than the target); no other fix staged or measuring; `stutter-fixes.json` writable;
  3. the rules' `evidence` condition evaluates TRUE (FALSE or UNKNOWN never offers) against the advice's own context, with one new key `causeSpikesAtLeast: {cause: n}` = at least n spikes in which that cause claimed at least half of the spike's lost time (UNKNOWN when the cause is unmeasured, unknown or not a whole number; UNKNOWN in the main list). Under SD-1's ring limits it only undercounts (the conservative direction).
- **Rules** (rules-v2 only, r17): a new lenient top-level section `stutterFixes` (`LenientSection`: a malformed entry drops only itself; an unreadable section becomes null and costs no advice). Entry fields per sf §2.2: `adviceId` (required, an existing `stutterAdvice` id, unique), `requires` (must contain `stutter-fix`, known only to `FixOffers.SUPPORTED_FEATURES`; an unknown feature skips the entry), `evidence` (required Condition), `set` (`key` from `FixSpec.KEYS`; `value` xor `step`; a `value` must decode in the key's ShareKeys entry; a `step` is a non-zero integer, |step| ≤ 8, needs `min` when negative and `max` when positive; target = clamp(current + step, bound, ShareKeys range)). - **Tracking and comparison**:
  - "Same conditions" (`FixConditions`): the MC version, the mod-set hash, the max heap and collector, the window size and fullscreen, every `ShareKeys.MANAGED` key plus `iris.shaderPack` except the fixed key (which must equal the target), the kind of world, and phase timing and the GC listener available on both sides. A differing session doesn't count; the block says why in one line.
  - Sessions of at least 120 s count; the after side accumulates to clamp(before gameplay, 300 s, 1200 s); 5 skipped sessions or 14 days → expired.
  - The comparison uses outcomes only, hitches per minute and lost ms per minute, never cause shares (the attribution rule itself changes with the Sodium fix) and never the 1 % low (SD-2). Quasi-Poisson: hitches binned per 60 s of wall time, dispersion φ = max(1, pooled variance/mean over bins with at least 3 per side), effective counts h/φ, a one-sided exact binomial test with p0 = after gameplay / total gameplay (log-space CDF, n capped at 100,000). Verdict: **less** (after rate ≤ 2/3 of before, p ≤ 0.05, lost ms per minute not higher); **more** (after rate ≥ 3/2 of before, p ≤ 0.05 the other way); otherwise **no clear change**. Every verdict shows both rates; "more" is shown with "Undo this change…".
  - The record follows the journal: staged → measuring (only once the change is in effect: at once for vanilla keys; for staged keys, the first session whose start has key = target and whose journal change is APPLIED) → compared; or undone (REVERTED), not applied (DISCARDED/ABANDONED), replaced (the key changed again), expired; an entry folded away stops tracking and keeps a computed verdict.

- **State**: `config/rigtune/stutter-fixes.json` on `StateStore` (X7): `formatVersion` 1, ≤ 32 KiB, ≤ 10 records (the oldest finished one goes first, never the active one), shape per sf §2.5; written only on StutterService's ordered io chain; the render thread never reads it. stutter.json is unchanged.

## 7. C16 Per-server profile offers (P1)
Sources: sp §1-9; bs §3 P1.3 and §9.3.

**Problem.** A player may want Quality on a small Realm with friends and Max FPS on a busy public server; Profiles holds one active profile and never remembers a per-place preference, so switching is manual every time.

**Required behaviour.**
- **Opt in per server**: Profiles → **Servers…** (row 3 becomes [Import code…] [Servers…] [Done]) opens `ServerProfilesScreen`, where "Offer %s here" takes the profile selected in Profiles, else the active one. Places: remote servers (`host:port`, lower case, default port written out), LAN guests (`lan:<host>`) and Realms (`realm:<world name>`), using `ServerLimitsTracker`'s kind and normalisation (`kind`/`address` made `public static`, a visibility change only). Never the player's own worlds, an Open-to-LAN host or the benchmark world.
- **On a later join** (Fabric's `ClientPlayConnectionEvents.JOIN`, at the end of `handleLogin`), when the mapped profile isn't active: at most one toast per server per game session ("Profile for this server" / "%s is set for this server. Press %s to switch.", the key from `RigTuneClient.openKey()`, an 8-second toast id) and the SERVER_PROFILE notice ("You set %s for this server. Switch to it?", actions **Switch** and **Don't offer here**, dismissible). A repeated JOIN with the same identity and no DISCONNECT is the same connection. **RigTune never switches by itself.**
- **The switch** is `ProfileService.switchProfile(id)`, unchanged: one `apply` entry labelled "Profile: X", Undo this/last/all, the existing clamps, refused by the shared busy check (C8) with the refusal as the toast; the offer stays until the profile is active, then retires. Settings only, so it behaves the same under every launcher policy. There is no switch-back offer on leaving (History's Undo and My settings are the way back).
- **Decision** (`core/profile/ServerProfilePrompt`, pure, in this order): NO_SERVER, NO_MAPPING, MISSING_PROFILE (a deleted or unknown profile: fail closed), ALREADY_ACTIVE, BENCHMARK (no offer while one runs), ON_BATTERY (on battery with Battery active: held, and the This-server line says why), OFFER.
- **Forgetting**: "Don't offer here" and "Stop offering here" remove the entry; × hides the offer for this connection only and writes nothing (`AwarenessService.dismiss` skips the per-join key); deleting a profile through Profiles removes its servers; a rename keeps the mapping (ids are `p-<uuid>`).

README's privacy list says "not stored in readable form" and nothing stronger (the salt is in the same file); the file never goes into a report.

No address, host or port is ever drawn or narrated.
- **Wording**: sp §2.6's keys (`rigtune.profile.servers*`, `rigtune.profile.server.*`, after `rigtune.profile.unnamed`).

**Cut order** (sp §9): the per-row list (keep the This-server line, Stop offering here and Forget all… with a count); the ON_BATTERY hold; the session-only × (store the key like other dismissals); `lastSeen`. Never cut: the SERVER_PROFILE slot above SERVER_LIMIT and the toast, fail-closed on a deleted/unknown profile, the switch through `ProfileService`, the no-plaintext checks, the two-connection game test, the downgrade fixture.

## 8. C02 First-time Apply trust flow (P1)

**Problem.** A first-time player sees a list of pre-ticked, unfamiliar settings with no idea whether Apply is safe or reversible, and after that first click nothing shows what changed or how to undo it (Apply shows only a status line; the "applied" toast comes at the next launch).

## 9. C18 Launch-time regression alerts (P1, first to cut)
Sources: la §1-9; bs §3 P1.4 and §9.4 (reuse `BenchmarkTrend`'s pure functions, not `assess()`).

**Problem.** On a big modpack, launch time can creep from 15 s to 40 s over updates; Tools shows only the last run, a median and a bare "mod set changed" flag.

**Required behaviour.**
- `core/footprint/StartupTrend` (pure): comparable = the same MC version only (a RigTune or mod-set change is an explanation, not a grouping; no Java version is stored, so none is claimed). Baseline = the newest `MAX_RUNS` (10 = `StartupTimesStore.MEDIAN_OF`) comparable runs before the latest; at least `MIN_RUNS` = 5 (launch time is noisier than benchmark FPS: ±7.5 % on one quiet PC, la §1.3). Floor = `BenchmarkTrend.noiseFloorPercent(null, baselineMs…)`, so at least 10 %, reusing `median()`/`mad()` directly, guarding an empty or too-small baseline. Kinds: NO_RUN, TOO_FEW, IN_LINE, IMPROVEMENT (computed, never shown in v0.5), SLOWER (the latest launch above the median by more than the floor). Cause, against the newest comparable run before the latest, first match only: mod count differs → MOD_COUNT; hash differs with the same count → MOD_SET; RigTune version differs → RIGTUNE_VERSION; else NONE. `MIN_RUNS` and the floor are **estimates** to revisit with real multi-launch data.
- `StartupTimes.View` gains the in-memory `assessment`, computed in `summarize()` on the existing off-thread path; `startup-times.json` is unchanged.
- The STARTUP_REGRESSION notice (C3; `client/notice/StartupRegressionNoticeSource`, key `startup.regression.<run at>`): "Launch time %s%% higher than usual (%s s vs your usual ~%s s)" plus one cause line ("May be related to your mod set changing (%s → %s mods) since your last launch", "…mod set changing since your last launch", "RigTune %s → %s since your last launch", or "No change recorded since your last launch; possibly another program running, a cold disk cache, or a driver/OS update"); actions **Tools…** (opens ToolsScreen) and **Got it** (stores the run's key in a new optional awareness.json array `acknowledgedStartupRegressions`, like `acknowledgedRegressions`); not dismissible otherwise. A later launch's own SLOWER assessment is a new key.
- ToolsScreen's startup detail adds the same regression and cause lines (existing `RowFocus.standalone` lines, `COLOR_NOTE`) while the latest run is SLOWER.
- Advice only: nothing is applied. Wording per la §1.4 (`rigtune.startup.regression*`, `rigtune.startup.notice.*`).
- **Decisions on la's open questions**: the notice gets a unit test through a static builder (as C16's `ServerProfileNoticeTest`) plus the game test; the floor reuses the benchmark constant (≥ 10 %) with `MIN_RUNS` 5, flagged as an estimate; no interaction with P0.4 (C18 changes no mod file). RW-16 (rw §12, vanilla's ~6 s wait on switched-off Windows performance counters at every launch) has its own advice (2L); C18's cause lines don't name it.

**Cut order** (la §9): Java/driver co-annotation (already out); the IMPROVEMENT display (already out); the notice's own unit test (fold into the game test); last, `MIN_RUNS` 5 and the launch-specific reasoning. C18 as a whole is the first P1 to cut.

- AC9.1 `StartupTrendTest`: fewer than 5 comparable runs → TOO_FEW, no cause; a run of another MC version never enters the baseline; a delta within the floor → IN_LINE; slower past the floor → SLOWER; faster past it → IMPROVEMENT; each cause and the first-match order; an all-identical baseline (MAD 0) doesn't divide by zero; one extreme baseline outlier doesn't blow the floor open (unit).
- AC9.2 A SLOWER assessment shows the STARTUP_REGRESSION notice with the numbers and exactly one cause line, "Tools…" opening ToolsScreen and "Got it" acknowledging; no regression is claimed anywhere with fewer than 5 comparable runs (unit on the builder; game test with a seeded startup-times.json in AwarenessGameTest, 3 legs).
- AC9.3 Got it persists `acknowledgedStartupRegressions`: the same run's notice doesn't return on a later screen init or a NoticeCenter rebuild, while a later SLOWER launch fires with its own key (unit + game test).
- AC9.4 startup-times.json's shape is unchanged (`StartupTimesFixtureTest` untouched and green); awareness.json gains only the optional array, 0.4.0 keeps it on its rewrites (compat040) and 0.5 reads a 0.4.0 file without it as empty (unit + CI).
- AC9.5 ToolsScreen shows the regression and cause lines while SLOWER, each a Tab stop that narrates its text (A11yGameTest's Tools block) (game test).
- AC9.6 LangCheckTest and WordingTest pass with the new keys (`rigtune.startup.*` stays under WordingTest's correlation prefixes) (unit).
- AC9.7 FootprintGameTest and FrameHookBudgetTest pass unmodified; C18 adds no render-thread hook (X4; footprint).
- AC9.8 Dev-PC check: several launches with no change raise no notice under the estimated floor; a launch after adding a batch of mods raises it with the right magnitude and the mod-count cause (docs/v0.5/verification/startup/; real run). ## Not fixed / deferred (with reasons)
- **L10** (a mod staged for disabling still counts as present for incompatibility checks): over-blocking is the safe side, and removing it would let a later Undo of the disable leave both mods active, since Undo's folder check covers `depends`, not incompatibilities (2H, Open question 2).
- **L11** (a top-level mod without a hash or file counts as nested): only a dev environment or a failed hash read produces it.
- **L12** (a dependency-level incompatibility between two additions refuses only the later one): one of the two is always refused and a bad combination never goes through; a consistency nicety, not a safety issue.
