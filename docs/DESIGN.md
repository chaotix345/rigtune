# RigTune: design

A client-side Fabric mod for Minecraft Java 26.2 and 26.3. It works out which mods and settings will get the most out of the player's hardware, and it keeps that advice current without needing a new mod release.

## Goals
1. **Detect the hardware**: CPU, RAM, JVM heap, GPU (vendor, model, VRAM, driver, graphics backend), display (resolution, refresh rate), and battery/laptop state.
2. **Scan installed mods**: use the Fabric mod ids (offline) plus jar hashes checked against the Modrinth API (for updates).
3. **Recommend** changes, each with a reason, an impact level, and a checkbox:
   - add missing performance mods that suit this hardware (e.g. Nvidium only on qualifying NVIDIA GPUs)
   - update outdated mods
   - remove obsolete or conflicting mods (Indium, Starlight, OptiFabric, both C2ME and Moonrise, etc.)
   - Sodium, Distant Horizons and Iris settings and vanilla video settings, by hardware tier and the player's goal (performance / balanced / quality)
   - advice outside the game: RAM allocation (which the launcher controls; since 0.3 with the detected launcher's own click steps) and GPU driver workarounds that Sodium applied
4. **Benchmark**: an in-game test that measures real frame times and tunes render distance (and, in singleplayer, simulation distance) to a target FPS (the recommended FPS cap: the multiple of 10 below the refresh rate, e.g. 180 Hz → 170, at most 240; measured uncapped on 1% lows). A dedicated benchmark world gives repeatable results without the player's own save, and a "measure before/after" mode reports the real gain from any change. Specs only give the starting point; the measurement decides.
5. **Apply**: vanilla settings take effect immediately. Mod file changes and config changes (Sodium, Distant Horizons, Iris) are staged, then applied safely after the game exits (see "Apply pipeline"), and every change is journaled so it can be undone. A **Preview** lists exactly what Apply would do, writing nothing.
6. **History and undo**: the History screen shows every journaled change and its status. Any RigTune change — a setting, a mod install/update/disable, a config patch — can be reverted by history entry ("Undo this"), for the last apply ("Undo last") or all at once ("Undo everything"), immediately or through the same post-exit helper as Apply.
7. **Stay current**:
   - **Live**: the Modrinth API reports mod availability and updates for the running MC version at runtime.
   - **Rules**: a JSON rules file hosted on GitHub is fetched at startup, with a cached copy and a bundled copy as fallbacks.
   - **Updater**: a scheduled GitHub Action regenerates the data parts of the rules from upstream curated packs (Fabulously Optimized, Additive) and the Modrinth API, then opens a PR for review.
8. **Let the player control the network use**: a settings screen with a master switch and finer switches for remote rules and Modrinth, so RigTune can be run fully offline.
9. **Stay useful after the first tune** (0.4), entirely on-device and inside a measured footprint budget: Performance Profiles with share codes, the Stutter Doctor, JVM and memory advice, benchmark history with regression alerts, server-aware advice, change awareness (hardware, driver, new rules) and a launch-time trend, all reached from one Tools hub and one notice line on the RigTune screen.

## Non-goals
- Changing the launcher's RAM allocation or Java arguments (we advise instead, with the launcher's own steps). Shader-pack tuning beyond advice and a shader-cost benchmark report (Iris' API gives no access to a pack's options or profiles; shader-pack option profiles were researched and deferred, docs/research/v0.4/profiles.md §7). Server-side optimisation. Loaders other than Fabric (Quilt: see the README's FAQ). Redo after an undo. Sending a bug report ourselves (Report a problem only opens a link the player confirms). Switching profiles by itself (the battery hook only offers). Recommending garbage-collector flags or a collector as an FPS gain (none measured one, docs/research/v0.4/jvm-gc.md). Saying which component limits the PC: tiers are estimates, and a benchmark measures only its own conditions. Per-mod startup times (Fabric Loader 0.19.5 records none).

Keeping the logic in `core/` means most behaviour is unit-tested without launching Minecraft. It also keeps the code that must be re-ported for each MC release small (just `client/`; see "Porting to new MC versions").

## Data flow
1. Client init: load the rules (bundled v2 → the v2 cache → 0.1.0's cache, read-only → remote v2, or remote v1 if that fails; the highest revision wins, ties broken toward v2, then remote over cache over bundled), probe the hardware once a GPU device exists, and scan the mods and every config namespace (Sodium, Distant Horizons, Iris). `OnlineLookupGate` triggers exactly one Modrinth lookup per scan-and-rules pair, from whichever of the two settles last, unless Modrinth is switched off; since 0.4 the lookup (and Apply's downloads) run on `Probes.NETWORK`, two daemon threads of their own, so a slow Modrinth can't hold up `Probes.EXECUTOR`'s short local work (History loads, Undo plans, report rebuilds, state-file I/O). Each scan also asks `LauncherProbe` which launcher started the game and `JvmProbe` what the JVM runs with (each detected once per session), and hands the probed hardware to `AwarenessService` for the change check.
2. Build a report in the background, including the Modrinth lookups: one bulk `POST /version_files` for installed hashes, one `POST /version_files/update` for updates, one bulk `GET /projects?ids=` to rule candidates out, and a `GET /project/{id}/version` check for each candidate that the project lists don't rule out. If Modrinth is unreachable or switched off, Add/Update recommendations become advice ("install/update it in your launcher") instead of a one-click action.
3. On the title screen, a small toast shows "RigTune: N suggestions" (unless the startup-toast switch is off). The button or keybind opens `RigTuneScreen`, which opens `RigTuneSettingsScreen` (Settings, also reachable from Mod Menu), `PreviewScreen` (Preview), `HistoryScreen` (History…, which opens `UndoScreen` for Undo this / Undo last / Undo all), `ToolsScreen` (Tools…, since 0.4 in Benchmark…'s footer slot: `BenchmarkMenuScreen`, `ProfilesScreen`, `StutterScreen`, `JvmScreen`, `BenchmarkHistoryScreen` and the launch-time line) and, for Report a problem, vanilla's confirm-link screen. One header line shows the top notice from `NoticeCenter` (evaluated on init/rebuild, never per frame) with "+N more", or a "…" button opening `NoticeScreen` below 400 scaled pixels.
4. The player ticks items and presses Apply. Vanilla settings are applied now, saved, and journaled with their before/after values. Mod, Sodium, Distant Horizons and Iris operations go into `config/rigtune/pending.json` as one group per recommendation, journaled as STAGED, and the screen tells the player to restart.
5. When the client stops, if there are pending operations, spawn `ApplyHelper` in a separate JVM (same Java executable, with copies of our jar and Gson on the classpath). It waits for the game process to exit, then takes the apply lock, applies the file operations, updates the journal (best-effort, and reachable only through core/Gson classes) and writes a result log.
6. On the next launch, preLaunch waits briefly for a helper that still holds the apply lock, then reads the result log and shows it, reconciles the journal (a STAGED change whose operation is no longer pending becomes ABANDONED), and — the very first time 0.2 runs against a 0.1.0 instance — imports 0.1.0's last apply as one `legacy-import` history entry. Operations that are still pending are reported and stay in `pending.json` for the helper at the next exit; since 0.4 a group the helper was killed in, or couldn't roll back, is finished or rolled back by that next run (see "Helper"). Since 0.3, preLaunch also logs one WARN line per op the helper's last run failed or dropped (the helper's reason, and "restart attempt n of 3" for a failed one), once per run (it remembers the run's `finishedAt` as `lastWarnedApply` in `rigtune.json`); the History screen shows the same reason next to the change.
7. Undo: on the History screen the player presses "Undo this" (the selected entry), "Undo last" or "Undo all"; `UndoScreen` shows exactly what `UndoPlanner` would revert (and what it would skip, with a reason). Confirming reverts settings immediately, stages file/config reversals the same way Apply does, and journals the whole thing as one new `undo` entry, which itself can't be undone.

## Apply pipeline (why a post-exit helper)
- On Windows, the loaded mod jars stay open, so they can't be renamed or deleted while the game runs.
- Loading two versions of the same mod id crashes Fabric Loader at startup. So an update must disable the old jar *and* enable the new one, both together, only after the game has exited.
- New jars are downloaded while the game runs to `mods/<name>.jar.rigtune-pending`, which Fabric doesn't load. Each download is checked against Modrinth's SHA-512.
- **File names**: a Modrinth file name must be a bare `.jar` name (no `/ \ :` or other characters Windows forbids, no control characters, no leading dot, no trailing dot or space, no reserved DOS device name such as `NUL.jar`, no 8.3 short-name alias such as `SODIUM~1.jar`, which NTFS could resolve to an existing jar), and the resolved path's parent must be the mods folder. Since 0.4 a Modrinth-supplied name (`requireJarName`/`resolveJar`) also may not hold any code point `LogSafe.hidden` flags (C0/C1 controls, bidi overrides and isolates, zero-width characters, BOM, lone surrogates, line/paragraph separators), and refusal messages escape them; the helper's own check of an enable target (`isSafeJarName`) doesn't, so an Undo re-enabling a jar the player named with a zero-width joiner stays possible. Otherwise the download is refused.
- **Which folders** (`InstanceDirs`): the mods folder is found the way Fabric Loader 0.19.5 finds it: `-Dfabric.modsFolder` if set (taken as given, so a relative value is relative to the working directory, as in Fabric), else `<gameDir>/mods`, then its real path. ModScanner, RealController and the helper all use this; the helper gets the game's value as `-Dfabric.modsFolder`. Folders are compared by real path, so a symlinked `mods/` works. The config folder is `<gameDir>/config`.
- **Which jars**: only jars directly in the instance's mods folder get file actions. A jar loaded from elsewhere (`-Dfabric.addMods`, a launcher-shared folder) still gets update checks, but the recommendation is advice only ("update it in your launcher").
- **Planning downloads** (`DownloadPlanner`): each Add/Update recommendation becomes one **group** (an update is {disable old, enable new}; an added mod is its jar plus the dependencies it needs); every enable records the jar's `fabric.mod.json` id.
  - Each recommendation works on its own copies of the installed projects and mod ids, committed only when it succeeds, so a failed one can't make a later one skip a dependency it never delivered.
  - A recommendation that needs a dependency an earlier one in the same batch staged joins that one's group (several groups merge), so the dependency is never applied or rolled back without its dependents.
  - An update whose target file name is already taken by another file is refused before downloading, as an added mod is.
  - Every update is planned before any addition (selection order kept within each kind), so tick order doesn't change the outcome (0.3).
  - Modrinth `incompatible` dependencies are judged against the state after the batch's updates (0.3, `DependencyResolver`): each staged update's new version joins the batch's version set, and its own `incompatible` entries are checked against installed projects and the batch, in both directions; installed mods' own entries are checked too. An addition that clashes only with the installed version of a mod whose update is in the same batch **joins that update's group** (both apply or neither); a failed update download is never committed, so the addition is then refused. An update whose Modrinth version is missing from the online data (it changed since the report was built) is refused before its download. Messages name the other project from local data (title, slug, then "another mod"), never a version id, and make no extra Modrinth call.
  - What earlier Applies staged (0.4, `StagedProjects`): `DownloadPlanner` records `projectId`/`versionId` on every ENABLE_FILE op, and `StagedProjects.read(pendingFile)` folds the still-pending ones into a separate set that only the incompatibility checks read (never the resolver's `seen`, so a dependant of a staged mod still resolves and joins its group). Forward: a new version declaring a staged project or version incompatible is refused ("… which is waiting for a restart"). Reverse: the staged versions are fetched once per plan (`GET /v2/versions?ids=`) and their own `incompatible` entries checked; with Modrinth off only the forward check runs. Staged DISABLE_FILE ops aren't folded.
  - Two ticked items that can't go in together (0.4, `refusedTogether`): ticked updates pairwise on their new versions, ticked additions pairwise on the rules' `conflicts` and their root versions, are refused together before any download, each naming the other; the rest proceed.
  - fabric.mod.json version ranges (0.4, `VersionPins`, `client/probe/FabricPins`): after the plan loop, every loaded mod's `depends`/`breaks` on a jar of the batch, and every new jar's own `depends`/`breaks` on what will be present, are checked with Fabric's own predicates over the folder the batch leaves behind (a declaration of a replaced jar goes with it; a target some new jar provides or nests isn't judged; pending.json's enables count as present). A group with a refused jar is dropped with its downloads, every recommendation in it gets a localised line naming the declaring mod, and this repeats until nothing is refused; reliance pairs are joined into one group. A pair of ticked items that rule each other out is refused together.
  - Only top-level jars count as present for the drop decision (0.4, `topLevelIds`: `sha1 != null || file != null`), so a library nested in another mod never makes the planner drop the standalone copy an addition needs.
  - An update whose new version requires a project that isn't installed, that the old version didn't require, is joined to an addition or earlier item that brings it, else refused (`missing_dependency`, or `missing_dependency_staged` when only an earlier Apply staged it). It doesn't resolve the update's dependencies itself (0.4, minimal fix).
  - An update's downloaded jar must carry the installed mod's id, or provide it (0.4, `not_same_mod`).
  - With Modrinth on and the installed mods not looked up yet (or the lookup failed), `plan()` refuses everything with `not_loaded` and asks nothing (0.4).
  - A failed recommendation's downloads that nothing else stages are deleted (0.4).
- **Sodium settings**: each value is checked against `sodium-options.json` as it is at staging, with the rules the patch uses, and a value that doesn't fit is reported as failed right away. The rest are staged one `PATCH_JSON` op per key, so one bad value can't block the others.
- **Staging** (`config/rigtune/pending.json`): each op has an id. Staging holds the apply lock and merges into the existing plan:
  - the plan's folders are derived from where `pending.json` is; the `modsDir`/`configDir` it records are informational only. Ops outside this instance's folders (a copied or moved instance) are dropped, and never touched.
  - a repeated change is dropped, and its group is joined with the new one
  - a newer enable for a mod id that already has a staged enable replaces it and takes over the rest of its group; the replaced pending jar is renamed to `<name>.jar.rigtune-superseded` and left inert
  - a config patch op repeats (and is dropped) only when it matches the *last* pending op for its file and key, so A → B → A for one key before a restart ends at A, not B (0.4; two profile switches leave two ops per key and the helper applies both in order)
  - a staged enable whose mod id is **loaded** and has its own update waiting in `mods/update/` (e.g. Distant Horizons' self-updater) is unstaged with its group on every rebuild and at exit (`Staging.dropQueuedUpdates`), because the two updaters would race for the same jar at exit; since 0.3 an addition or undo re-enable of a mod that isn't loaded is kept, and an enable staged without a mod id is matched by its jar's own id; since 0.4 a group the helper left half done is never unstaged this way. `StagedRecommendations` then keeps a recommendation staged only while one of its op ids is still in `pending.json`
- **Helper**: runs from copies of our jar and Gson in `config/rigtune/helper/`, because a JVM keeps its classpath jars open and Windows can't rename an open jar; running from `mods/` would block RigTune's own update. It waits (up to 15 min) for the game process to exit *without* the lock, so a game JVM that lingers can't block staging in a relaunched game, then a short settle delay (2 s) before it even tries to apply, giving anything that briefly grabbed a mod jar right at exit (the Modrinth App re-scanning the instance, an AV scanner) a moment to let go. Only then does it take `config/rigtune/apply.lock` (an OS file lock, so a killed helper releases it), which it holds while it reads the plan, applies it and rewrites `pending.json`. It:
  - derives the mods and config folders from where `pending.json` is, and refuses any op whose files aren't directly in that mods folder (or, for JSON patches, inside that config folder)
  - runs each group all-or-nothing: disables first; an enable only once the group's disables are OK or already done. Since 0.4 (H4) a group is tried as a whole: each op once per pass; when one fails, the rest are skipped, every rename of the pass is rolled back at once (the rollback has its own full retry budget), and only then is the whole group retried under the failing op's retry state, so between two passes the group is untouched. After a failed rollback the remaining ops are retried in place instead (roll forward), with one more full rollback once that budget is spent. A group that ends failed stays pending (minus ops that were already done)
  - records each pass's renames (op id, from, to; a disable's `.disabled` name is decided then) in `config/rigtune/unfinished-groups.json` before renaming anything, and keeps them until `last-apply.json` is written (0.4). At the next run a recorded rename still in effect counts as done (SKIPPED_ALREADY_DONE with its real `resultPath`): the group completes if the remaining renames succeed, or is rolled back entirely, the earlier run's renames included, if any op fails again. A refused group's earlier renames are rolled back; a dropped group (the mod was installed another way meanwhile) keeps them. A group left half applied (a FAILED result with a `resultPath`) is never abandoned: its `attempts` stop at 2 until a run ends it consistently. The record lives outside `helper/` because 0.1.0-0.3.0 empty that folder whenever they launch their helper (review-8 CR-1); a record a 0.4 dev build left at `helper/unfinished-groups.json` is still read once and then moved
  - before a group with an enable that carries a mod id, reads the `fabric.mod.json` id of every `*.jar` in the mods folder, ignoring jars the group disables. If the mod is already there (the launcher updated it meanwhile, or it was installed by hand), the group is **abandoned**: nothing is renamed and its downloads become `.rigtune-superseded`
  - renames pending files → `.jar`
  - renames removed or old jars → `.jar.disabled` (the Modrinth App's convention for disabled content, so it can be re-enabled from the launcher)
  - patches `config/sodium-options.json`, keeping each existing field's JSON type (a value that doesn't fit fails the patch)
  - re-reads `pending.json` and removes only the ops it ran successfully or abandoned (by op id), so ops staged meanwhile survive. Each failed op counts an attempt; when one reaches 3 failed runs, its whole group is abandoned
  - writes `config/rigtune/last-apply.json`; abandoned ops have status `ABANDONED`, and their downloads are renamed to `.rigtune-superseded`
  - writes in a crash-safe order (0.4, L2): the ABANDONED ops leave `pending.json` and the FAILED ones count a run; then `last-apply.json`; then the done ops leave `pending.json`; then the journal (best effort). A death before `last-apply.json` leaves the done ops pending, so reconcile keeps them STAGED and the next run redoes them idempotently; an abandoned op is out of `pending.json` before `last-apply.json` names it
  - a rename or patch write retries: a sharing violation (Windows denying it because something still has the file open) backs off exponentially (300 ms, doubling, capped at 5 s) up to a ~30 s total budget, since that kind of contention can outlast a few seconds; any other I/O error keeps the fast, fixed-delay retry (10 × 300 ms), same as a rollback undoing an earlier op in the group. Since 0.4 a failing op's retry is a retry of its whole group after a rollback (above), each op keeping its own retry state
  - writes `pending.json`/`last-apply.json` themselves temp-then-atomic-move, retrying the move (10 × 100 ms) while Windows denies it because an AV scanner, indexer or sync client has the file open
- **Next launch**: preLaunch tries the apply lock. If the helper still holds it, preLaunch waits up to 5 s and then shows a warning that changes take effect after another restart (Fabric has already picked the mod jars by then), rather than racing the helper. A toast reports the last result, including how many changes were dropped.
- **Discard pending**: while `pending.json` exists, the RigTune screen shows a "Discard pending" button. Under the apply lock it renames every staged download to `.rigtune-superseded` and deletes `pending.json`. Since 0.4 it keeps a group the helper left half done (`PartlyApplied`: a rename recorded in `unfinished-groups.json` in effect while another op of the group is left, or, for a failed rollback, a disable done after a helper attempt while its enable isn't), so the next exit finishes it instead of leaving the mod missing.
- Nothing is ever deleted (the only exception is a just-downloaded duplicate that no staged op uses), so every change can be undone (see "Undo").
- If the helper never runs, the pending files stay inert, which is safe.

### Journal, undo, and the new config patch ops
- **Journal** (`config/rigtune/history.json`, `core/history/Journal`): every Apply, benchmark "Keep" and Undo is one journal entry, holding the (now reentrant) apply lock and written atomically. It holds at most 50 entries (0.4, M6, `Journal.cap`): the oldest finished entries (nothing staged, and either an undo or nothing applied) are dropped first; then the oldest run of at least 2 consecutive entries with nothing staged (never the newest entry) is folded into one `baseline-<uuid>` apply entry that keeps what Undo all needs (per setting, the chain from the oldest `before` to the newest `after`, stopping where the player changed it in between, at most two changes per key; every applied mod-file change as it was); only when no such run exists are the oldest unstaged entries dropped. A 400-seed property test checks that Undo all plans the same script on the capped and the uncapped history. To 0.3.0 the baseline is an ordinary Apply. Each change records its `before`/`after` and moves `STAGED` → `APPLIED`/`ABANDONED`/`DISCARDED` as `pending.json` and the helper's result evolve. The helper's own journal update runs through core classes and Gson only (never `RigTune.LOGGER`, Fabric or MC classes), so the helper's classpath stays just our jar and Gson; a mistake here is caught by running the helper in a child JVM with only those two on the classpath.
- **Config patch ops**: alongside Sodium's `PATCH_JSON`, new `PATCH_TOML` and `PATCH_PROPERTIES` ops patch `config/DistantHorizons.toml` and `config/iris.properties` the same staged, validate-at-both-staging-and-apply-time way. The TOML patcher never infers a value's type from the *incoming* string — only from what's already in the file (a quoted key vs. a bare one) — and refuses a mismatch, because DH writes doubles and enums quoted but ints and booleans bare; guessing from the new value's shape could silently write a value DH's own parser can't read.
- **Retry policy**: a *sharing violation* (a file still briefly open right after the game exits — the Modrinth App re-scanning the instance, an antivirus scan) backs off exponentially (300 ms, doubling, capped at 5 s) over a ~30 s budget; every other `IOException` keeps the original fixed 10 × 300 ms retry. Rollback (undoing an earlier op in a group after a later one fails) uses whichever policy applies, with its own full budget; since 0.4 a failed op's retry is a retry of its whole group after a rollback. The helper also waits 2 s (not 1 s) after the game process exits, before it even tries to take the apply lock, to give anything that briefly grabbed a jar right at exit a moment to let go.
- **Undo** (`core/history/UndoPlanner`, `client/undo/UndoService` + `UndoScreen`): "Undo last apply" is the newest entry with anything left to revert; "Undo everything" is every entry. A staged change is removed from `pending.json` by op id, taking its whole group with it (a dependency can't be dropped while a dependent stays); an applied change is reverted only if nothing has changed it since ("you changed it since" otherwise), checked against a simulated mods folder so a whole reversal sequence (e.g. an update chain a→b→c undone back to a) is checked as one. A reversal is skipped rather than applied if it would leave two active jars sharing a mod id, or drop a `depends` mod id nothing else provides. Settings revert immediately; mod/config reversals are staged and applied by the same post-exit helper as Apply. The undo itself is one journal entry and can't be undone.
  - Since 0.4: every file op of one undo is staged in **one** group (H5), so a failed rename can't leave a mod active without its library; when a second undo in the same start relies on a staged op of the first, it joins that op's group, or waits ("restart once, then undo it") when it relies on an ungrouped op or several groups. A staged key's current value is its last still-pending staged op, not the file's value (2n), so a second Undo last of a staged Sodium/DH/Iris key reverts it. A reversal whose file a still-staged op moves at the next exit waits instead of reporting the file missing, and Undo last stops at that entry rather than undoing an older one (M3); an entry part of which waits is undone whole or not at all. A group the helper left half done (see Discard pending) is skipped with `waits_partly` (M2, review-8 AH-1).
  - "Disable X" on the RigTune screen goes through `DisableGuard` → `FolderCheck.disableRefusals` (0.4, M5 and H1-B): refused when X's disable is already staged in a group that brings the same mod back, or when a jar left active would miss a mod it depends on (the Apply's disables checked as a set); one toast names the reason and the rest of the Apply goes ahead. `FolderCheck.problems` is also UndoPlanner's folder check, so Undo and Apply refuse the same folders.
- **History screen** (0.3, `core/history/HistoryModel`, `client/ui/HistoryScreen`): the journal's entries newest first (kind: Apply, Benchmark result, Undo, Imported from 0.1; local time; RigTune and MC version; a count summary) in one accordion list, since at 640×480 GUI scale 2 the screen is too narrow for two panes. Rows: a setting as "<label>: <before> → <after>" with the Undo screen's labels; "Added / Disabled / Re-enabled <file>"; a disable plus an added enable with the same group, mod id and status as "Updated <mod>: <old file> → <new file>". Statuses: Applied, Waiting for restart (STAGED), Not applied (ABANDONED), Cancelled (DISCARDED), Undone (REVERTED). A STAGED change whose op `last-apply.json` marks FAILED shows the helper's reason and "try n of 3 at restart" (n = the op's `attempts` + 1); an ABANDONED one "Not applied: <reason>". Reasons have the instance's folder paths cut to file names. Since 0.4 a change staged by 0.4 records the mod's own `name` (`JournalChange.modName`, from the jar's fabric.mod.json, sanitised: no `§`, no control or format characters, at most 64 code points) and rows show it instead of the file name; a profile switch shows as "Profile: <name>" from `profiles.json`'s label map; Undo last / Undo all are active only when something is undoable. An empty, corrupt, newer-format or unreadable `history.json` (`Journal.state()`) shows a read-only message; reading never writes or backs anything up. No `history.json` format change.
- **Undo this** (0.3, `UndoPlanner.planEntry`): one entry, planned by the same `build()` as Undo last, so `recheck()` re-checks it at confirm time. A **superseded** pass runs first: a selected change is skipped ("Changed again by a later apply") when a later non-undo entry, not itself in the plan, has a STAGED or still-APPLIED change to the same settings key, the same file name (either direction) or an enable of the same mod id, and its group is skipped with it. Changes of one plan never supersede each other, so Undo everything is unchanged. Restoring `graphicsPreset` (which rewrites a dozen options) writes back every vanilla option whose latest RigTune change is still in effect and that the plan doesn't set, so undoing an older entry can't overwrite a later one's options; the dependency check sees the staged ops the undo leaves in `pending.json`.

## Rules (v2, with a safe v1 projection)
0.2+ clients read `rules/rules-v2.json` (`schemaVersion: 2`): more condition fields (`gpuModelMatches`, `displayPixelsAtLeast`/`displayPixelsAtMost`, `modVersion`, `mcVersionRange`), `settingLabels` for recommendation titles, and three-valued (TRUE/FALSE/UNKNOWN) evaluation that fails closed — an unknown condition field anywhere in a rule's condition tree makes the whole rule not fire, rather than silently matching or not matching.

0.1.x clients still read `rules/rules-v1.json` (`schemaVersion: 1`). The same updater run that writes `rules-v2.json` also writes a conservative *projection* of the same knowledge into v1 terms — a rule that uses a v2-only feature is either rewritten (an explicit, hand-checked `v1` override), or left out, never silently weakened — so a 0.1.x install can never get a less safe recommendation after the 0.2.0 rules go live. A differential test runs the pinned 0.1.0 recommender over the old and new `rules-v1.json` across a hardware × mods × goal matrix to catch a regression automatically.

0.4 (rules revision 14 and later) adds, all in `rules-v2.json` only: two top-level sections, `profileTemplates` (the five profile templates) and `stutterAdvice` (entries `requires: ["stutter-doctor"]`, evaluated only by `StutterAdvisor`), which 0.2.0/0.3.0's parsers ignore; the `driverVersion` condition, which poisons a condition to UNKNOWN on 0.2.0/0.3.0 (`LegacyConditionFailClosedTest`); the stutter condition keys, accepted only inside `stutterAdvice`; `jvm-*` advice with `requires: ["jvm-flags"]` (0.2.0/0.3.0 support no features, so they skip it) testing `jvm-` flag facts that are UNKNOWN until the JVM probe has run (`jvm-probed`). The updater refuses a v2-new key in a clamp, an `avoidWhen` or a `skipUpdateWhen` without a `requires` (not firing is conservative only for advice and value entries), and a settings rule with both `value` and `min`/`max`. The only 0.4 change 0.1.x sees is the VSync suggestion made optional and the two reworded reasons.

The full field list, the client's candidate list and `pickNewest` tie-break, and the v1 projection rules are documented in [docs/RULES_SCHEMA.md](RULES_SCHEMA.md); the maintainer workflow (the hand-written source, the updater, `REVIEW.md`) is in [tools/README.md](../tools/README.md).

## Hardware tier
- Tiers run from 1 to 5, computed as `min(gpuTier, cpuTier, memTier)`. Since 0.4 it is shown as an **estimate**: "Estimated tier N/5 · lowest estimated component: CPU", naming every tied component, never "limited by" or similar wording (`WordingTest` checks en_us.json and the share report). `Report.tierBasis` (`TierBasis`) says per component whether it came from a table row ("table match") or the fallback formula ("fallback estimate from 16 threads", `CpuClassifier.classifyDetailed`), and the badge's tooltip shows it with the last benchmark's line.
  - gpuTier comes from the regex table in the rules. Software renderers get tier 0, which triggers a critical warning.
  - cpuTier comes from logical cores and the max clock, plus a bonus for known cache-heavy parts (X3D).
  - memTier comes from the JVM max heap.
- The player's goal (performance / balanced / quality) shifts the effective tier by −1, 0 or +1 when picking settings.

## Benchmark v2
Two scenes: **current** (the player's world and position, as in 0.1) and the dedicated **benchmark world** — a singleplayer save named `rigtune-benchmark` with a fixed seed, camera spot, time (frozen at noon) and weather (clear), created on demand from the title-screen benchmark menu and reused across runs (recreated only if its recorded MC version or seed no longer matches). Since 0.3 the camera is at the terrain floor from the noise + 16 (y 133 on 26.2 and 26.3) instead of 10 above the highest motion-blocking block, which depended on a tree; if the camera block or the one above isn't air it falls back to the old rule, never lower. A game test checks the scene with `SceneVariety` (not mostly ocean, not flat, at least two biomes) on every supported version and logs its fingerprint, so a worldgen change in a new Minecraft version is noticed. Two modes: **Tune** and **Measure** (no tuning, just measures the current settings — used for before/after).

1. Remember the current settings and hide the GUI. Test values are set in memory only; options.txt is written once, with the original values, when they're restored. Creative flight is toggled client-side only, so the server never stores it. Lift the frame-rate limit to unlimited (260), turn vsync off and set the inactivity limit to `minimized` so the AFK throttle (30 FPS after 60 s without input) can't kick in.
2. **Tune**, under a ~5 minute deadline (coordinate descent, one knob at a time):
   - render distance: `RenderDistancePlanner` — for each candidate, set it, tell the server the new render distance (`Options.broadcastOptions()`, no options.txt write), then wait until every chunk within RD − 1 of the camera (a circle, capped at the server's limit) is on the client and the sections have compiled, or a 20 s timeout (`SettleCheck`); a step that timed out with more than 2% of those chunks missing never counts as meeting the target. Then a 360° camera sweep at two pitches (level, then 25° down), 8 s each, while recording frame times; it raises the render distance while the 1% low stays at or above the target FPS, otherwise lowers it, and stops after 6 steps or when the search converges;
   - in the player's own world (the current scene) Tune tests at most 8 above the starting render distance (`BenchmarkSession.maxRenderDistance`), because each tested distance makes the server load, generate and save that much more of the world; the benchmark menu says so. The benchmark world keeps the full range;
   - simulation distance (singleplayer only): a cheaper 3-point local search (current, −2, −4) that only lowers it below the current value when doing so beats it by a clear margin, since it's also a gameplay setting;
   - the chosen settings are measured twice more, and the coefficient of variation of the two 1% lows is reported (a result "was noisy, close background apps and retry" warning above 5%);
   - **Distant Horizons and shader cost reports**: one extra measurement each with DH rendering off, then with shaders off (DH back on in between), each always restored right after — these are reports of what the feature is costing, not something the benchmark auto-disables. A report whose feature refuses to switch off, or that the deadline cuts, is shown as "not measured" rather than a number.
3. **Measure**: two repeats of the current settings at the fixed scene, no tuning — the "before" and "after" of a before/after comparison.
4. Restore the camera, GUI, Distant Horizons/Iris state and original settings on every exit path (Esc, a disconnect, a world or player change, an exception in the benchmark, or the client stopping). A crash-safety marker (`config/rigtune/benchmark-restore.json`), written before DH or Iris is ever changed, is retried at the next launch if a restore didn't finish; DH's `renderingEnabled` turned out to persist to `DistantHorizons.toml` itself (not purely an in-memory API override), so the restore writes the *original* value back explicitly rather than just clearing an override.
5. The result screen shows the target, the result and a noise warning if relevant, the DH/shader cost lines, and a small chart (`config/rigtune/benchmarks.json`, the last 50 runs kept; since 0.4 the chart shows only runs comparable with the latest, see "Benchmark history and regression alerts (0.4)"). **Measure before** (saved with a pair id) → the player applies recommendations, restarting if needed → **Measure after** (same scene and MC version) reports "1% lows: +X% (avg +Y%)", or "no significant change" when the gain is within twice the larger of the two runs' noise. Since 0.3 the result screen also shows a read-only shader advice (`ShaderAdvice`: the shader cost was measured, the 1% low misses the target only with shaders on, and the pack takes at least 10% of the shaders-off 1% low; it suggests a lighter profile in the pack's settings and writes nothing), and each new run in `benchmarks.json` has an optional `context` (DH rendering, shaders, shader pack, framebuffer size, fullscreen, protocol 1; `schemaVersion` stays 1, and 0.2.0 reads the file unchanged) so comparable runs can be told apart later. Since 0.4 the context also carries `modSetHash` (SHA-256 over the loaded non-builtin mods minus RigTune itself, `ModSetHash`) and `journalCursor` (the newest history.json entry id), both optional.

Esc cancels at any point and restores everything, as do a disconnect, a world or player change, an exception in the benchmark, and the client stopping.

## Settings and network switches
`config/rigtune/settings.json` (`client/ClientSettings`) is deliberately its own file, separate from `rigtune.json`, so a 0.1.x downgrade (which only knows the old file) can't reset it on a later re-upgrade. It holds: `networkEnabled` (the master switch — off means no request of any kind, of anything below), `remoteRules`, `modrinth` (lookups, update checks *and* downloads), `startupToast` (the title-screen suggestions toast), the default `goal`, `benchmarkScene`, and since 0.4 `stutterMonitor` (default off). A missing or partial file gives defaults for whatever's missing.

`RigTuneSettingsScreen` (opened from the RigTune screen, or from Mod Menu's config button) edits it directly: every change is saved at once through `SettingsSaver` (0.4: its own single daemon thread, rapid changes coalesced into one write of the latest values, a pending write flushed at CLIENT_STOPPING, so a slow Modrinth on the shared worker pool can't delay it), and the three network switches also call `settingsChanged()` (reloads the rules, then rescans). Gating happens at two seams so every call path is covered by one check apiece: `core/modrinth/GatedModrinthClient` wraps every Modrinth call and refuses it (before touching the delegate) while `modrinth` is off — installed-jar lookups, update checks (including RigTune's own self-update), availability checks, dependency resolution and downloads all go through it — and `RulesSources` checks `remoteRulesAllowed()` before each rules request. With Modrinth off, Add/Update recommendations keep their title, category and impact but become advice ("install/update it in your launcher") instead of a one-click action; with the network master off, the RigTune screen's header says "Offline (network off in settings)".

## Launcher-aware memory advice (0.3; MultiMC, GDLauncher and Java-arguments steps in 0.4)
- `core/launcher/LauncherDetector` decides from injected signals; `client/probe/LauncherProbe` fills them with exactly these names and runs the detection on `Probes.EXECUTOR` once per session (the signals can't change while the game runs). Each caller waits at most 3 s; a timeout or any Throwable is Unknown, and a result that arrives late is used by the next rescan. Signals: the system properties `org.prismlauncher.instance.name`, `multimc.instance.title` and `minecraft.launcher.brand`; the environment variables `INST_ID` and `INST_NAME`; the files `instance.cfg`, `mmc-pack.json` and `minecraftinstance.json` in the game dir and its parent (absolute, normalized, nothing higher).
- Order: (1) `org.prismlauncher.instance.name` → Prism Launcher; otherwise `multimc.instance.title` or `INST_*` → MultiMC (0.4; PolyMC sets only `INST_*`, so it is named MultiMC, and MultiMC's steps fit it word for word); (2) brand `theseus` → Modrinth App, `ATLauncher` → ATLauncher, `GDLauncher` → GDLauncher (0.4); (3) the game dir, then its parent: `instance.cfg` with an `InstanceType=` key next to `mmc-pack.json` → Prism, `minecraftinstance.json` → CurseForge (with its top-level `isMemoryOverride` when readable); (4) brand `minecraft-launcher` → the official launcher; (5) Unknown. The official brand comes after the files because CurseForge starts the game through the official launcher and passes the same brand.
- Files: opened only if `Files.isRegularFile` (a FIFO or a directory with that name never is); `instance.cfg` ≤ 64 KiB, checked before opening; `minecraftinstance.json` streamed through Gson's `JsonReader` over a stream that fails after 32 MiB, reading only the top-level `isMemoryOverride`. `MaxMemAlloc`/`allocatedMemory` are never read: `Runtime.maxMemory()` already is the effective value.
- UI (`client/ui/LauncherLines`): with a known launcher the header's memory line names it ("Memory 2.0 GB of 16 GB, set in the Modrinth App"), and every advice whose recommendation id starts with `advice:ram-` (rule ids `ram-*`, a convention documented in RULES_SCHEMA.md) gets "In <launcher>: <steps>", one lang key per launcher. The Modrinth App, Prism, MultiMC, ATLauncher and GDLauncher get the instance's own memory steps; CurseForge gets the pack's Profile Options steps ("choose Custom RAM Allocation", a radio button) unless `isMemoryOverride` is false, then the app's global Java settings; the official launcher, the installation's JVM arguments (Mojang's own path, "Installations → select the installation → More Options → JVM Arguments … Save"). Since 0.4 every `advice:jvm-` recommendation gets "Found in your Java arguments: <flags>" and the launcher's Java-arguments steps (`rigtune.launcher.jvm_steps.*`, all seven launchers), and in the Modrinth App and GDLauncher, where a typed `-Xmx` beats the memory slider (`LauncherInfo.typedXmxWins`), the `ram-*` advice adds a note when the JVM probe saw two `-Xmx`. Unknown leaves the screen as in 0.2. `ShareReport` adds `- Launcher: <name>` for a known launcher and nothing else about it.
- Sources: the brand literals from the launchers' source (Modrinth App, ATLauncher), Minecraft's bytecode and public crash reports (official launcher, CurseForge); the Modrinth App, Prism and ATLauncher steps from their UI strings at a pinned release; CurseForge's and the official launcher's steps from CurseForge's blog and third-party guides, not source-verified (docs/v0.3/design/ws-c.md). 0.4 (docs/research/v0.4/launcher-steps.md): MultiMC's labels from its source (0.6.16), GDLauncher's from Carbon's source, and CurseForge's and the official launcher's from their own support and help articles, not from the closed-source UIs.

## Preview (0.3)
- `PreviewScreen` (Preview, right after Apply, active exactly when Apply is) gets exactly Apply's selection (`RigTuneScreen.ticked()`, which Apply uses too). Sections: written now (options.txt), changed at the next restart (Sodium/DH/Iris keys, old → new), downloaded now and added at the next restart, renamed to `.disabled` at the next restart, and not changed (with the reason). Paths are relative to the game folder.
- It reuses Apply's code rather than a second set of rules: `core/preview/PreviewPlanner` partitions the selection exactly as `RealController.apply`'s switch does (the one duplicated piece; `PreviewDifferentialTest` replays that switch against the real staging classes and the helper's executor, and PreviewGameTest runs the real Apply); vanilla values go through `SettingsBridge`'s checks (`problems` runs the option's own parse and range check without setting anything); config values through the same stagers, which only read the file; `.disabled` names through `ApplyExecutor.disabledTarget`; downloads through the real `DownloadPlanner` and `DependencyResolver` via `DryRunPlanner`, whose fetcher returns a path that is never created, with a `LookupOnlyClient` that throws on `download()`, and on every call while Modrinth is off.
- Limits: a download's mod id is known only once it's downloaded, so the preview can't show Apply's download-time outcomes (not a Fabric mod, already loaded, two jars of one mod, and since 0.4 a fabric.mod.json version range another mod doesn't allow) and says so; since 0.4 setting rows use the main list's labels and value names (the same `HistoryModel.Labels` as History); `vanilla.graphicsPreset` (which no rule sets) rewrites other options at Apply, and only the preset is listed; Modrinth's answers can change between Preview and Apply. Previews run one at a time on their own daemon thread, never on `Probes.EXECUTOR`.

## Report a problem (0.3)
- The button copies the full `ShareReport` to the clipboard, then calls `ConfirmLinkScreen.confirmLinkNow(screen, uri)`, vanilla's confirm-before-open screen, with a link built by `core/report/IssueLink`: `issues/new?template=problem.yml&title=<…>&report=<…>`, form-encoded (`+` becomes `%2B`; every RigTune version contains one). RigTune makes no request itself; only if the player picks Open in Browser does the browser's GET give GitHub what's in the link.
- `MAX_URL` is 675 characters: 15 rows of 45 of the widest glyph the encoder emits, in the confirm screen's 270-pixel text width at 640×480 GUI scale 2 (the smallest layout), so the whole link can be read before it's opened. A report that doesn't fit is cut at a line boundary with "(shortened; the full report is on your clipboard)", or left out; the title is dropped rather than overflowing. The link never carries `labels`/`assignees`/`projects`/`milestone` (a value the visitor can't set makes GitHub 404 the whole link).
- `.github/ISSUE_TEMPLATE/problem.yml` is an issue form (`what-happened`, `expected`, `report`; `labels: ["bug"]`). GitHub reads issue templates from the default branch, so the form needs it on main.
- Minecraft's Copy to Clipboard on the confirm screen replaces the report on the clipboard with the link; the README's FAQ says to press Copy report again.

## Localisation (0.3)
- `core/model/Text` (sealed, no Minecraft imports): `Translatable(key, fallback, args)`, `Literal(value)` (data, never translated) and `Joined(separator, parts)`. `english()` formats the fallback exactly as Minecraft's `TranslatableContents` does (checked with javap on 26.2 and 26.3); `client/ui/Texts` renders a Text through `Component.translatableWithFallback`, so a language file's template is used when it has the key and the English otherwise. `TextException extends IOException` carries a Text for refusals the UI shows.
- Text sits next to the existing Strings (`titleText()` beside `title()`, and so on): no existing signature changed, and nothing persisted (`pending.json`, `last-apply.json`, `history.json`, `benchmarks.json`) and no class on the helper's path changed. Converted: Recommender's own titles and reasons, ModrinthOffAdvice, UndoPlanner's descriptions and reasons, DependencyResolver's and DownloadPlanner's refusals, Preview. English by design: rule-provided titles, reasons and advice, mod and file names and values, network and helper-path error details, the share report and the logs; recommendations are still sorted by their English title.
- `LangCheckTest` (a JUnit source scan with a small Java lexer) fails on a string literal with letters in `literal(...)` or in client UI code (outside an allowlist), a key used in the code but missing from `en_us.json`, an unused `en_us.json` key (dynamic families are enumerated from their enums), a `Text.of` whose English differs from `en_us.json`, and any other language file that isn't a flat object of strings with a subset of the keys and the same arguments. A pseudo-locale check renders core-built text through an uppercasing translator. No full translation ships in 0.3: nobody here can check one, and rule text stays English.

## Performance Profiles and share codes (0.4)
- A profile is a value map over a fixed keyset (`ShareKeys.MANAGED`: the share table plus the two local-only thread counts), never `graphicsPreset` or `iris.shaderPack`. "Optional mods" are Distant Horizons rendering and Iris shaders as settings; no jar is enabled or disabled.
- **A switch is an ordinary Apply.** `ProfileSwitch` makes `SetSetting` recommendations for the keys the instance has (never creating one) that pass `SettingKeys.changeable` and differ, and `RealController.apply(selected, entryId)` journals them as one `apply` entry; `profiles.json` maps that entry id to the label ("Profile: Battery"), which `HistoryModel.withProfiles` shows. Undo this/last/all need no change, and 0.3.0's UndoPlanner undoes switch entries. Refused while downloading or while a benchmark runs. `ActiveProfile` voids the active marker once the switch's entry has nothing applied or staged left.
- Current values (switch, Preview, templates, Save current) come from `EffectiveSettings`: a staged key reads as its last still-pending op, else the file's value.
- **Templates** (`ProfileTemplates`) are computed on demand in layers: the baseline ("My settings", auto-saved the first time Profiles opens or before the first switch) → the rules' value entries evaluated with the template's goal and forced facts (`Recommender.settingTargets`, extracted with `recommend()` output unchanged, checked by a 240-scenario golden report) → the template's own entries from rules-v2 `profileTemplates` (else the bundled rules' section, else a built-in copy) → every clamp → table bounds. Templates never see server limits. Saved and imported profiles get the rules' clamps for this PC too ("My settings" doesn't), and Preview lists each clamp.
- **Share codes**: `RT1-` + base64url without padding of (body ‖ CRC32 big-endian); the body is a format byte, a name (≤ 64 bytes UTF-8) and up to 64 (key index, value) pairs as unsigned varints over `ShareKeys`' frozen, append-only v1 table (30 keys; the two thread counts are local-only and never emitted). No strings but the name, no paths, mod ids or floats. Decoding is strict and ordered: size caps before anything (4096 raw, 700 stripped characters), code shape, version, canonical base64url, CRC, exact pair count and no trailing bytes, canonical varints, duplicates rejected, unknown keys skipped and counted, known keys range-checked. Names are sanitised (`ProfileNames`: NFC; Cc, Cf, Co, Cs, Cn, Zl, Zp, `§`, `=`, `#`, `"` and `\` dropped; ≤ 32 code points) and only ever rendered as literals; profile ids are `p-<uuid>`. `ShareCodeFuzzTest` flips every byte of the golden codes and throws 100,000 random bodies at the decoder. Import always goes through the PreviewScreen confirm overload (Apply / Save only / Cancel); the clipboard is read only on Paste.
- **Battery**: `PowerWatcher` (thread "RigTune power") starts only when the startup probe found a real battery, polls every 30 s and counts a change after 2 polls; `BatteryPrompt` decides (an AC → battery edge, a 10-minute cooldown, not snoozed, no benchmark, Battery not active; back on AC it offers the previous profile). The offer is a notice plus a toast; RigTune never switches by itself.

## Stutter Doctor (0.4)
- **Capture** (`client/stutter/`): `DebugScreenOverlayMixin`'s frame hook calls `StutterMonitor.onFrame`, which writes allocation-free primitive rings that exist only while a capture runs (one volatile read when off); `MinecraftFrameMixin`'s 7 phase-timer injectors (packets, ticks, render, limiter) are `require = 0, expect = 0`, and phase attribution is on only when every required hook fired, else the report says "Phase timing unavailable". `GcListener` is registered on the GC beans only while capturing; `GcClock` maps each pause to [start + offset, end + offset + 1 ms] with offset = min(receive − end) over the session (the receive time is never the pause time). A 4 Hz daemon `ThreadSampler` ("RigTune stutter sampler") groups thread CPU by name; `BuildBacklog` reads Sodium's builder counters through guarded MethodHandles, with vanilla's compile queue as fallback. Fabric events give world saves, level changes (the next 10 s are excluded), teleports and fast movement (tags), menus and an unfocused window (excluded).
- **Analysis** runs off the render thread when StutterScreen opens (and every 5 s while it's open) on copies of the rings. Spike: d > max(2b, b + 8 ms, 20 ms) with b the median of the previous 120 non-spike gameplay frames; a run of 60 spikes re-baselines. `Attributor` apportions the lost time GC → packets → ticks → render, each capped at what's left; rendering claims milliseconds only as chunk building and only with evidence (a Sodium backlog, the vanilla compile queue, or Chunk Updates set to wait); saves, Distant Horizons, CPU contention, teleport, fast movement, loading and (review-8/P5A-F2) chunks loading within 250 ms of the spike are tags that never claim milliseconds; "not explained" is always shown. Every frame in the frame ring keeps a 32-bit phase word (packets/ticks/render excess over the baselines, rounded down, and its chunk loads), so a spike keeps its measured phases even when later candidates push its candidate record out (review-8 ST-2); the frame and phase baselines re-warm after an excluded span or pause of at least 1 s (ST-3).
- **Advice**: `StutterAdvisor` is the only evaluator that supports `stutter-doctor`; the stutter keys evaluate against `StutterFacts` and are UNKNOWN in the main list. Facts fail closed on what wasn't measured (GC counts without the listener, the GC share without calibration, phase shares without phase timing). No verdict or advice below 3 spikes or 2 minutes of gameplay.
- The benchmark always captures during its sweeps (a smaller ring, analysed at the end of the run, one line on the result screen); a running session pauses during a benchmark, and a session a benchmark interrupted is saved only with 2 minutes of gameplay (P5A-F3), so the run's own capture is the summary shown afterwards. `ThreadSampler.stop()` never joins its thread (each start gets its own worker, which stops writing once its rings are taken; review-8 ST-1), so turning the monitor off can't stall the render thread. `stutter.json` keeps 5 session summaries, each with at most 10 worst spikes, ≤ 64 KiB, through one ordered chain of writes (a Clear can't be undone by an older save). **Copy summary** escapes rule-sourced titles with `MarkdownSafe`.
- The monitor is off by default (`settings.json` `stutterMonitor`); on, it holds 2,506,752 bytes of rings (about 2.5 MB) and gives them back when it stops.

## JVM & memory advice (0.4)
- `client/probe/JvmProbe` reads `RuntimeMXBean.getInputArguments()`, `HotSpotDiagnosticMXBean.getVMOption`, the GC beans, the heap sizes, the version and vendor once per session on `Probes.EXECUTOR` (callers wait at most 3 s; every call guarded; the HotSpot-only code in a nested class, so OpenJ9 turns the check off instead of failing). `core/jvm/JvmArgs` keeps flag names, heap sizes and `-D` names only, never a value, so no path can reach the screen, the log or the share report; `JvmFinding` refuses anything but a flag name.
- `JvmFlagClassifier`: IGNORED (getVMOption doesn't know the flag), OVERRIDDEN (a boolean reads back differently), plus curated rows (young generation fixed under G1, a typed Serial/Parallel collector, Epsilon, Aikar's set by marker or at least 4 of its 7 distinctive flag names, `DisableExplicitGC`, two `-Xmx`). Launcher-injected arguments are recognised and ignored. Facts go into `HardwareProfile.flags` under `jvm-`; `jvm-probed` is set only when the probe really read the options and GC beans, and every `jvm-` flag in a rule is UNKNOWN without it (so a `not` can't fire before the check ran).
- Advice lives in the rules (`jvm-*`, `requires: ["jvm-flags"]`, `"v1": false`); every number in it traces to docs/research/v0.4/jvm-gc.md's measured table (checklist in docs/v0.4/design/ws-j.md). No advice adds a GC flag or proposes a collector for FPS. Copy report gets one line: "Java: 25.0.3 (vendor), G1, 2 argument notes".

## Benchmark history and regression alerts (0.4)
- **Comparable** (`BenchmarkHistory.comparable`, `BenchmarkTrend`): the same MC version, scene, render and simulation distance, and `Context.sameConditions` (width, height, fullscreen, shaders and pack, DH rendering, protocol). The mod-set hash is not part of it (it feeds the rerun marker and the change window). Runs without a context compare only with each other.
- **Noise floor** = 2 × max(latest cv or 5 %, 1.4826 × MAD / median) over the baseline, the newest 10 comparable runs with a result *before* the latest, at least 3. A drop past the floor is a regression, a rise an improvement (never an alert), anything else "in line with your usual". With fewer than 3 comparable runs, "different conditions … cause unknown" is said only when the previous run of the scene differs past the noise; otherwise nothing is claimed.
- **Change window** (`ChangeWindow`): the History entries between the baseline's and the latest's `journalCursor` (by time when a cursor is gone), only rows that took effect, including staged changes that took effect at the restart in between; "RigTune A → B" for a version change, "Something outside RigTune changed too (the mod set differs)" when the hashes differ with no mod-file row, "No change recorded; possibly a driver, OS or other change" when there is nothing.
- **Stale marker** ("Needs a rerun"): MC version, RD, SD, resolution (under 10 % of the pixel count counts as the same), fullscreen, shaders or pack, DH, and the mod set. The regression notice isn't dismissible (acknowledging it stores the run id in `awareness.json`); the stale notice is dismissible per run. The tier badge's tooltip and Copy report show the last benchmark with its conditions. Dates are yyyy-MM-dd.

## Server-aware advice (0.4)
- `ClientPacketListenerMixin` (TAIL of `handleLogin`, `handleSetChunkCacheRadius`, `handleSetSimulationDistance`, `require = 1`, the same on 26.2 and 26.3) and its accessor feed `ServerLimitsTracker`, which keeps the live limits and the kind (singleplayer, including an Open-to-LAN host; LAN guest; Realm; remote); DISCONNECT clears them, and the report rebuilds on join, disconnect and a change.
- `core/recommend/ServerCap` runs on the finished main-list report only (never inside `settingTargets`, so templates never see it): with target T, current C and limit L, T > C becomes min(T, max(C, L)) with "The server sends at most L chunks."; capped down to C, the recommendation is dropped (the notice explains); T ≤ C is untouched. RigTune never proposes a decrease because of a server.
- `ServerLimitsStore` (`server-limits.json`, ≤ 32 entries) keys each server by HMAC-SHA256 with a random 16-byte salt created once and kept in the file: `host:port` (lower case, default port written out), `realm:<world name>`, `lan:<host>` (an Open-to-LAN port changes every time). Singleplayer is never stored, the store only feeds "(was N)", and the file never goes into a report. The docs say the addresses are "not stored in readable form" and claim nothing stronger, since the salt is in the same file.
- The notice's key names only the limit, never the server.

## Change awareness (0.4)
- `DriverVersionParser` never throws and returns UNKNOWN for anything it doesn't recognise: on OpenGL AMD Adrenalin ("Context YY.M.rev.build"; the pre-2024 five-part form stays UNKNOWN), Mesa, NVIDIA and Intel "Build a.b.c.d"; on 26.3's Vulkan the leading API version is dropped and NVIDIA's number, a Mesa version or AMD's "AMD proprietary driver X.Y.Z" (from the Phase 5 capture) is read.
- The `driverVersion` condition is TRUE/FALSE only when the detected vendor is the rule's and the string parses as that vendor's own driver family, so a Mesa version is never compared with a proprietary range.
- `Fingerprint`/`ChangeDetector` (on `AwarenessStore`): GPU (vendor or normalised renderer) before driver (parsed versions in the same family, else raw strings on the same backend) before CPU or RAM (≥ 512 MB). The first run, a corrupt file or an unusable fingerprint seed silently; an OpenGL ↔ Vulkan switch alone moves the stored fingerprint on silently, and across such a switch parsed versions are compared only on the parts both backends report (GL `550.54.14` vs Vulkan `550.54`; review-8 JW-2). A change is committed once its notice is shown (checked per screen tick against the top notice, or listed on NoticeScreen) or dismissed; these dismissals last the session only, so a recurring change isn't hidden for good.
- `WhatsNew`: the baseline is a rules revision plus the ids that revision *could* produce, so goal changes and newly installed mods never count as new; an older revision (a downgrade, a lost cache) isn't news.

## RigTune's own footprint (0.4)
- `client/FootprintStats` measures RigTune's own startup (wall and render-thread CPU of preLaunch and `onInitializeClient`, the CLIENT_STARTED handler) and the CPU of every "RigTune…" thread in the 5 s after CLIENT_STARTED. `FootprintGameTest` (every CI leg, after the other feature classes) adds the tick hook, notice evaluation, a class histogram and heap after full GC before and after 20 screen open/close cycles (leak suspects must be 0), and the session monitor on and off in a world; `FrameHookBudgetTest` times the frame hook with the monitor off, on, and on with the phase timers. Both read `tools/footprint-budgets.json` and fail past a budget.
- Budgets are 2 × the largest value observed in calibration, never above SPEC 10's ceilings as amended: render-thread init 400 ms wall / 150 ms CPU (the time is class loading, mostly Gson in preLaunch), the phase-timed frame 400 ns, the sampler 120 ms per 60 s. The render-thread CPU is clamped to its wall time (Windows reports thread CPU in 15.625 ms steps). `HttpModrinthClient` builds its HttpClient lazily, never on the render thread. Retention is gated by explicit accounting (`StutterMonitor.retainedBytes()`, leftover instances) rather than heap deltas.
- Without compressed oops (ZGC, or heaps over 32 GB) the shallow-size budget (`rigtuneClassBytesIdle`) doubles, capped at its ceiling (`FootprintBudgets.forCompressedOops`, P5A-F5); the leak checks don't change.
- `client/footprint/StartupTimes` records launch-to-title (`RuntimeMXBean.getUptime()` at the first TitleScreen per JVM) in `startup-times.json` (last 30 runs, ≤ 16 KiB) with the versions, the mod count and the mod-set hash (`ModSetHash.ofLoadedMods`, RigTune left out, the same hash as the benchmark's; review-8 BF-1); Tools shows the last run, the median of the last 10 and a "may be related" note when the hash changed. Fabric Loader 0.19.5 has no per-mod timing, so there is no attribution.

## Porting to new MC versions
All MC-touching code lives in `client/`, and it uses Fabric API events rather than mixins wherever possible. The recommendations themselves don't need a port; they arrive through the rules file.

One jar can't serve two MC versions: `InputConstants` key codes are compile-time constants that javac inlines (F8 is 297 on 26.2, 65 on 26.3), and classes move between packages. So each version is compiled separately from one source tree with [Stonecutter](https://stonecutter.kikugie.dev/) 0.9.8:

```
settings.gradle                  Stonecutter plugin; versions '26.2', '26.3'; vcsVersion (the committed state, 26.2)
stonecutter.gradle               root script: the active version, Loom declared once, run tasks ordered by version
build.gradle                     per-version script, run once for each versions/<mc>/ (stonecutter.current.version is <mc>)
gradle.properties                shared properties (loader, Loom, mod_version)
versions/<mc>/gradle.properties  minecraft_dependency (the fabric.mod.json range), fabric_api/modmenu/iris versions, optional sodium_version
src/                             shared by every version, in the active version's state
versions/<mc>/build/             rigtune-<mod_version>+mc<mc>.jar, generated sources for the non-active versions, test reports
```

Version-specific code is a comment conditional at the call site: `//? if >=26.3 {` … `//?} else {` … `//?}`, with the inactive branch commented out (a braceless `else` covers one line). Predicates are semver, so `>=26.3` also matches 26.3.1. Prefer an API that exists on every version over a conditional; the shipped code has these today: the key type in `RigTuneClient`, the GPU device imports and the refresh rate in `HardwareProbe`, `RowList`'s 26.2-only hover narration fix (`//? if <26.3`), and `BenchmarkWorld.terrainFloor`'s 26.4 snapshot API (`//? if >=26.4-alpha`).

A node's `minecraft_dependency` is `~<mc>` for a release (it accepts that version's hotfixes and rejects the next drop) and `~<base>-` for a pre-release node, which isn't shipped; never an open-ended `>=`. `sodium_version` is optional: without it the node builds and runs its tests without Sodium. CI's game-test legs (`tools/gametest_matrix.py`) and the release's Modrinth uploads loop over `versions/*/`, so a new node needs no workflow edit.

Adding a version (details, the tools' checks and the hotfix steps: `tools/MC_VERSIONS.md`):
1. When Fabric announces the version, read its blog post. Upgrade Loom and Gradle on their own first if it asks.
2. Run `python tools/add_mc_version.py <mc>` (it checks the Mojang manifest, Java 25, Fabric meta, Fabric API, Mod Menu, Sodium and Iris, adds the node to `settings.gradle` and writes `versions/<mc>/gradle.properties`), then `./gradlew :<mc>:build`.
3. Fix compile errors with `//? if >=<mc> {`; for a break a snapshot or pre-release introduced, use `>=<base>-alpha` (Stonecutter compares pre-release ids as text, so `26.4-pre-1` sorts below `26.4-snapshot-1`). Run `python tools/mc_apidiff.py <prev> <mc>` and review every changed class, including reflection targets, the mixin target, `Options` keys and runtime defaults.
4. Run `:<mc>:runClientGameTest` and a production smoke test.
5. Review version-specific rules. Regenerate the rules for all supported versions.
6. Update docs and the changelog. Run `./gradlew "Reset active project"` and commit on a feature branch.
7. Tag a release. CI builds and publishes every node.
8. For each later hotfix: bytecode-compare (`mc_apidiff.py` with both nodes built), then `PATCH` `game_versions` on Modrinth.

To move the committed state to a newer version, change `vcsVersion`, `stonecutter.active` and the version checked in `.github/workflows/build.yml` together.

Dropping a version: remove it from `versions`, delete `versions/<mc>/`, and delete the conditional branches only it used (Stonecutter doesn't prune them).

## Safety
- The mod never touches files without an explicit Apply. Everything is reversible (`.disabled`, never deleted) and, since 0.2, explicitly undoable through the journal (since 0.3 from the History screen: Undo this / Undo last / Undo all). Downloads are hash-verified. Modrinth requests carry a descriptive User-Agent, a byte cap, a stall timeout and an overall deadline, and results are cached.
- Network failures fall back to offline behaviour and never block startup; the player can also switch any network request off entirely (see "Settings and network switches").
- 0.4's features (profiles, share codes, Stutter Doctor, JVM advice, benchmark history, server-aware advice, change awareness, the launch-time trend) open no connection and work with the network off (each game-test class runs its main case with `networkEnabled = false`). Anything that changes a setting goes through `RealController.apply` → journal → Undo; the advice-only features write only their own new files. Share codes are untrusted input: strict decoding (size caps before decoding, canonical base64url and varints, CRC, exact pair count, range checks) with a fuzz test, and names sanitised and shown only as literals. Text from outside RigTune (rules, mod names, setting labels, driver strings) is drawn through `SafeText`/`SafeLiteral` (formatting codes, control, bidi/format, private-use, surrogate and unassigned characters dropped; review-8 SE-2) and Markdown-escaped on the clipboard (`MarkdownSafe`); JVM arguments are never stored as values, so nothing downstream can show or log a path. Log lines name config files relative to `config/rigtune` (`LogSafe`), not by absolute path.

## Deviations (apply/modrinth/benchmark)
- **Modrinth API (verified live 2026-09-24)**: `GET /v2/projects?ids=` accepts ids and slugs mixed and silently drops unknown ones, so an unknown candidate slug is left out of `availableBySlug` (unknown) rather than marked unavailable. `/version_files` and `/version_files/update` return maps keyed by hash and omit unknown hashes. `GET /project/{id}/version` returns 404 for an unknown project, and `latestVersion` maps that to `Optional.empty()`. Response ordering isn't documented, so versions are sorted by `date_published`.
- **Errors**: `ModrinthClient` methods throw `IOException`. `ModrinthException extends IOException` and carries `statusCode()` and `rateLimited()` (429).
- **HTTP limits** (`core/net/BoundedHttp`): `HttpRequest.timeout` only covers the wait for headers, so every body is read through a capped subscriber with a stall timeout and an overall deadline, after which the exchange is cancelled. Downloads: file size + 1 KB when Modrinth gives a size, 256 MB at most, 30 s stall, 10 min deadline. JSON: 16 MB, 30 s stall, 60 s deadline. Error bodies are truncated at 64 KB. A 429 is retried once after `Retry-After` (seconds or an HTTP date; `X-Ratelimit-Reset` as a fallback; 1 s if neither), waiting 10 s at most.
- **OnlineDataFetcher**: `fetchAll` returns `Result(OnlineData, projectIdsByModId)`, and `fetch` returns just the `OnlineData`. It skips an "update" whose version was published before the installed one, which guards against a downgrade when a build is mis-tagged. `UpdateInfo.currentVersion` is the installed Modrinth `version_number`. It sends no `version_types`, so a newer beta or alpha can be offered as an update. Failures are logged before it falls back to offline data. Since 0.3 `Result` also keeps each installed and update version (with its dependencies) by version id and a version id → project id map, for the resolver's post-update view and Preview, and every Modrinth game-version query uses the raw version (`FabricLoader.getRawGameVersion()`, falling back to the normalized one), which the normalized version (still used for `mcVersionRange`) differs from only on snapshots and pre-releases. The offline availability map from the bundled rules is keyed by Modrinth's version tags but looked up with the normalized version, so it misses only on a snapshot.
- **Availability**: project `loaders` and `game_versions` are unions over all versions (a mod with Fabric only for 26.1 and NeoForge for 26.2 lists both), so a project-level miss means unavailable but a hit only means "maybe". Each hit gets `GET /v2/project/{id}/version?loaders=["fabric"]&game_versions=[mc]` (via `latestVersion`), 4 at a time; a compatible version with a file means available, none means unavailable. A failed check leaves the candidate unknown, and after a 429 the remaining checks are skipped.
- **DependencyResolver**: breadth-first, root first, default depth 5. It throws `IOException` when the root or a `required` dependency has no compatible version. It ignores Modrinth dependency version pins and uses the latest compatible version instead (since 0.4 the fabric.mod.json ranges of the jars are checked separately, `VersionPins`). Required dependencies that have only a `version_id` are skipped; an `incompatible` entry naming a version applies to that version only.
- **PendingActions**: each op is one flat record (`type` plus nullable `from`/`to`/`path`/`patches`, and `id`, `group`, `modId`, `attempts`). Paths are stored as strings and `createdAt` as an ISO-8601 string. Ops without a group (including plans written before groups existed) run on their own; ops without an id are matched by value. The executor never overwrites an existing `ENABLE_FILE` target (that op fails instead), and within a group it runs `DISABLE_FILE` ops first, so an update whose new file name equals the old one works.
- **ApplyExecutor**: groups run in order of their first op, and results are reported in plan order. A sharing violation retries with the exponential backoff described above; every other `IOException` uses the fixed 10 × 300 ms retry, and so do rollbacks (a failed rollback is reported in the op's message, since 0.4 with its `resultPath` and "the next exit finishes or rolls back this change"). Since 0.4 the helper's messages read "Gave up after N tries" and "Gave up after 3 restarts". Malformed JSON/TOML/properties or bad op fields fail immediately. A `PATCH_JSON`/`PATCH_TOML`/`PATCH_PROPERTIES` op isn't rolled back by a later failure in its group, but it runs last (RealController never groups a config patch with anything that could still fail after it). A `PATCH_JSON` that changes nothing is `SKIPPED_ALREADY_DONE`, and a missing `sodium-options.json` is created from `{}` (the TOML/properties patchers refuse a missing file instead, since DH/Iris must have run once to create one). The mods and config folders come from where `pending.json` is (`InstanceDirs`), whatever the plan records, and `last-apply.json` goes next to `pending.json`.
- **ApplyHelper**: exit codes are 0 (all done), 1 (some ops failed or were abandoned), 2 (bad args) and 3 (game still running after 15 min, the apply lock still held by someone else after 60 s, or interrupted). On a timeout it applies nothing and leaves `pending.json` for the next launch.
- **HelperLauncher**: `launch(configDir, pendingJson)` uses the current pid and truncates `config/rigtune/helper.log` on each run. The classpath copies are named `<n>-<file name>`; an identical copy is reused, a copy still in use by an older helper gets a fresh name, and other files in the folder are deleted (0.4: except a dev build's `unfinished-groups.json` there, kept until the helper moves it to `config/rigtune/`). Class directories (development runs) are used in place. If copying fails the helper isn't started, and the plan stays pending. RigTune offers updating or disabling its own jar only when it runs from a jar (`HelperLauncher.selfUpdateSupported`).
- **SodiumConfigPatcher**: an existing boolean accepts only `true`/`false` (any case), an existing number only a number (a whole number when the current value is one), an existing string any text; objects and lists are never replaced. A new field gets an inferred type.
- **Remote rules**: the body is capped at 2 MB (15 s stall, 30 s deadline), a larger cache file is ignored, and an `OutOfMemoryError` while parsing counts as an invalid document. `gpuTiers`/`cpuTiers` patterns over 200 characters are dropped, and matching runs on a `CharSequence` that throws after 1,000,000 character reads, which counts as no match.
- **RenderDistancePlanner**: upward steps are +2, +4, +8… from the last pass. A pass recorded above the lowest failing RD is treated as noise, so the result stays conservative. A step recorded as incomplete (its settle timed out with more than 2% of the chunks missing) never passes, and the best-effort fallback ignores it while any complete step exists.

## Deviations (client)
- **ModScanner** keeps nested jar-in-jar mods in the list with a null file and hash, as `InstalledMod` documents, so rules see every real mod id (never `provides` aliases). Only top-level jars are hashed and sent to Modrinth, and only jars directly in `mods/` get a `file`.
- **SettingsBridge** drives the private `Options.processOptions(FieldAccess)` through a `java.lang.reflect.Proxy`, because `FieldAccess` is package-private. Writes validate against the option's `ValueSet` before `set()` (an invalid value would otherwise reset the option to its default), and `graphicsPreset` is applied before any other key so explicit values win.
- **Entry buttons**: on the title screen the button sits left of Options; on vanilla video settings right of Done. Sodium replaces the video screen and its page list swallows clicks, so there the button goes bottom-left and claims its clicks through `ScreenMouseEvents.allowMouseClick`.
- **Keybind** (F8, unused by vanilla) works in game only, like every vanilla key mapping; menus use the buttons.
- **Benchmark HUD** is attached after `VanillaHudElements.SLEEP`, the one layer vanilla still draws while the GUI is hidden.
- **Benchmark render distance cap**: the server's view distance only caps the search on a remote server (since 0.4 read through `ClientPacketListenerAccessor.serverChunkRadius`, no reflection on `Options`; a Tune whose highest step the server lowered says so on the result screen). In singleplayer `IntegratedServer` copies the client's render distance into the view distance every tick, so it would otherwise pin the search to the starting distance. The chunks the server sends a player follow that player's *requested* view distance, though, which only changes when the client broadcasts its options; that's why every benchmark step broadcasts (see "Benchmark v2").
- **Benchmark in client game tests**: the harness syncs with the test thread on every frame that runs a tick, so those frames (about 1% of frames at ~2000 FPS) are slow and the 1% low reads far below the average (e.g. avg 1914, 1% low 234 on an RX 7800 XT). The numbers are uncapped but not representative of normal play.
- **AddMod** downloads are checked for a `fabric.mod.json` id that is already loaded and dropped if so, since a second top-level jar with the same id stops Fabric from starting. An id that is only staged isn't dropped: the newer jar replaces the staged one when merged.
- **Client game tests** need no extra build config: the `fabric-api` POM pulls `fabric-client-gametest-api-v1` in transitively even though the fat jar doesn't nest it. `runClientGameTest` starts from a fresh run directory each time.
