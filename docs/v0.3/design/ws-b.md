## Decisions
- **Superseded rule (B-H1).** A selected change is SKIP "Changed again by a later apply" when a change of a *later* (higher index) non-undo entry, not itself part of the plan, is STAGED, or APPLIED and not being reverted (an undo change with `reverts` pointing at it is STAGED or APPLIED), and touches the same thing: the same settings key; file changes whose `{file, resultFile}` names intersect; or the later change is an enable of the selected change's mod id. Every other selected change sharing a group with it (its journal `group`, or for a staged change the group of its op in pending.json) is SKIP "Goes with a change a later apply changed again", so a group stays all-or-nothing. Changes of the same plan never supersede each other, so Undo everything is unchanged (every later candidate is in the plan), and Undo last only changes in its fall-through case (the newest entry's plan is all skips and an older one is picked), which is the case the review found broken. It runs inside `build()`, so `recheck()` applies it at confirm time (a download of a later apply that finished in between is caught: `recheckSkipsAChangeALaterApplyChangedSinceItWasShown`). At confirm time every change the list showed, skips included, counts as part of the plan, so the confirmed Undo everything matches the shown one (self-review M1).
- **Two more guards for undoing an older entry (self-review H1, H2).** Restoring `graphicsPreset` rewrites the preset's options (review M7 wrote back only the options the plan skipped); now every vanilla option whose latest RigTune change is still in effect and that the plan doesn't set is written back as it is, so Undo this on an older entry can't overwrite a later entry's options. This also fixes a v0.2 gap: the confirm-time re-plan selects only the reverted changes, so M7's write-back of the options the list showed as skipped was lost at confirm time. And the dependency check (review M9) now sees the staged ops the undo leaves in pending.json, which the helper runs first at the next exit: an older entry's undo can't disable a jar a later entry's staged mod depends on (`undoThisKeepsAJarALaterStagedModNeeds`).
- **"Fully undone" (B-L1).** Undo this is offered for an entry that isn't an undo and has a change that is STAGED, or APPLIED and not being reverted (the planner's own candidate rule). Such an entry can still end up with only skips (e.g. superseded); the Undo screen then says "Nothing here can be undone; the reasons are listed", which is more useful than a disabled button. Legacy-import entries are undoable like applies, as they are for Undo last.
- **planEntry's empty cases.** An unknown id, an undo entry, or an entry with nothing left gives `UndoPlan(false, null, [])` (the same "Nothing to undo" as today's empty Undo last); `undoOf` is null so nothing is journaled.
- **Journal.state() has a fifth value, UNREADABLE**: an existing history.json whose read threw an I/O error (locked by another program, a directory). It isn't CORRUPT (update() doesn't back it up; it throws), and "empty" would be wrong. The screen shows "Could not read RigTune's history; see the log." `state()` logs through `Journal.Log` only (helper-safe); HelperLauncherTest passes. `update()` returns false for it rather than writing. Reading never makes the `.bad` backup; the corrupt message says RigTune keeps a copy "when it next writes the history" (B-M2).
- **Failure reasons (3e, B-M1).** A STAGED change whose op is FAILED in last-apply.json shows "Last attempt failed: <reason> (attempt n of 3)", n = the op's `attempts` + 1 (the op records the count from before that run). An ABANDONED change whose op is ABANDONED there shows "Not applied: <reason>". A change in any other state never shows an old reason. The reason is the helper's own English message with the instance's mods and config folder paths cut to bare names (`C:\…\mods\x.jar -> …` becomes `x.jar -> …`), which also keeps the user name out of latest.log. For an update row the disable's reason wins: the disable runs first, and the enable's is "Not applied because disabling x failed".
- **WARN lines once per run (B-M1).** preLaunch logs one line per FAILED/ABANDONED op, naming the helper run (the first 0.3 start may log a result 0.1.x/0.2.x left long ago), e.g. `RigTune's helper couldn't apply a change (run finished 2026-09-24T23:09:01.530708800Z, attempt 1 of 3; it's retried at the next exit): DISABLE_FILE fabric-26.2.jar: Gave up after 10 attempt(s): java.nio.file.FileSystemException: fabric-26.2.jar -> fabric-26.2.jar.disabled: The process cannot access the file because it is being used by another process`, then remembers `finishedAt` as `lastWarnedApply` in rigtune.json (a new optional field; 0.2.0's Gson ignores it, and a 0.2.0 save drops it, which only means one repeat of the lines after a downgrade and upgrade). A run with no failures writes nothing. When preLaunch finds the helper still running (it couldn't get the lock), it skips the lines: the helper writes a newer result.
- **Rows.** A setting is "<label>: <before> → <after>" with the same labels as the Undo screen (`GameState`: the option caption / the rules' settingLabels and value labels), "(none)" for an absent value. An enable is "Added <file>", or "Re-enabled <file>" when it `reverts` a change (an undo's). A disable is "Disabled <file>". A disable plus an added (not re-enabled) enable of one entry with the same group, mod id and status is one "Updated <mod>: <old file> → <new file>" row (B-L1); an undo's disable + re-enable pair stays two rows, because it is a revert, not an update. File names are shown, not mod names: the journal records only the file and mod id.
- **Statuses.** Applied (green), Waiting for restart (STAGED, yellow), Not applied (ABANDONED, red), Cancelled (DISCARDED, grey), Undone (REVERTED, blue), Unknown for anything else.
- **Layout.** One accordion list (the selected entry opens up under its row) instead of two panes: at 640×480 GUI scale 2 the screen is 320×240 scaled pixels, too narrow for side-by-side panes. The newest entry is selected when the screen opens. A click selects on the next tick so the list isn't rebuilt inside its own click handler. The footer uses the RigTune screen's balanced button rows: Undo this, Undo last, Undo all, Done. Undo last and Undo all stay always active, as they were on the main screen; the Undo screen explains an empty or unavailable plan. The screen reloads its model (off the render thread) when it opens and whenever it comes back from an Undo screen, keeping the selection (by id) and the scroll position.
- **Main footer (X-M2).** "History…" takes the place of "Undo last" and "Undo all", so the main footer has one button fewer than in 0.2 (Apply, History…, [Discard pending], Benchmark…, Rescan, Copy report, Done). WS-F adds "Report a problem" right after "Copy report". The existing `rigtune.screen.undo_last`/`undo_all` keys (and tooltips) are reused by the History screen's buttons.
- **Text.** Every word is an en_us.json key under `rigtune.history.*` (43 keys, inserted in alphabetical order after `rigtune.header.display_rules`). Data (file names, mod ids, versions, times, the helper's reason) is inserted as arguments. HistoryScreenTest checks the set of `rigtune.history.*` keys the sources and the model use equals the set en_us.json defines. UndoPlanner's new skip reasons are English strings like its existing ones; WS-G converts them with the rest (G-H1).
- **No format change.** history.json, last-apply.json and pending.json are read as they are. rigtune.json gains the optional `lastWarnedApply`.

## API for WS-H (B-M3: the e2eUndo per-entry case)
- `default @Nullable UndoPlan RigTuneController.undoPlanFor(String entryId)` (package `io.github.chaotix345.rigtune.client.ui`; returns `io.github.chaotix345.rigtune.core.history.UndoPlan`), implemented in RealController: the plan for "Undo this" on that history.json entry (call it off the render thread; RealController reads the mods folder and marshals the options read to the render thread itself). RealController never returns null: an already-undone entry, an unknown id or an undo entry gives a plan with no items (`items()` empty, `undoOf()` null, `problem()` null); while downloads run it returns `UndoPlan.unavailable(false, "rigtune.undo.busy")`; for a history.json from a newer RigTune `unavailable(false, "rigtune.undo.unavailable")`; an exception gives `unavailable(false, "rigtune.undo.error")` (check `problem() == null`). Carry it out with the existing `controller.undo(plan)`, which re-checks it under the apply lock exactly as for Undo last and journals one `undo` entry with `undoOf = entryId` (a plan with nothing to do journals nothing).
- Or drive the screen: `new UndoScreen(parentScreen, controller, entryId)`; its Confirm button (`rigtune.undo.confirm`) calls `controller.undo(plan)`. `UndoScreen.entryId()` and `plan()` are public.
- The entry ids are in `config/rigtune/history.json` (`Journal.entries()`; for the scenario "two applies, each adding a mod", the older apply is the entry whose change has the first mod's `file`).
- The `UndoScreen(Screen, RigTuneController, boolean)` constructor UndoDriver uses is unchanged.

## Deviations
- `Journal.State` has UNREADABLE besides the four states in B-M2 (above).
- The benchmark kind is labelled "Benchmark result" (SPEC 6 sketches "Benchmark keep").
- History rows name mod files, not mod display names (the journal has no names).
