# WS-P design notes: dry-run preview (SPEC 13)

Branch `feat/preview`. Plan: docs/v0.3/plans/ws-p.md. The coordinator folds these notes into DESIGN.md.

## What ships
- A **Preview** button in the RigTune footer, right after Apply, active exactly when Apply is (something ticked). It opens `PreviewScreen` with exactly the items Apply would take (`RigTuneScreen.ticked()`, which `applySelected()` now uses too, so the two can't drift).
- `PreviewScreen` lists, file by file, what Apply would do, in five sections: **Written now** (options.txt: `key: old → new`), **Changed at the next restart** (config/sodium-options.json, config/DistantHorizons.toml, config/iris.properties: `key: old → new`, "not set" for a new Sodium field), **Downloaded now, added at the next restart** (`mods/<file> (<item>)`, `(needed by <item>)` for a required dependency, or "A file from Modrinth for <item>, with any mods it needs" when Modrinth is off), **Renamed to .disabled at the next restart** (`mods/<file> → <file>.disabled (<item>)`, both removals and the old jar of an update), and **Not changed** (each ticked item Apply would skip, with the reason). Paths are relative to the game folder. The model is worked out on `Probes.EXECUTOR` (it may ask Modrinth), with a loading, empty and error message; Done returns to the RigTune screen with the ticks kept.
- Nothing is written or downloaded, and Modrinth is only asked (metadata lookups, never a download) while Modrinth is on in RigTune's settings.

## How it reuses Apply (no second set of rules)
- `core/preview/PreviewPlanner`: the partition of the selection is RealController.apply's switch, case for case (vanilla prefix → now; a ConfigTargets prefix → the target's stager; DisableMod directly in the mods folder → disable; Add/Update → downloads; anything else → nothing). It is the one duplicated piece (RealController.apply isn't unit-testable and the brief keeps RealController's edit to one method); the class comment says to keep the two in step, and PreviewDifferentialTest replays apply's switch against the real staging classes.
- Vanilla: SettingsBridge.applyVanilla's own checks in its order (`SettingKeys.changeable`, `SettingKeys.safeValue`, an option the game has, then the option's own parse and range check through the new read-only `SettingsBridge.problems`, which runs applyBatch's `decode` + `validateValue` without setting anything) and the game's current values (`SettingsBridge.readVanilla`), both read on the render thread and only when a vanilla setting is ticked; only a value that differs is listed (Apply's `options.save()` runs only when something changed).
- Config files: the stagers Apply calls (`SodiumConfigPatcher`/`TomlConfigPatcher`/`PropertiesConfigPatcher.stage`, which only read the file) and the ConfigTargets readers for the old values (what Staging journals as "before"); a refused value is listed with the patcher's own message.
- `.disabled` names: `ApplyExecutor.disabledTarget` (made public; visibility only), so a taken name shows `.disabled.1` as the helper would pick.
- Downloads: the real `DownloadPlanner` and `DependencyResolver`, with RealController.download()'s own inputs (`DownloadInputs`: installed versions, update versions, installed projects, loaded ids, staged jars, the rules' conflicts, the raw game version), run through `core/modrinth/DryRunPlanner` (new file; calls DownloadPlanner's package-private constructor, so DownloadPlanner itself is untouched). Its fetcher checks the file name with `SafeFileNames.resolveJar` like Apply's and returns a path that is never created (`<name>.jar.rigtune-pending.preview-<uuid>`); the same file fetched again keeps its stand-in mod id. `LookupOnlyClient` wraps the client: `download()` always throws, and every call throws while Modrinth is off. So every planner check runs as for Apply: updates before additions, conflicts between ticked additions, a target file already taken, an update whose Modrinth data changed, Modrinth incompatibilities (post-update view, SPEC 3b), dependencies already installed or brought by an earlier item (listed once, under the first item). A refusal is listed with the planner's own reason (its errors come one per refused item, in its order).

## Footer (AC13.2): why an ordinary button after Apply
RigTuneScreen fits `clamp((column + 4) / 92)` buttons per row (column = min(width - 32, 480)). Measured in CI (PreviewGameTest logs every footer button):

| GUI size | 8 buttons (no pending changes) | 9 buttons (Discard pending shown) |
|---|---|---|
| 640x480 @ 2 (320 wide) | 3 rows, 93 px | 3 rows, 93 px |
| 854x480 @ 2 (427 wide) | 2 rows, 95 px | 3 rows, 120 px |
| 1280x720 @ 2 (640 wide) | 2 rows, 117 px | 2 rows, 92 px |

Every button stays >= 92 px, so ReportGameTest's "Report a problem" (needs >= 91) still fits, and at 640x480@2 the footer has the same 3 rows as before. The only cost is a third row at 854x480@2 while Discard pending is shown. A split Apply/Preview button was rejected: half of a 93 px slot (about 45 px) can't hold "Apply (12)".

## Known limits (documented, not fixed)
- With Modrinth off in the settings, Apply's client refuses every download; the preview still lists each update's file and each addition as "A file from Modrinth" (as the brief asks), with a note that Apply can't download them until Modrinth is on again. Practically unreachable: ModrinthOffAdvice turns Add/Update items into advice while Modrinth is off.
- A config value already equal to the file's is shown as "already set"; Apply still stages its patch op (pending.json, a restart prompt, a history entry), which the helper then skips without touching the file. Only a stale report can tick such an item.
- A download's jar mod id is only known once it is downloaded. The preview gives each resolved file a stand-in id (an update's file gets the updated mod's id), so it can't show Apply's three download-time outcomes: a jar that turns out not to be a Fabric mod (refused), a jar whose mod is already loaded (skipped), or two jars of the same mod (joined). The downloads section says so in a note.
- A vanilla value the game accepts but then changes ("Rejected by the game" in SettingsBridge.setOption) can only be seen by setting it. `vanilla.graphicsPreset` (allowed, but no rule sets it) rewrites a dozen other options at Apply; the preview lists only the preset.
- While an earlier Apply's downloads are still running, Apply answers "busy" (and a helper still holding the apply lock makes staging fail); the preview shows what Apply would do once they're done.
- Skipped details (the patchers' and the planner's messages) are English strings from core. WS-G's `Text` conversion (DownloadPlanner.Result.errorTexts, TextException) isn't merged yet; once it is, the preview's download refusals can take the translated `errorTexts` (same order as `errors`).
- Previews run one at a time on their own daemon thread (never on Probes.EXECUTOR, so their Modrinth lookups can't hold up report rebuilds or Apply's downloads); one still queued when its screen closes is skipped, but one already running finishes (its lookups have BoundedHttp's timeouts).
- Modrinth's answers can change between Preview and Apply (a newer version, a new dependency).
- DownloadPlanner logs its usual WARN ("Could not prepare …") for an item it refuses, also during a preview (WS-G owns DownloadPlanner).

## Tests
- `core/preview/PreviewPlannerTest` (15): vanilla now/unchanged/not changeable/control characters/unknown/refused by the game's own check; Sodium, DH and Iris keys at restart with old values from the file (a new Sodium field has none); refusals with the patcher's reason; disables including `.disabled.1`; outside the mods folder; advice; an empty selection; the instance tree (SHA-256 of every file) unchanged; `relative`.
- `core/preview/PreviewDownloadsTest` (13): an update (download + disable), an addition with a required dependency (by id and by slug), a dependency two additions need (listed once), a dependency fetched again after a failed item (the next new file still listed), files already there (NO_NEW_FILES), a taken target and a conflict (the planner's reasons), an unresolvable addition, Modrinth off (no call at all; "a file from Modrinth"; an update still planned but flagged), settings alone, and no write or download.
- AC13.1 `client/PreviewDifferentialTest` (3 selections in temp instances, a fake Modrinth whose download writes real jars): "everything applies" (vanilla renderDistance, a Sodium key, a DH key, an update, a disable, an addition with a required dependency); "refusals and edge cases" (an unchanged vanilla value, a Sodium value the file refuses, a new Sodium field, a quoted DH enum, an Iris key and an unknown one, a disable whose `.disabled` name is taken, a disable outside mods, an update whose target is taken, an addition already in mods/ with its dependency installed, an advice); "items in one batch" (two conflicting additions, a dependency two additions share, a dependency already installed, an update). For each: the preview writes and downloads nothing; then RealController.apply's staging, step by step with the real classes (the stagers, `Op.disableFile`, `Staging.stage` with the real lock and journal, `DownloadPlanner` with a fetcher that downloads through the fake): the items the preview marks refused are exactly the ones the real staging refuses, the `.rigtune-pending` downloads are exactly the preview's jars, pending.json's ops name exactly the preview's files (less the `.disabled` names the helper picks at restart), and after `ApplyExecutor.run` (the helper's executor) the files created, renamed away or changed (outside config/rigtune/) are exactly `preview.filesAtRestart()`. Shown to fail when the preview drops a dependency. Because this replays apply's switch by hand, PreviewGameTest also runs the real RealController.apply (below).
- AC13.2 `PreviewGameTest` (registered last): the stub's report through a controller with a canned preview (every section, long DH keys and file names, an unresolved addition, three kinds of "not changed"); at 640x480@2, 854x480@2 and 1280x720@2 (plus the 9-button footer at each) Preview is right after Apply in the same row, every footer button >= 91 px with its label inside, nothing overlaps or leaves the screen; Preview gets exactly Apply's selection; every preview row's text fits its column; screenshots `preview-footer-<size>`, `preview-<size>`. Then the real controller: Preview on the default ticks (Modrinth lookups included), options.txt, mods/ and config/ (RigTune's apply files included) byte-identical afterwards and no `.rigtune-pending` file; screenshot `preview-real`. Then AC13.1 through the real RealController.apply: preview renderDistance n → n-1 (one Setting, options.txt, nothing else; 99 is listed as refused by the game), Apply it, and options.txt's changed keys are exactly {renderDistance: n-1}; then a disable of a throwaway jar plus (Sodium loaded) a Sodium switch flipped: after the real Apply, pending.json names exactly the preview's files, nothing has changed yet, and it's all discarded. Restored afterwards (options, history.json, the probe jar).
