# RigTune v0.3.0: specification

Status: DRAFT (Phase 2). Each item has acceptance criteria (AC). An item ships only when every AC is verified, and the evidence is recorded in docs/PROGRESS.md. Priorities: P0 must ship; P1 should ship (defer with a written reason); P2 stretch. Cut P2 before compromising P0/P1 quality.

Research inputs: docs/research/v0.3/{mc-versions,ci-gametests,launcher-ram,hardware-tiers,benchmark,misc}.md. Orientation (2026-09-26): the user's real instance still runs 0.1.0 (last played 2026-09-25 09:08; no benchmark, no history); the Modrinth project is still in review; no update-rules PR is open.

Compatibility promise:
- A 0.1.x client never gets an unsafe or less conservative recommendation from `rules-v1.json` (RulesV1DifferentialTest + check_rules_v1.py).
- A 0.2.x client never gets an unsafe recommendation from `rules-v2.json`: a new condition field fails closed; a new rule-level field is either ignored-safe for 0.2.0 (it can only take a recommendation away) or the rule carries a `requires` feature 0.2.0 doesn't know; a new tier-table column needs a new schema file.
- Every file 0.1.0 and 0.2.0 wrote (`pending.json`, `last-apply.json`, `history.json`, `benchmarks.json`, `settings.json`, `rigtune.json`, `rules-cache.json`, `rules-v2-cache.json`, `benchmark-restore.json`, `helper/`) keeps working after an upgrade to 0.3.0. 0.3.0 doesn't change any of their formats (no `formatVersion`/`schemaVersion` bump), so a downgrade to 0.2.0 keeps working too; any new optional field must be one 0.2.0 ignores on read.

## 3. Deferred v0.2 defects (P0)
Sources: docs/reviews/review-4.md ("Deferred to v0.3.0"), orientation of the real instance.

### 3a. `Staging.dropQueuedUpdates` scope and `staged` bookkeeping
- Today (client/undo/Staging.java:195) every staged ENABLE_FILE whose mod id has a jar in `mods/update/` is dropped with its group on every rebuild, even when that mod isn't loaded. A stale jar there cancels an addition or an undo re-enable forever; and RealController's `staged` set (RealController.java:88/308) only clears `update:<id>`.
- Fix: drop a staged group only when it is RigTune's **update** of a **loaded** mod whose own update is queued: the group has an ENABLE_FILE with that mod id AND the mod id is loaded (ModScanner's loaded ids) AND the mod has a queued jar in `mods/update/`. Additions and undo re-enables of a mod that isn't loaded are kept. After a drop, the client's staged bookkeeping is recomputed from `pending.json` (every recommendation id whose ops left pending is cleared, not only `update:<id>`), so the report ticks/labels match what's really staged.
- AC3.1 Unit tests: an addition of an unloaded mod with a stale queued jar stays staged; an undo re-enable of an unloaded mod stays staged; an update of a loaded mod with a queued update is dropped (with the notice); the staged ids after a drop equal the ids still in pending.json.

### 3b. DependencyResolver judges the post-update state
- Today (core/modrinth/DependencyResolver.java:88-114) a version-specific Modrinth `incompatible` dependency is judged against the pre-update installed version ids, and the batch's own updates aren't in the "going in together" set.
- Fix: the resolver's view is "installed, with every update in this batch applied": an installed project with a batched update counts with the update's version id (the old one no longer counts), and every batched update version joins the set checked against `incompatible` entries (both directions, as for additions).
- AC3.2 Unit tests: (i) B declares `incompatible` on A's version v1; A is installed at v1 and updated to v2 in the same batch → B is not refused; (ii) B declares `incompatible` on A v2, which is being updated to in the batch → refused, naming A; (iii) an update's own version declaring `incompatible` on an installed project → refused; (iv) the existing tests stay green.

### 3c. No raw version ids in messages
- A version-only dependency's message shows a Modrinth version id today (DependencyResolver.java:101-103). Fix: name the project the version belongs to (its title, from the version lookup; slug, then "another mod" as fallbacks), never a raw id.
- AC3.3 A unit test asserts the message for a version-only incompatible dependency contains the project title and matches no base62 version-id pattern of the fixture.

### 3d. Weekly rules PRs
- None open on 2026-09-26. Before the release, any open `bot/rules-update-*` PR is triaged: merged into feat/v0.3.0 (after a green CI and a read of its REVIEW.md) or closed with a written reason.
- AC3.4 PROGRESS.md records every rules PR seen during v0.3 and its outcome.

### 3e. Real-instance feedback
- The only real-world failure (0.1.0's DH update racing DH's own updater) is fixed in 0.2; the queued DH build in the user's `mods/update/` is a multi-loader jar whose `fabric.mod.json` id is `distanthorizons`, so 0.2+ detects it (checked read-only 2026-09-26).
- The failure's reason was only in `config/rigtune/helper.log`. Fix (with item 6): at startup, when `last-apply.json` has failed ops, RigTune logs one WARN line per failed op in `latest.log` (op, mod or file name, reason, attempt n of 3) and item 6's history screen shows the reason next to the change.
- AC3.5 A unit test over a real 0.1.0-shaped failed `last-apply.json` (the captured fixture) produces the WARN lines; the history screen shows "Last attempt failed: ..." for that change (item 6 game test).

### 3f. Benchmark render-distance steps load no extra terrain (found in v0.3 research)
- ClientKnobs applies render distance in memory (`SettingsBridge.applyVanilla(..., save=false)`), and only `Options.save()` calls `broadcastOptions()`, so the (integrated) server keeps the join-time view distance: after RD 5 → 12 in memory the client held 162/167 chunks (26.2/26.3) for 10 s; within about 1 s of `options.broadcastOptions()` it held 637 on both (benchmark.md §c). Tune's up-steps therefore measure the start-RD chunk set and can recommend too high a render distance.
- Fix: after every render-distance or simulation-distance change the benchmark makes (each step and the restore), call `options.broadcastOptions()` (no options.txt write), and wait until the chunk count settles before measuring.
- AC3.6 = AC8.1-AC8.3, plus a game test in the benchmark world that joins at RD 5, runs a step at RD 12 and asserts every chunk within 11 of the camera is loaded before that step records its first frame (26.2 and 26.3). AC3.7 A real `runBenchmarkAutorun` Tune on 26.2 and 26.3 (Phase 5) records per-step chunk counts that grow with RD.

## 5. Launcher-aware RAM advice (P1)
Sources: docs/research/v0.3/launcher-ram.md.
- The rules keep deciding **when** and **how much** (the `ram-*` advice rules; the research found their thresholds corroborated: 2 GB launcher defaults are too little for modded play, 6 GB for Distant Horizons or shaders, about 8 GB with both, no more than about half of system RAM on small machines, a ceiling around 8 GB because a larger G1 heap lengthens pauses). 0.3 adds **how**: the launcher's exact steps.
- Detection (pure core, `core/launcher/`), from signals the running JVM can read, in this order; every signal is optional and a missing one is just "not this launcher":
  1. `org.prismlauncher.instance.name` or `multimc.instance.title` system property, or the `INST_ID`/`INST_NAME` environment variables → **Prism Launcher** (MultiMC family).
  2. `minecraft.launcher.brand` = `theseus` → **Modrinth App**; = `ATLauncher` → **ATLauncher**; the official launcher's literal only if verified from primary evidence during implementation (else those users get the generic text).
  3. Walking up from the game dir (at most 3 levels): `instance.cfg` + `mmc-pack.json` → Prism (corroborates 1; `MaxMemAlloc` read); `minecraftinstance.json` → **CurseForge app** (reads `isMemoryOverride`, `allocatedMemory`).
  4. Otherwise **Unknown**: today's generic wording, no launcher named.
  Path substrings are never the only signal. Only these property/env names are read; nothing about the launcher leaves the machine except the launcher *name* in the share report the user copies.
- UI: every advice whose id starts with `ram-` (documented in RULES_SCHEMA.md as the convention) gets one extra line: "In <Launcher>: <click-steps>" (translatable, one key per launcher; CurseForge uses the per-pack "Profile Options" steps when that pack overrides memory, else the global Java settings). The hardware header's memory line names the launcher ("6 GB of 32 GB, set in the Modrinth App"). Click-step wording comes from the launcher's own UI strings where the launcher is open source (Modrinth App, Prism, ATLauncher: cite file and line in the research doc) and from the best available sources otherwise (marked).
- AC5.1 Unit tests for detection: each launcher from its real signals (property/env/file fixtures copied from real formats), precedence (Prism property beats a `theseus` brand), malformed/oversized `instance.cfg`/`minecraftinstance.json` → no crash, no value, Unknown only when nothing matches, no signal → Unknown. AC5.2 Scenario tests over the bundled rules: the `ram-*` advice for (8 GB system, 2 GB heap), (16 GB, 2 GB, DH), (32 GB, 6 GB, DH + shaders), (32 GB, 16 GB) gets the right launcher line for each launcher and none for Unknown. AC5.3 UiGameTest screenshots at 3 sizes show the launcher line with `-Dminecraft.launcher.brand=theseus` and without it. AC5.4 The share report names the launcher and nothing else about it (unit test).
